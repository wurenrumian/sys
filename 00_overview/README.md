## 一、三个方向其实是一次训练 step 的三段时间

大部分人第一次看这份材料，会把它读成"三个并列的技术领域"。这是最容易走偏的地方。
它们其实是**同一条时间线上的三段**：

```
        ┌──────────── 一次训练 step ────────────┐

  磁盘/对象存储 ──①──> CPU 内存 ──②──> GPU 显存 ──③──> 算子执行 ──④──> 跨卡同步
       └── 01 存储：读得动、存得起 ──┘   └── 02 编译：算得快 ──┘  └─ 03 网络：对得齐 ─┘

  ① 列存/压缩/缓存      ② ETL 与 GPU 计算的流水线重叠     ③ 显存分配、算子融合、编译
  ④ AllReduce / AllToAll，以及它和在线 RPC 抢同一张网
```

**推论 1：优化哪一段，取决于这一段现在占多少。** 这不是态度问题，是算术问题。
`04_endtoend/demo1` 把这笔账算给你看：在默认的推荐训练场景里，通信占 ~89%，
于是"把存储做快 2 倍"的端到端收益精确等于 **1.00x**。

**推论 2：瓶颈会迁移。** 卡数从 1 到 4096，瓶颈从数据变成通信；
batch 从 1k 到 256k，瓶颈从通信变成计算。所以"该学哪个方向"没有普适答案，
只有"在你的场景里先测一遍"。

## 二、共同母题

> **在异构硬件（CPU/GPU/DPU/网卡/SSD）上，把"数据搬运"的成本压到接近"数据计算"的成本。**

搜广推让这个母题格外尖锐，因为它同时要：

| 约束 | 后果 |
|---|---|
| (a) 万亿级流量 | 存储与 I/O 成本超过算力成本，必须分层、压缩、缓存 |
| (b) 毫秒级 P99 | 尾延迟成为一等指标，而尾延迟对突发和不可抢占单元极度敏感 |
| (c) 稀疏、不定长数据 | 稠密张量的假设失效：padding 浪费、显存碎片、编译无法特化 |

**任意去掉一条，通用的 LLM Infra 方案就够用了；三条同时成立，就必须重做。**
这句话是整份材料的题眼。

## 三、量级速查表（建议背下来）

做系统的人和不做系统的人，区别往往就是这张表在不在脑子里。

### 延迟

| 操作 | 量级 | 相对 L1 |
|---|---|---|
| L1 cache 访问 | ~1 ns | 1× |
| L2 / L3 cache | ~4 / ~30 ns | 4× / 30× |
| 本机 DRAM | ~100 ns | 100× |
| GPU HBM | ~200 ns（延迟高，但带宽极大） | 200× |
| NVLink 跨卡 | ~1 µs | 1,000× |
| 同机架 RDMA / RTT | ~2–10 µs | 10,000× |
| 本地 NVMe 随机读 | ~100 µs | 100,000× |
| 跨可用区网络 | ~1 ms | 10⁶× |
| **TCP 超时重传（RTO_min）** | **~200 ms** | **2×10⁸×** |
| 对象存储（S3/HDFS）首字节 | ~10–100 ms | 10⁷× |

> 最后两行是尾延迟的所有故事的来源：正常路径是微秒级，**异常路径是毫秒级**，
> 差 3~5 个数量级。所以只要有万分之一的请求走了异常路径，P999 就完了。
> 见 `03/demo4`。

### 带宽

| 通道 | 典型带宽 |
|---|---|
| GPU HBM3 | 3–4 TB/s |
| NVLink（单向，机内） | 300–450 GB/s |
| PCIe Gen5 x16 | ~60 GB/s |
| InfiniBand NDR / 400G 以太 | ~50 GB/s |
| 本地 NVMe | 3–7 GB/s |
| 对象存储（单客户端） | 0.1–1 GB/s |

> 每往外一层，带宽掉一个数量级左右。**分层存储的全部设计工作，
> 就是在这条阶梯上决定什么数据放在哪一层。**

### 算力与"脊点"

| 量 | 典型值 |
|---|---|
| H100 bf16 稠密算力 | ~1000 TFLOPS |
| H100 HBM 带宽 | ~3.35 TB/s |
| **脊点 = 算力/带宽** | **~300 FLOP/Byte** |

> 算术强度低于 ~300 FLOP/Byte 的算子，**无论如何都吃不满算力**。
> 而推荐模型里的绝大多数算子（embedding lookup=0、逐元素≈0.1、LayerNorm≈1）
> 全都远低于它。这一条解释了推荐训练 MFU 为什么天然只有百分之几。见 `04/demo1`。

## 五、贯穿全场的 5 条通用规律

这些规律在多个 demo 里反复出现。认出它们，比记住任何单个数字都重要。

1. **木桶效应是可量化的。** 优化非瓶颈的收益不是"比较小"，而是**精确等于 0**。
   （01/demo5、04/demo1）

2. **尾延迟由"最大不可抢占单元"和"突发性"决定，与平均利用率无关。**
   平均利用率 8% 的链路照样能有 320µs 的 P999。（03/demo1、03/demo4）

3. **平均值会骗人，方差才是系统的真实成本。** 平均 ETL 比 GPU 快，GPU 照样挨饿；
   编译缓存命中率 97%，P99 照样 400ms。（01/demo5、02/demo5）

4. **用确定的小浪费，换掉不确定的大抖动，几乎总是划算的。**
   分桶 padding、分片、分页、对冲请求，全是这个模式。（02/demo3、02/demo5、03/demo1、03/demo4）

5. **手工优化的成功率很低，必须实测。** "看起来更优"的写法经常更慢，
   因为人的心智模型跟不上 cache / 预取 / 分配器 / 极值统计的真实行为。（02/demo1、01/demo4）

## 六、怎么用这个项目

```bash
python3 site/serve.py --open      # 推荐：在浏览器里读、调参、真跑、逐条验证
bash run_all.sh                   # 或者：命令行一次跑完所有 demo
```

**建议的顺序**：先跑 `04_endtoend/demo1`（看清楚账单），再按账单里占比最大的那一段
去读对应目录。如果是为了准备面试，看 `99_learning/README.md` 里的四周路线。

每个 demo 在网站上都有一组**验证点**——把结论拆成可以逐条核对的断言。
跑完之后自动比对，不吻合的会标红。**跑出不吻合是好事**：要么你改了参数
（说明这个结论有边界条件），要么这里本来就该被推翻。
