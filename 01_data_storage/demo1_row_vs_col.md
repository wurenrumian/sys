# demo1 · 行存 vs 列存

> 同一张表，同样的值，只是字节在磁盘上的摆放顺序不同 —— 扫描 I/O 差 13 倍，压缩率差 24%。

---

## 一、真实场景：这段代码对应线上的什么

抖音/淘宝的推荐模型训练，每天要从数据湖里读**上百 PB** 的样本。一条训练样本长这样：

```
user_id, item_id, 时间戳, 场景ID, 设备型号, 国家, 网络类型, ...    ← 标量字段，几十上百个
user_behavior_seq: [item_1 ... item_2000]                      ← 长序列
item_emb: float16[128], video_frames_emb: [...]                ← 多模态向量
label: {点击, 完播, 点赞, 下单}                                   ← 多目标
```

关键事实：**一次实验只关心其中一小部分字段。** 算法同学今天想验证"加入设备型号交叉特征有没有用"，
那这个实验只需要几十个字段里的 3~5 个。剩下的字段一个都不会进模型。

但如果样本是按"行"存的（一条样本的所有字段挨着放），存储和网络**没办法只搬那几个字段** ——
磁盘和网络的最小传输单位是块（4KB~1MB），一个块里混着这一行的所有字段。
于是你为了用 5% 的数据，付了 100% 的 I/O。

一天的训练任务跑几十上百个实验，每个都全量扫一遍。这就是为什么存储布局在推荐场景是**成本问题**，
不是性能洁癖。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造一张有代表性的宽表

`make_table()` 造 `N_ROWS × N_COLS` 的表。**字段类型是刻意混合的**，按 `c % 4` 分成四类：

| 列类型 | 怎么造的 | 为什么要有它 |
|---|---|---|
| 时间戳（单调） | `arange(N)//100 + 1.7e9` | 模拟事件时间，**局部单调**，delta 编码后熵极低 |
| 稀疏 ID（长尾） | `rng.zipf(1.3)` | 模拟 item_id/user_id，长尾分布，难压缩 |
| 低基数枚举 | `rng.integers(0,16)` | 模拟场景/设备/国家，只有 16 种取值 |
| 稠密浮点 | `normal(0,1)*1000` | 模拟统计特征，近似随机，最难压缩 |

**这一步是整个 demo 的关键设计**：如果四类字段都造成同一种分布，就看不出列存的第二个收益
（分列之后每列可以各自选最优编码）。

### 第 2 步：做出两种物理布局

```python
as_row_format(cols)  →  np.stack(cols, axis=1)   # (N_ROWS, N_COLS) 的 C-order 二维数组
                                                  # 内存里一行的 40 个字段是连续的
as_col_format(cols)  →  [c.copy() for c in cols] # N_COLS 个独立的一维数组
                                                  # 内存里同一列的 N 个值是连续的
```

这两份数据**内容完全一样**，`assert np.array_equal(r_out, c_out)` 会验证这一点。

### 第 3 步：测投影扫描

```python
scan_row: touched = 整表字节数        # 行存无法跳过 → I/O 是全量
          out = row_tbl[:, project].sum(axis=0)    # 跨列跳着取，stride = 40*8 字节

scan_col: touched = 只有 3 列的字节数  # 列存只读 3 个列文件
          out = [col_tbl[c].sum() for c in project]  # 每列内部完全顺序访问
```

注意 `touched` 是**手工算的 I/O 量**（模拟磁盘/网络要搬多少字节），
而计时测的是**CPU 侧的访存效率**。两者是两个独立的收益，demo 分开报告。

### 第 4 步：测压缩率

用 `zlib.compress(level=6)` 分别压：整张行存表的字节流 / 每一列各自的字节流。
再逐列打印压缩比，暴露"不同字段类型可压缩性差异极大"这个事实。

### 第 5 步：外推到真实量级

按"单样本 1KB、1000 亿条/日 = 100PB/日 原始"，算出两种布局各自的落盘量和单次实验扫描量。

## 三、涉及的机制（为什么重排字节能差一个数量级）

### 机制 1：投影下推（projection pushdown）

存储层搬的是**块**不是**格子**。列存把同一字段的值连续放，于是"只读 3 列"能落到物理 I/O 上：

```
I/O 比例 = 投影列数 / 总列数        （理论下限，demo 里实测正好达到）
```

### 机制 2：熵更低 → 压缩更好

同一列的值：类型相同、取值域接近、常常还有序。信息论上熵更低，通用压缩器（zlib/zstd）就压得更狠。
更重要的是**分列之后可以逐列选专用编码**，这在行存里做不到（一行里各字段类型是混的）：

| 编码 | 适合什么列 | 原理 |
|---|---|---|
| Delta | 单调/近似单调（时间戳、自增 ID） | 只存相邻差值，差值范围小 |
| 字典 + RLE | 低基数枚举（场景、设备、国家） | 值 → 小整数，连续相同值只存 (值, 次数) |
| Bit-packing | 值域已知且小 | 用 `ceil(log2(基数))` 位而不是 64 位 |
| 通用压缩 | 稠密浮点 | 只能靠 zlib/zstd，收益有限 |

### 机制 3：访存局部性 → CPU 也更快

行存读 3 列是 **strided access**：每读 8 字节要跳 320 字节，一个 cache line（64B）里只有 8 字节有用，
预取器也不友好。列存是纯顺序访问，cache line 100% 利用、硬件预取器全速工作、还能向量化。
demo 里 CPU 耗时的差距（默认约 23x）主要来自这一条。

**这三个机制是相乘的**，这是列存收益大的根本原因：

```
有效收益 ≈ (投影比例) × (1/压缩比) ，再叠加 CPU 侧的访存效率
```

## 四、方案对比

| 布局 | 做法 | 优点 | 代价 | 什么时候用 |
|---|---|---|---|---|
| **行存** | 一行的所有字段连续 | 取整行极快；单行写入/更新便宜 | 投影扫描必须读全部字节；压缩率低 | OLTP：点查、按主键更新 |
| **列存** | 同一列的所有值连续 | 投影下推、高压缩、向量化友好 | 取整行要跨 N 个列文件；改一个值要重写整个 column chunk；**写入必须攒批** | OLAP：全表扫、只用少数列、只读不改 |
| **混合（PAX）** | 先按行分组（row group），组内按列存 | 兼顾"一次读一批完整行"和列裁剪 | 实现复杂；row group 大小又是一个要调的参数 | Parquet/ORC 实际用的就是这个 |

**训练样本读取属于哪一类？** 全表扫 + 只用少数列 + 只读不改 —— 是一次标准的 OLAP 扫描。
所以数仓那套优化能原样搬过来，这也是"湖仓一体"在推荐场景成立的前提。

**代价里最要命的是"写入必须攒批"**：

- 批大 → 压缩率高、小文件少，但数据要等攒够才可见，**新鲜度差**；
- 批小 → 数据新鲜，但压缩率掉、小文件数量爆炸、**元数据本身成了大数据**。

推荐场景既要分钟级新鲜的样本（在线学习），又要数仓级的压缩率，这两个要求直接打架。
**这就是流式 Lakehouse（Iceberg / Hudi / Paimon）的核心矛盾**，也是这条课题真正的战场。

## 五、怎么读输出

### `[1] 投影扫描`

```
             扫描字节      耗时(ms)
  行存         64.0MB        7.3
  列存          4.8MB        0.3
  -> I/O 量降为 7.5% (理论下限 7.5%), CPU 耗时 23.3x 加速
```

- **7.5% 正好等于理论下限 3/40** —— 说明列存把投影收益吃满了，一个字节都没多读。
- **23.3x 是 CPU 侧的额外收益**，来自 cache 局部性，和 I/O 那 13 倍是**两笔独立的账**。

### `[2] 压缩比`

```
  行存整表          :   5.52x
  列存整表          :   6.85x
    col0  时间戳(单调)   253.57x     ← 单调 → delta 后几乎不占空间
    col1  稀疏ID(长尾)     5.33x
    col2  低基数枚举       9.41x     ← 还能上字典/RLE 再翻几倍
    col3  稠密浮点         3.50x     ← 近似随机，压不动
```

**这四行是本 demo 最有信息量的地方**：同一批数据混着压只有 5.52x，分开压最好的一列 253x。
数据一个 bit 没变。这说明"重排"本身就创造了价值 —— 因为它让相似的东西挨在了一起。

### `[2b] 逐列专用编码对比 —— 列存第二个、也是更值钱的收益`

```
列类型          原始int64      zlib   delta+zlib   字典+RLE   bit-pack     最优编码
时间戳(单调)        1.0x     253.6x      318.2x      57.1x       5.8x   delta+zlib
稀疏ID(长尾)       1.0x       5.3x        4.0x       3.1x       2.7x         zlib
低基数枚举          1.0x       9.4x        8.3x       4.0x      16.0x     bit-pack
稠密浮点           1.0x       3.5x        3.4x       3.6x       4.6x     bit-pack
```

**四种列类型的最优编码各不相同** —— 这就是"分列之后每列可以各选编码"的直接证据。
通用 zlib 是所有列的"及格线"，专用编码在对的列上能再翻几倍到几十倍。
Parquet/ORC 的编码选择器做的就是这件事：扫一遍列的统计信息（是否有序、基数多少、值域多大），
自动挑一种编码。**行存做不到这一点，因为一行里各字段类型是混的。**

两个跑出来才知道的细节：

1. **字典+RLE 在低基数枚举列上输给了 bit-pack。** 因为这里的枚举值是随机排列的，
   游程长度平均只有 1，RLE 完全没东西可折叠。**RLE 的前提是有序。**
   这解释了一个真实的工程实践：数仓会按低基数列做**排序/聚簇**（sort key、clustering、Z-order）
   —— 排序本身不改变数据，却能让 RLE 从失效变成暴击。
   也就是说，**编码的效果取决于数据的物理顺序，而顺序也是可以设计的**。
2. **稠密浮点对谁都不敏感** —— 近似随机的数据压不动。所以 embedding 这类稠密向量的
   存储成本只能靠**量化**（fp16/int8）去降，而不是靠压缩。压缩解决不了"信息量本来就大"。

### `[3] 外推`

把上面两项相乘，落到 PB 级的钱上。列存的落盘量和单次实验扫描量同时下降。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `N_PROJ` | 3 → 40 | I/O 从 7.5% 涨到 100%，投影收益**归零**，只剩压缩那一项 | 列存的收益条件是**投影比例低**，不是"列存天生更快"。要全字段的作业，列存并不占优 |
| `N_COLS` | 40 → 10 | 收益缩到 30% 左右 | 表越宽，列存越赚。这解释了为什么数仓要做**宽表** —— 宽表放大了列存的优势 |
| `N_ROWS` | 调大 | 压缩比基本不变，耗时线性增长 | 压缩率由**数据分布**决定，与数据量无关 |

**建议先做第一个实验**（`N_PROJ` 拖到 40）。看着收益归零，比看着收益很大更能学到东西 ——
它告诉你这个结论的边界在哪。
