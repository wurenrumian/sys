# demo4 · 不定长序列：padding 浪费与 Jagged 布局

> 动态 padding 听起来该省很多，实测几乎白干（1.00x）。真正有效的是按长度排序分桶（15x）。

---

## 一、真实场景：这段代码对应线上的什么

推荐样本和 LLM 样本最大的**结构差异**，是用户行为序列长短差着两三个数量级：

```
新注册用户：    [item_7]                                    长度 1
普通用户：      [item_3, item_91, ..., item_44]             长度 20~60
重度用户：      [item_1, ......................, item_2000] 长度 2000
```

而 GPU 只吃**规整的稠密张量** —— 一个 batch 必须是 `(B, L, D)` 这样的方块。
于是短序列要补零补到 L。补的那些 0：

- 占显存（`B × L × D × 4` 字节，不管有没有用）
- 占访存带宽（kernel 照样要把它们读进 cache）
- 占算力（照样参与乘加，只是结果被 mask 掉）

这对应表格里两处课题：数据中台的"高效数据格式（不定长序列）"，
和编译方向的"Jagged Tensor 的 padding-free codegen"。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造长度分布

```python
lens = clip(lognormal(mean=3.0, sigma=1.6), 1, MAX_LEN)
```

**为什么用对数正态**：真实的用户活跃度是乘性过程的结果（每天活跃概率相乘），
数学上收敛到对数正态。它的特点是**连续长尾** —— 不存在一个"自然的"截断点。
默认参数下 p50=20、p99=837、max=1024，差 40 多倍。

### 第 2 步：算四种布局各要分配多少槽位

```python
useful      = lens.sum()                              # 真正有用的元素数
global_pad  = n * MAX_LEN                             # 所有样本补到全局上限
dyn_pad     = Σ over batch: len(batch) * batch.max()  # 补到本 batch 的最大值
bucket_pad  = 先按长度 sort，再切 batch，同上          # 排序后同批长度接近
jagged      = useful                                  # 零 padding
```

**这四行就是四种工程方案的全部差异。** 后面所有结论都从这四个数出来。

### 第 3 步：扫描 batch size

对每个 batch size 重算动态 padding 和排序分桶的放大倍数 —— 揭示 batch 与浪费的关系。

### 第 4 步：扫描截断阈值

如果直接截断长序列（只保留最近 K 个行为），能保住多少行为 token、影响多少用户。

### 第 5 步：实测两种布局的算子性能

对若干个 batch 的序列做一次 **sum-pooling**（把用户历史行为聚合成一个向量，
这是推荐模型里最基础的操作）：

```python
padded:  dense = zeros((b, L));  dense.sum(axis=1)          # 读整块，大部分是 0
jagged:  np.add.reduceat(values, starts)                    # 分段归约，只读有效值
```

`assert np.allclose(...)` 确认两者结果一致。`reduceat` 相当于一个最朴素的 jagged kernel。

## 三、涉及的机制

### Jagged / Ragged 布局

```
稠密 padded:                        Jagged (values + offsets):
[[a, b, c, 0, 0],                   values  = [a,b,c, d, e,f,g,h]
 [d, 0, 0, 0, 0],                   offsets = [0, 3, 4, 8]
 [e, f, g, h, 0]]                              ↑  ↑  ↑  ↑
                                            第0行 第1行 第2行 结束
15 个槽位，8 个有用             8 个槽位，8 个有用
```

和列存是**同一个思想**：把同类数据紧密排列，用一个索引数组描述边界。
代价也一样：随机访问要多一次间接寻址，而且现成的稠密算子全都不能直接用。

### 为什么"动态 padding"会失效（极值统计）

一个 batch 补到 `max(batch)`，而 `max` 是**极值统计量**：n 个样本的最大值随 n 增长，
在长尾分布下增长得还很快。默认参数下：

```
各 batch 最大值的中位数 = 1024
全局最大值             = 1024
```

一批 512 个样本里，只要有**一个**接近上限的重度用户，整批就被撑满 ——
而长尾分布下这件事几乎必然发生。所以"补到批内 max"和"补到全局 max"几乎没差别。

### 为什么排序分桶有效

排序把"一个长样本污染整批"变成了"长样本只和长样本同批"。
排序后每批的 `max` 逼近该批的 `mean`，浪费自然消失。

**代价**：batch 内样本不再独立同分布（同一批全是重度用户），会影响 BatchNorm 的统计量、
负采样的分布、以及梯度的方差。工业折中是**局部排序**：在几千样本的窗口内排序后再切批，
兼顾随机性与整齐度。

## 四、方案对比

| 方案 | 做法 | 浪费 | 优点 | 代价 | 什么时候用 |
|---|---|---|---|---|---|
| **全局 padding** | 全补到 MAX_LEN | ~15x | 实现最简单，shape 完全静态（编译器最爱） | 显存和算力浪费巨大 | 序列长度差异小；或者调试期 |
| **动态 padding** | 补到批内 max | ~15x | 改一行 collate 代码 | **长尾下几乎无收益** | 长度分布集中时有用 |
| **排序分桶** | 先按长度排序再切批 | ~1.02x | 收益接近 Jagged，**不用改任何 kernel** | 破坏 batch 内 i.i.d.；需要能提前知道长度 | **性价比最高，应该是默认选择** |
| **截断** | 只保留最近 K 个行为 | 可控 | 显存直接可控，shape 静态 | **拿效果换成本**，砍掉重度用户的长期兴趣 | 显存实在不够时的兜底 |
| **Jagged** | values + offsets | 0 | 理论最优 | 每个算子都要重写（含反向）；破坏静态 shape；GPU 负载不均 | 长度差异极端、且有算子库支撑（torchrec/FBGEMM） |

## 五、怎么读输出

### `[1] 四种布局的槽位分配量`

```
  全局 padding (补到 MAX_LEN)     204.8M    15.78x    93.7%
  动态 padding (补到批内 max)     204.5M    15.75x    93.7%   ← 几乎一样！
  排序分桶 + 动态 padding          13.3M     1.02x     2.0%
  Jagged (values+offsets)        13.0M     1.00x     0.0%
```

**93.7% 的槽位是 padding。** 也就是说，不做任何处理时，你买的显存和算力有 93.7% 在算 0。

而动态 padding 只拿到 1.00x —— 这是本 demo 第一个反直觉点，原因见上面的极值统计。

### `[2] batch 越大越亏`

```
   batch    动态padding放大    排序分桶放大
      32           8.98x          1.00x
     512          15.75x          1.02x
    8192          15.78x          1.27x
```

**"加大 batch 提高 GPU 利用率"这条常识，在不定长场景下要打折扣** ——
真实吃进去的算力有很大一部分在算 padding。而排序分桶能把这条曲线压平。

### `[3] 截断`

```
  截断 K       保留的行为占比    受影响用户    相对全局padding
  p90 =156         65.2%         9.9%          15.2%
  p95 =279         78.5%         5.0%          27.2%
  p99 =837         97.6%         1.0%          81.7%
```

截到 p95 保住 78.5% 的行为 token，显存降到 27%。看起来很划算 ——
**但被砍掉的是重度用户的长期兴趣，而重度用户往往贡献了大部分消费时长和收入。**
这个取舍不是纯 infra 能决定的，要和算法一起做。

### `[4] 实测`

```
  padded (b x 1024)      16.8MB    0.44ms    1.00x
  jagged (values+offsets) 1.1MB    0.06ms    6.93x
```

内存差 15.9x，耗时差 6.9x。**浪费的不只是显存**：padding 位置的 0 也要被读进 cache，
在 memory-bound 的算子上，浪费的访存带宽就等比例地变成了浪费的时间。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `SIGMA` | 1.6 → 0.3 | 长度分布变集中，**动态 padding 开始有明显收益** | 动态 padding 不是没用，是**在长尾下**没用。它的失效条件是可以说清楚的 |
| `BATCH` | 512 → 32 | 动态 padding 的放大从 15.75x 降到 8.98x | 小 batch 撞上超长样本的概率低。但小 batch 又损失 GPU 利用率 —— 两难 |
| `MAX_LEN` | 1024 → 4096 | 全局 padding 的浪费急剧恶化，排序分桶基本不受影响 | 排序分桶对长度上限**不敏感**，这是它最好的性质 |
| `N_USERS` | 调大 | 各批 max 更容易顶到上限 | 又是极值统计：样本越多，极值越极端 |

**建议先做第一个实验**（`SIGMA` 拖到 0.3）。看着"没用"的方案变得有用，
比看着它一直没用更能说明问题 —— 你会记住的是**条件**，不是结论。

## 七、和其他 demo 的关系 / 为什么这条课题难

- **和 `02/demo5` 直接冲突**：Jagged 消灭了 padding，却也消灭了静态 shape，
  于是编译器无法特化。省下的访存，可能被"无法编译优化"吃回去。
  **这个张力是推荐 infra 最核心的难题之一。**
- **和 `02/demo3` 是同一问题的两个层次**：不定长是显存碎片的根源；
  分页是显存侧的解法，Jagged 是张量侧的解法。
- **和 `01/demo1` 同源**：Jagged 就是列存思想在序列维度上的延伸。

工程上难在三点：

1. **生态不兼容**：所有现成算子（matmul/attention/norm）都假设稠密规整张量，
   走 Jagged 每个算子都要重写一遍还要处理反向 —— 这是 torchrec / FBGEMM / NestedTensor 存在的理由。
2. **和编译对冲**：见上。
3. **GPU 负载不均**：一个 warp 里各线程处理的序列长度不同，会等最慢的那个。
   所以 Jagged kernel 通常还要做按长度分组的负载均衡调度。
