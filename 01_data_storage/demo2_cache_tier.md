# demo2 · 多级存储与 Embedding Cache

> 长尾分布让 1% 的缓存吃掉大半流量；但决定平均延迟的不是命中率，是**穿透率**。

---

## 一、真实场景：这段代码对应线上的什么

推荐模型里最大的东西不是网络结构，是 **Embedding 表**：

```
user_id  →  向量[128]      几亿~几十亿个 user
item_id  →  向量[128]      几十亿~上百亿个 item
各种交叉特征 ID → 向量      ...
```

单表几百 GB 到几十 TB 是常态（表格里提到 200TB 级的 Sparse 参数）。这个量级：

- **放不进 HBM**：一张 H100 只有 80GB；
- **放不进单机 DRAM**：一台机器 1~2TB 顶天；
- 所以必须**分层**：热的放 HBM/本机 DRAM，温的放远程 DRAM（走 RDMA），冷的放 NVMe/对象存储。

一次在线推理请求要查几百上千个 item 的 embedding；一次训练 step 要查一整个 batch 的。
**每一次查询落在哪一层，直接决定这次请求的延迟。**

存储金字塔的延迟差是**数量级**的，这是整个设计的第一性原理：

| 层级 | 典型延迟 | 相对 HBM |
|---|---|---|
| GPU HBM | ~0.2 µs | 1× |
| 本机 DRAM | ~2 µs | 10× |
| 远程 DRAM (RDMA) | ~10 µs | 50× |
| 本地 NVMe SSD | ~100 µs | 500× |
| 对象存储 / HDD | ~10 ms | 50000× |

对应表格里 TikTok 那条："设计高性能的分布式特征索引缓存（Embedding Cache），减少 RDMA 远程访问次数"
以及 "Sparse/Dense 参数多级存储流水线协同：模拟并优化从冷存储到 HBM 之间的多级 Buffer 穿透率"。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：生成符合真实形态的访问序列

```python
keys = (rng.zipf(ZIPF_A, N_REQ) % N_KEYS)
```

**为什么用 Zipf**：推荐场景的 item 访问频率是极度长尾的 —— 头部几百个热门视频占了大部分播放量，
尾部几亿个视频几乎没人看。Zipf 分布（第 k 热门的频率 ∝ 1/k^a）是这类现象的标准模型，
`a≈1.15` 接近实测量级。

### 第 2 步：可选地注入"热点 churn"

```python
gen_trace(churn_every=50000)   # 每 5 万请求，把 key 空间整体平移一次
```

**分布形状不变，变的是"谁是热点"。** 这模拟推荐场景里真实存在的现象：新视频爆火、
旧热点过气、大促/春晚/热搜更迭。这是缓存策略的照妖镜 —— 稳态下表现好的策略，churn 下可能崩。

### 第 3 步：六种策略横向对比 + 理论最优上界

对同一条 trace 跑六种策略，扫描不同容量。**关键是加了 Belady 最优上界** ——
它需要预知未来所以线上不可实现，但它回答了最重要的问题：**"还值不值得继续调？"**
没有上界的优化就是在黑暗里拧螺丝。

### 第 4 步：算端到端有效延迟（本 demo 的核心）

```python
effective_latency(hit_rates):
    lat = Σ (第 i 层命中比例 × 第 i 层延迟)  +  穿透比例 × 最慢层延迟
```

注意 `hit_rates[i]` 是**占总流量的绝对比例**，不是条件概率。剩下的
`1 - sum(hit_rates)` 就是**穿透率** —— 一路穿过所有缓存层、落到对象存储的那部分。

然后做一个**同等投入的三方对比**（这是 demo 最值钱的一节）：

| 投入 | 具体动作 |
|---|---|
| 上层调优 | 把 1 个百分点的流量从 DRAM 提到 HBM |
| 硬件升级 | 把 NVMe 层的延迟降到 1/10 |
| 压穿透 | 把穿透到对象存储的流量砍一半 |

在两个场景下各算一遍：**场景 A 穿透率 2%**、**场景 B 穿透率万分之几**。

### 第 5 步：算成本

给每层一个相对单位成本（HBM 100 / DRAM 10 / RDMA 8 / NVMe 1 / 对象存储 0.05），
按容量分布加权，对比"全量放 HBM"的方案。

## 三、涉及的算法

### LRU（Least Recently Used）

用 `OrderedDict` 实现：命中就 `move_to_end`，满了就 `popitem(last=False)` 淘汰最久没用的。
**假设**：刚被访问过的，马上还会被访问（时间局部性）。

### 近似 LFU（Least Frequently Used）

真正的 LFU 要在淘汰时找全局最小频次，那是 O(容量) 的，工业上没人这么干。
这里用的是 **Redis `allkeys-lfu` 的做法**：

```python
SAMPLE = 8
淘汰时：随机采样 8 个候选，淘汰其中频次最低的那个   # O(8)，不是 O(n)
```

采样 8 个就已经非常接近精确 LFU 的效果（这是 Redis 作者实测过的）。

另外两个关键细节：

- **计数老化**：每 20 万次访问把所有频次右移一位（`freq >>= 1`）。
  不老化的话，曾经的热点会因为历史高分永远赖在缓存里，新热点根本进不来。
- **惰性清理**：采样池 `keys` 里允许有已被淘汰的陈旧项，抽到了再顺手删掉。

**假设**：长期被频繁访问的，未来还会被频繁访问（频率稳定性）。

### FIFO / 随机淘汰（对照组）

- **FIFO**：只看进来的顺序，命中时**不**移到队尾。它和 LRU 的唯一差别，
  就是"时间局部性"这一个信号值多少钱。
- **随机淘汰**：连顺序都不看。用来回答"策略到底值多少钱"——
  如果精心设计的策略只比随机好一点点，那说明**容量才是主要矛盾，不是策略**。

### W-TinyLFU（Caffeine 的默认策略）

```
小 LRU 窗口(1%)  →  被挤出来的候选要和主体的"受害者"比频次  →  主体(99%)
                     ↑ 准入过滤器：一次性访问的 key 根本进不来
频次定期整体减半（老化周期 = 10 × 容量）
```

### 自适应 W-TinyLFU（爬山法）

固定窗口有个真实弱点：窗口小 → 稳态好但对突变反应慢；窗口大 → 抗突变但稳态吃亏。
而"该多大"取决于当前流量形态，是会变的。

爬山法：每隔一段统计命中率，和上一段比 —— **变好就沿同方向继续调窗口，变差就掉头**。
一个最朴素的在线控制器，不需要任何先验知识。

### Belady MIN（理论最优，不可实现）

淘汰"下一次访问最晚"的那个。实现上先算出每个位置的"下次出现位置"，
再用最大堆维护缓存内各 key 的下次访问时间（惰性删除处理过期条目）。

### 各策略的信号与失效场景

| 策略 | 用什么信号 | 强项 | 失效场景 |
|---|---|---|---|
| 随机 | 无 | 无最坏情况 | 平庸 |
| FIFO | 进入顺序 | 简单 | 不认时间局部性 |
| LRU | 最近访问时间 | **对分布变化反应快** | 一次全表扫描就冲垮 |
| LFU | 历史频次 | 稳态长尾强 | **陈旧计数挡住新热点** |
| W-TinyLFU | 频次 + 窗口 + 准入 | 稳态强、抗扫描 | **负载整体突变时准入过滤器成负资产** |
| 自适应 W-TinyLFU | 同上 + 命中率反馈 | 能自我校正 | 反馈有滞后 |

## 四、方案对比

| 策略 | 做法 | 优点 | 代价 | 什么时候用 |
|---|---|---|---|---|
| 无缓存 | 每次都查底层 | 无一致性问题、无内存开销 | 延迟被最慢层支配 | 访问分布均匀（推荐场景不成立） |
| LRU | 淘汰最久未用 | 实现简单；分布变化时恢复快 | 抗不住扫描型流量 | 流量突发多、热点变化快 |
| LFU（采样） | 淘汰频次最低 | 稳态命中率高 | churn 时被陈旧计数拖累 | 热点稳定的长尾分布 |
| W-TinyLFU | LRU 窗口 + TinyLFU 主体 + 老化 | 两者优点都要 | 实现复杂、参数多 | 生产环境的默认选择 |

## 五、怎么读输出

### `[0] 分布有多偏`

```
访问过的 key 共 92,154 个, 其中最热的 1% 承接了 67.0% 的请求
```

一句话解释了**为什么缓存在推荐场景性价比高得离谱**：极小的容量覆盖极大的流量。

### `[1] 六种策略横向对比 + Belady 上界`

```
 容量占比    条目数   随机淘汰   FIFO    LRU    LFU  W-TinyLFU 自适应  Belady上界  离上界
   0.1%     1,000   55.2%  55.2%  58.7%  65.3%   63.7%  63.4%    69.4%   4.0pt
   1.0%    10,000   68.4%  68.3%  70.6%  73.2%   72.7%  72.5%    76.8%   3.6pt
  10.0%   100,000   77.0%  77.0%  77.0%  77.0%   77.0%  77.0%    77.0%   0.0pt
```

三件事：

1. **强凹曲线**：前 1% 的容量买到绝大部分收益，之后急剧衰减。
2. **策略之间的差距，比容量带来的差距小得多。** 把容量从 0.1% 提到 1%（+13 个点），
   比把随机淘汰换成最好的策略（+10 个点）更有效。**先把容量给够，再谈策略。**
3. **Belady 给出天花板**：现有最好策略离上界还有 3.6 个点。
   没有这个数，你不知道自己是该继续优化还是该收手。

### `[2] 热点 churn —— 跑出来和教科书叙述不一样`

```
  策略             稳态流量   churn流量     掉幅   churn下排名
  随机淘汰           68.4%     66.1%    -2.2%       5
  FIFO             68.3%     67.1%    -1.2%       3
  LRU              70.6%     68.4%    -2.3%       1   ← 最笨的反而第一
  LFU              73.2%     66.9%    -6.3%       4
  W-TinyLFU        72.7%     59.0%   -13.7%       6   ← 稳态最好的成了最差
  自适应W-TinyLFU    72.2%     67.6%    -4.5%       2   ← 救回来了
  Belady上界        76.8%     70.4%
```

**稳态下的排名在 churn 下整个翻过来。** 三层解读：

1. **越聪明的策略，历史先验越重。** LFU 的频次计数、W-TinyLFU 的准入过滤器，
   都是拿"过去"预测"未来"。热点整体换代时这些先验全部失效，而且会**主动把新热点挡在门外**
   —— 准入过滤器本来是挡一次性扫描流量的，此刻它把真正的新热点也一起挡了。
   相比之下 LRU 没有任何先验，所以也没有可失效的东西。
2. **救回来的办法是让策略能自我校正。** 自适应版本用一个最朴素的爬山法，
   掉幅从 -13.7% 收到 -4.5%。它做的事其实是"检测到先验失效，就自动退化成 LRU"。
3. **可迁移的结论：带先验的优化在负载突变时是负资产。**
   生产系统真正需要的不是"某个场景下最强的策略"，而是"没有灾难性失效场景 + 能自我校正"。
   这也是 Caffeine 后来给 W-TinyLFU 加自适应窗口的原因。

> 另一个教训：**拿稳态 benchmark 选策略，上线后会被 churn 教做人。**
> 推荐场景的 churn 尤其剧烈（新内容不断爆火），选型时必须把它压进测试集。

### `[3] 有效延迟 —— 本 demo 最重要的一节`

```
场景A 穿透率高:   穿透到对象存储 = 2.000%, 基线有效延迟 = 201.62 us
  上层调优: HBM +1pt         201.60us     0.0%
  硬件升级: NVMe 提速 10x     201.61us     0.0%
  压穿透: 穿透率减半          101.62us    49.6%
```

**穿透率只有 2%，却贡献了 200us 里的 200us。** 上层调优和硬件升级的收益基本是噪声（0.0%），
唯一有效的动作是压穿透率。

再看场景 B（穿透率压到万分之几）：压穿透的边际收益迅速衰减，上层的命中率分布才开始成为主要矛盾。

> **这就是为什么 TikTok 那条课题写的是"优化多级 Buffer 穿透率"而不是"把某一层做快"。**
> 优化顺序是被这条延迟-穿透率曲线**算出来**的，不是拍脑袋定的。
> 一般规律：当某一层比其他层慢 4~5 个数量级时，**系统的平均延迟由"落到那一层的概率"独占**。

### `[4] 成本`

分层把存储成本降到全 HBM 方案的百分之几，代价是有效延迟涨了几倍。
**分层存储的全部设计工作，就是在这条兑换曲线上找业务能接受的那个点。**

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `ZIPF_A` | 1.15 → 1.01 | 分布趋近均匀，1% 容量的命中率大幅下降 | 缓存的收益完全来自**分布的偏斜**。分布一平，缓存就不值钱了 |
| `ZIPF_A` | 1.15 → 1.5 | 头部更集中，极小缓存就能打到很高命中率 | 越是"爆款驱动"的业务，缓存越划算 |
| `CHURN_EVERY` | 50000 → 5000 | churn 更频繁，LFU 掉得更狠 | LFU 的前提是"热点稳定"。热点变化快到一定程度，LFU 就该换掉 |
| `CACHE_RATIO` | 0.01 → 0.001 | churn 场景下两者都崩 | 缓存太小时，策略之间的差异不重要，容量才是主要矛盾 |
| `N_KEYS` | 调大 | 命中率下降（同样的容量占比，绝对条目数变了） | 提醒：命中率要看**绝对容量**，"容量占比"是个会骗人的指标 |
