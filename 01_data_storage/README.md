# 01 · 数据计算和存储中台

> 表格原文（节选）：用户行为序列数据量呈指数级增长（百亿至千亿级/日）…… 传统存储架构面临读写性能瓶颈
> 与成本压力；传统基于 CPU 的大数据框架（Spark/Hadoop）难以高效处理非结构化数据，GPU/DPU 等异构
> 计算资源利用率不足；数据处理流程与模型训练脱节，ETL 环节耗时长，CPU-GPU 协同效率低下。
>
> 探索方向：流式数据湖（Lakehouse）、文件格式 / 流压缩 / 元数据管理、数据湖+缓存+分布式计算+GPU IO 协同、DCAI。

## 一、先算一笔账：为什么"存储中台"是搜广推的一等公民

一条抖音的训练样本长什么样？大致是：

```
user_id, item_id, 时间戳, 场景, 设备,                      # 标量字段，几十个
user_behavior_seq: [item_1 ... item_2000],               # 长序列，稀疏 ID
item_embedding: float16[128], video_frames_emb: [...],   # 多模态向量
label: {是否点击, 是否完播, 是否点赞, 是否下单}              # 多目标
```

单条样本 KB 量级，一天千亿条 → **每天新增的原始样本是 PB 级**。这个量级下有三件事同时成立：

1. **存不起**：全量热存的成本比训练卡还贵，必须分层 + 压缩。
2. **读不动**：训练时通常只用到全部字段的一小部分（一次实验只关心几十个特征），
   如果按"行"存，磁盘/网络会把 100% 的字节都搬一遍，只为用其中 5%。
3. **喂不饱**：GPU 每秒能吃掉几 GB 样本，而 CPU 侧的解析（protobuf 反序列化、
   特征拼接、padding）常常成为瓶颈 —— 表格里说的 "CPU-GPU 协同效率低下" 就是这件事。

下面的 demo1~demo3 分别对应这三件事；demo4、demo5 再补上推荐场景特有的两个坑：
**不定长序列的 padding 浪费**，和 **CPU/GPU 流水线的重叠**。

## 二、demo1：行存 vs 列存 —— "读不动"的解法

```bash
python3 demo1_row_vs_col.py
```

**要点**

- **列存（columnar）** 把同一个字段的值连续放在一起。训练只读 3/40 个字段时，
  行存必须扫全部字节，列存只扫 3 列 → I/O 量按投影比例线性下降。
- 列存还顺带把**压缩率**打上去了：同一列的数据类型相同、取值域接近（比如都是时间戳、
  都是同一分布的 item_id），熵更低。这就是 Parquet/ORC 的核心，也是表格里
  "文件格式、流数据压缩" 这条的落点。
- 代价：写入需要攒批（column chunk），所以**流式**场景要在"攒多大批"上做权衡 ——
  批小则压缩率低、元数据爆炸；批大则数据新鲜度差。**这正是"流式 Lakehouse"要解决的核心矛盾**，
  也是 Iceberg/Hudi/Paimon 这类系统的主战场。

demo 会打印：全字段扫描 vs 投影扫描的字节量/耗时，以及行存/列存分别的压缩比。

## 三、demo2：多级存储与缓存 —— "存不起"的解法

```bash
python3 demo2_cache_tier.py
```

**要点**

- 推荐系统的访问分布是极度**长尾（Zipf）**的：极少数热门 item 占了绝大多数请求。
  这意味着一个很小的缓存就能吃掉很大比例的流量 —— 缓存的性价比在推荐场景里高得离谱。
- 存储金字塔的延迟差是**数量级**的：

  | 层级 | 典型延迟 | 相对 HBM |
  |---|---|---|
  | GPU HBM | ~0.2 µs | 1× |
  | 本机 DRAM | ~2 µs | 10× |
  | 远程 DRAM (RDMA) | ~10 µs | 50× |
  | 本地 NVMe SSD | ~100 µs | 500× |
  | 对象存储 / HDD | ~10 ms | 50000× |

  所以**命中率提升 1% 带来的收益，远比让某一层快 10% 更大**。这是分层设计的第一性原理。
- demo 里对比 LRU / LFU / 无缓存，并算出**有效平均延迟**。你会看到 LFU 在 Zipf 分布下
  明显赢 LRU（因为热点稳定），但在有"流量突变"时 LRU 反而更稳 —— 对应表格里
  TikTok 那条 "分布式特征索引缓存（Embedding Cache），减少 RDMA 远程访问次数"。

## 四、demo3：DCAI —— 数据质量比模型更值钱

```bash
python3 demo3_data_quality.py
```

**要点**

- 表格里点名了 **DCAI（Data-Centric AI）**："通过数据质量优化与自动化处理链路提升模型性能，
  而非单纯依赖模型改进"。在推荐里这不是理念，是**事故防线**：上游一个特征生产任务挂了，
  某个特征全变成默认值，模型 AUC 会当天掉几个千分点，而模型代码一行没改。
- demo 用 **PSI（Population Stability Index）** 这个工业界最常用的漂移指标：

  ```
  PSI = Σ (实际占比 - 期望占比) × ln(实际占比 / 期望占比)
  PSI < 0.1  稳定 | 0.1~0.25 需关注 | > 0.25 显著漂移，必须报警
  ```

- demo 注入四种真实事故：**特征缺失（变默认值）、口径变更（分布平移）、
  离在线不一致（部分流量取到脏值）、特征不新鲜（叠加噪声）**，然后对比每种事故下
  PSI 的读数 **和** 下游 AUC 的实际掉幅。

- **跑出来的结论和直觉相反，这是这个 demo 最值钱的地方**：PSI 只抓到了前两种事故；
  后两种 AUC 已经掉了 2 个点以上，PSI 却判定"正常"。原因是 PSI 是**单特征边缘分布**指标，
  而"离在线不一致"污染后的特征，边缘分布和训练期几乎完全一致 —— 变的是它与 label 的
  **关联**，不是它的直方图。而这恰恰是推荐系统最高频的一类事故。
  所以工业上必须分层组合：统计类（空值率）抓任务挂掉、分布类（PSI/KS）抓口径变更、
  一致性对拍抓训推不一致、特征-label 关联漂移抓语义错位、影子流量 AUC 兜底。

## 五、demo4：不定长序列 —— padding 浪费与 Jagged

```bash
python3 demo4_jagged_padding.py
```

**要点**

- 推荐样本和 LLM 样本最大的结构差异：**用户行为序列长短差着两三个数量级**。
  一个新用户 3 个行为，一个重度用户 2000 个。而 GPU 只吃规整的稠密张量。
- demo 对比四种布局：全局 padding / 动态 padding（补到批内 max）/ 排序分桶 / Jagged。
- **跑出来的第一个反直觉结论**：动态 padding 几乎白干（1.00x）。
  直觉上"补到批内最大值总该省不少"，但极值统计不答应——一批 512 个样本里只要有
  **一个**接近上限的重度用户，整批就被撑满，而长尾分布下这件事几乎必然发生。
- 真正有效的是**按长度排序分桶**（15x），距离 Jagged 的理论下限只差 2%。
  也就是说：不改任何 kernel、不引入 Jagged Tensor，光靠数据侧的排布就能吃掉
  几乎全部浪费。代价是 batch 内样本不再独立同分布，工业折中是"局部排序"
  （在几千样本的窗口内排序后再切批）。
- 第二个反直觉：**batch 越大，动态 padding 的浪费越严重**。所以"加大 batch 提高
  GPU 利用率"这条常识，在不定长场景下要打折扣。
- demo 最后实测了 padded 稠密算子 vs jagged 分段算子（`np.add.reduceat`）的
  内存与耗时差距——浪费的不只是显存，padding 位置的 0 也要被读进 cache。

**为什么这条课题难**：Jagged 消灭了 padding，却也消灭了静态 shape，于是编译器
更难特化（见 `02/demo5`）。这个张力是推荐 infra 最核心的难题之一。

## 六、demo5：CPU 喂不饱 GPU —— 重叠、木桶与抖动

```bash
python3 demo5_etl_overlap.py
```

**要点**

- 一次 step 里 CPU 侧（解析、拼接、padding）和 GPU 侧（前反向）**本可以重叠**。
  能不能真的重叠起来，直接决定你买的 GPU 有多少时间在干活。
- demo 用一个精确的流水线模型回答三个问题：worker 加到几个够了？
  为什么平均 ETL 更快 GPU 还挨饿？一份优化预算该花在哪？
- **最反直觉的一点**：平均值够快不代表 GPU 不挨饿。抖动一大，即使均值完全没变，
  GPU 利用率就开始掉——因为流水线是同步的，**快的时候省下的时间存不下来**。
  这正是 prefetch 队列的作用：它不让 CPU 更快，它给流水线加缓冲。
- 另外两个容易踩的坑：① worker 数过了拐点收益精确为 0（还白占内存）；
  ② **队列槽位数是 worker 并行度的硬上限**——只调 `num_workers` 不调 `prefetch_factor`，
  是最常见的"调了参数却没效果"的原因。
- 最后一张表把"优化预算花在哪"量化了，结论有三层：优化非瓶颈收益精确为 0；
  同一块气泡上的几种优化**不可叠加**；而优化瓶颈只是把瓶颈推给下一个环节，
  所以每轮优化之后必须**重新测量**。

这一节对应表格里的 "GPU/DPU 等异构计算资源利用率不足" 和 "数据处理流程与模型训练脱节"。
把解压、解析、特征变换从 CPU 挪到 GPU/DPU（GPUDirect Storage、nvCOMP、DALI），
本质上就是在压缩这张表里的 ETL 那一段。

## 七、可以往下挖的研究点（对应表格 C 列）

| 表格里的方向 | 真正的难点 | 可发论文/可落地的切口 |
|---|---|---|
| 流式 Lakehouse | 新鲜度 vs 压缩率/小文件 | 自适应 commit 间隔；行存热区 + 后台异步转列存 |
| GPU IO 协同 | CPU 解析成为瓶颈 | GPUDirect Storage、在 GPU 上做解压/解析（如 nvCOMP）、DPU 卸载 ETL |
| 高效数据格式 | 不定长序列（Jagged） | padding-free 的列式布局 + offset 数组，直接喂给 GPU kernel |
| 元数据管理 | 千亿文件的元数据本身就是大数据 | 分布式元数据 + 分区裁剪下推 |
| DCAI | 数据质量→业务指标 的映射 | 建立 "特征漂移量 → AUC 掉幅" 的预测模型（和 LLM 页的"算子精度→AUC"是同一类问题） |
