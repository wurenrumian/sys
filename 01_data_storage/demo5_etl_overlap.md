# demo5 · CPU 喂不饱 GPU：流水线重叠、木桶与抖动

> 平均 ETL 比 GPU 快，GPU 照样挨饿 —— 因为快的时候省下的时间**存不下来**。

---

## 一、真实场景：这段代码对应线上的什么

一次训练 step 实际上是两件事在跑：

```
CPU 侧（dataloader worker）：
    从对象存储/HDFS 读一批样本
    → protobuf / Parquet 反序列化
    → 特征哈希、查表、类型转换
    → 变长序列 padding、拼 batch
    → pin memory、H2D 拷贝

GPU 侧：
    前向 → 反向 → 优化器更新
```

这两件事**可以重叠**：GPU 在算第 i 批的时候，CPU 可以准备第 i+1 批。
能不能真的重叠起来，直接决定你买的 GPU 有多少时间在干活。

**推荐场景的特殊难点**：样本大（KB 级）、字段多（几百个）、要做哈希和 padding，
所以 ETL/GPU 的耗时比值天然比 CV/NLP 高得多。别的领域不用操心的事，在推荐里是头号瓶颈。

对应表格里："数据处理流程与模型训练脱节，ETL 环节耗时长，CPU-GPU 协同效率低下" /
"GPU、DPU 等异构计算资源利用率不足"。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造每个 step 的耗时

```python
etl ~ lognormal(均值=ETL_MS, 变异系数=ETL_CV)    # CPU 侧：长尾
gpu = GPU_MS * (1 + 2% 噪声)                     # GPU 侧：近似恒定
```

**为什么 CPU 侧是长尾**：大多数批很快，偶尔撞上一个超长序列的批、一次 page cache miss、
一次 GC、一次网络抖动，就会慢几倍。**这个长尾是本 demo 的主角。**

对数正态的参数是反解出来的，保证**均值恰好等于 `ETL_MS`** ——
这样后面改变异系数时，"均值不变、只有抖动变"这个对照才成立。

### 第 2 步：流水线模型（核心）

`simulate()` 只有十几行，但把流水线的约束写全了：

```python
第 i 批的生产开始时刻 = max(
    worker_free[w],              # (a) 有空闲的 worker
    cons_done[i - queue]         # (b) 队列有空槽：第 i-queue 批已被 GPU 消费掉
)
第 i 批的 GPU 开始时刻 = max(
    gpu_free,                    # GPU 上一批算完
    prod_done[i]                 # 这一批已经准备好
)
```

- `queue=1` → 只有一个槽位 → "生产一批 → GPU 算完 → 再生产下一批"，**完全串行**；
- `queue=2` → 经典**双缓冲**；
- `queue=k` → 生产者最多领先消费者 k 批。

这个模型对应 PyTorch DataLoader 的 `num_workers`（= workers）和
`prefetch_factor × num_workers`（= 队列槽位数）。

### 第 3 步：四组实验

1. **重叠与否**：串行 / 双缓冲 / 多 worker+队列
2. **worker 扫描**：把 ETL 调重到 GPU 的 2.6 倍，看拐点在哪
3. **抖动扫描**：均值固定，只改变异系数，配两种队列深度对照
4. **队列扫描**：worker 固定，只改队列槽位
5. **优化预算归因**：五种方案各自的端到端收益

## 三、涉及的机制

### 木桶效应（Amdahl 的流水线版本）

完美流水线的 step 时间 = `max(生产速率的倒数, 消费速率的倒数)`：

```
step ≈ max( ETL / workers ,  GPU )
```

所以 worker 加到 `ceil(ETL/GPU)` 之后，瓶颈换成 GPU，**再加收益精确为 0**。

### 队列的真正作用：吸收抖动，不是提速

这是本 demo 最重要的概念。流水线是**同步**的：

- CPU 某一批慢了 → GPU 干等（气泡）
- CPU 某一批快了 → 它**没法把省下的时间存起来**给未来用

所以即使 `E[ETL] < E[GPU]`，只要有方差，就会持续产生气泡。
**队列的作用是给"快"提供一个存放的地方**：快的时候多攒几批放队列里，慢的时候从队列里取。
它把"瞬时的慢"摊平成"平均的快"。

数学上这就是一个有限缓冲的 G/G/1 队列，缓冲深度 ↑ → 阻塞概率 ↓，收益随深度**指数衰减**。

### 队列深度是并行度的硬上限

在途批次数不可能超过槽位数。所以：

```
有效并行度 ≤ min(workers, queue_slots)
```

**只调 `num_workers` 不调 `prefetch_factor`，是最常见的"调了参数却没效果"的原因。**

## 四、方案对比

| 手段 | 治什么 | 成本 | 收益上限 | 副作用 |
|---|---|---|---|---|
| **加 prefetch 队列深度** | 抖动造成的气泡 | 内存（每槽位一整批样本，推荐场景可能几百 MB） | 消掉全部抖动气泡 | **数据新鲜度下降**（在线学习要命）；内存占用线性增长 |
| **加 worker 数** | 平均产能不足 | CPU 核 + 每 worker 一份内存 | 到 `ETL/GPU` 拐点为止 | 过了拐点纯浪费；worker 间抢内存带宽 |
| **降低 ETL 时间** | 平均产能不足（治本） | 工程量大 | 直到 GPU 成为瓶颈 | 要改数据格式/上 GPU 解码，跨团队 |
| **降低 ETL 抖动** | 抖动（治本） | 要先定位抖动来源 | 同上 | 抖动来源往往在别人家（存储、网络、GC） |
| **换更快的 GPU** | GPU 侧瓶颈 | 💰💰💰 | 取决于 GPU 当前占比 | **可能把瓶颈推回 CPU 侧**，收益远小于 2x |

**降低 ETL 时间的具体手段**（对应表格里的异构计算）：

- **GPUDirect Storage**：数据从 NVMe 直达显存，绕过 CPU 和系统内存
- **nvCOMP**：在 GPU 上做解压
- **DALI**：在 GPU 上做预处理
- **DPU 卸载**：把解析/过滤下推到网卡

## 五、怎么读输出

### `[1] 重叠与否`

```
  串行(1 槽位, 不重叠)     188.2ms   理想100.1ms   气泡88.1ms   利用率53.2%
  双缓冲(2 槽位)          115.3ms                 气泡15.2ms   利用率86.8%
  4 worker + 2 槽位       113.3ms                 气泡13.2ms   利用率88.4%
```

串行时 step = ETL + GPU；重叠后逼近 max(ETL, GPU)。
**注意：没有任何一行代码变快，快的只是安排。** 这是流水线的全部价值。

### `[2] worker 扫描`（ETL 调重到 GPU 的 2.6 倍）

```
  1    264.4ms   利用率 37.8%
  2    132.5ms   利用率 75.5%   (+99.6%)
  3    104.0ms   利用率 96.3%   (+27.4%)
  4    102.8ms   利用率 97.3%   (+1.1%)
  6~16 102.8ms   利用率 97.4%   (+0.0%)   ← 拐点之后收益归零
```

拐点在 3（= ceil(2.6)）。之后每个多余的 worker 都在占内存、占核、抢带宽，**收益是 0**。

### `[3] 抖动扫描 —— 本 demo 最反直觉的一节`

均值**始终 90ms**，永远快于 GPU 的 100ms：

```
  变异系数   ETL p99   队列槽位   GPU利用率   实际step
  0.0         90ms        2       100.0%    100.1ms
  0.6        279ms        2        88.0%    113.7ms   ← 均值没变，利用率掉了
  0.6        279ms        8       100.0%    100.1ms   ← 加深队列就回来了
  1.5        617ms        2        76.6%    130.6ms
  1.5        617ms        8        97.1%    103.0ms
```

**同一行的两个槽位深度对照，是整节的重点**：没多花一分钱 CPU，只是把槽位从 2 加到 8，
利用率就回来了。这说明气泡的成因是**抖动**而不是产能，对症的药是**缓冲**而不是加人。

### `[4] 队列扫描`

收益很快饱和（抖动被吸收完就没用了），代价是内存和数据新鲜度。

### `[5] 优化预算归因`

```
  基线                        113.3ms      —       88.4%
  把 ETL 做快 2x              101.0ms    1.12x     99.0%
  worker 数翻倍               113.3ms    1.00x     88.4%   ← 一分不赚
  队列槽位翻倍                100.3ms    1.13x     99.8%   ← 改配置就行
  消除 ETL 抖动               100.1ms    1.13x    100.0%
  GPU 换成快 2x 的卡            79.1ms    1.43x     63.2%   ← 不是 2x，而且瓶颈翻转了
```

三层结论：

1. **优化非瓶颈的收益精确等于 0**（worker 翻倍 = 1.00x）
2. **收益有天花板**：CPU 侧三个方案都在抢同一块 13ms 的气泡，最多 1.13x，**不可叠加** ——
   做了最便宜的那个（改配置），另外两个就没价值了
3. **优化瓶颈只是把瓶颈推给下一环**：换快 2x 的卡只快 1.43x，且 GPU 利用率掉到 63%（瓶颈翻到 CPU）

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `ETL_CV` | 0.6 → 0 | 队列深度 2 就够，`[4]` 那张表变平 | 队列的价值**完全**来自抖动。没抖动就不需要缓冲 |
| `ETL_MS` | 90 → 300 | 瓶颈翻到 CPU，`[5]` 里"ETL 快 2x"变成收益最大的方案 | 同一张归因表，换个工作点答案完全不同 —— 所以**每轮优化后必须重测** |
| `WORKERS` | 4 → 1 | `[1]` 的第三行退化 | 单 worker 时抖动无法被并行摊平 |
| `QUEUE` | 2 → 1 | 全部退化为串行 | 一个槽位 = 没有流水线 |
| `GPU_MS` | 100 → 20 | GPU 变快，瓶颈立刻翻到 CPU | 验证"换卡不一定有用" |

## 七、这个 demo 的边界

模型没有建的东西（用它做数量级判断，别用它预测毫秒数）：

- worker 之间抢内存带宽、抢 CPU cache（真实中 worker 多了单个会变慢）
- H2D 拷贝和 PCIe 争用（真实中 pin memory 和 DMA 也要排队）
- GPU 侧的显存压力（队列越深，pin 住的内存越多，可能挤掉显存）
- 数据新鲜度的**业务代价**（在线学习里队列深度是有上限的）
