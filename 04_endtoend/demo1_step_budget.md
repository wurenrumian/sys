# demo1 · Roofline + 一次训练 step 的时间预算

> 推荐训练 MFU 只有百分之几不是 bug，是模型形态决定的。
> 而纯数据并行下，计算/通信的平衡点**只由单卡 batch 决定，和模型多大无关**。

---

## 一、真实场景：这个 demo 想解决什么问题

前面 14 个 demo 每个都在回答"某一段能快多少"。但一个 5% 占比的环节，
**就算你把它做到无穷快，端到端也只有 1.05x**。

所以在动手之前必须先回答两个问题：

1. **瓶颈在哪？**（我该先学/先做哪一段）
2. **瓶颈会随什么迁移？**（换个卡数、换个 batch、换个模型形态，答案就变了）

这个 demo 用**纸面模型**回答它们 —— 所有数字都由硬件常数和模型规模**算出来**，
不是拍脑袋写死的。改参数重跑，就能看到瓶颈怎么迁移。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：Roofline —— 判断每个算子在等什么

```python
脊点 (ridge point) = 峰值算力 / 峰值带宽 = 989 TFLOPS / 3350 GB/s ≈ 295 FLOP/Byte
```

对六个典型算子算出算术强度（FLOP / 访存字节），和脊点比较：
低于脊点 → memory-bound（在等内存），高于 → compute-bound（在等算力）。

### 第 2 步：把一次 step 拆成三段，每段都算出来

```python
# ---- 数据段（01 存储）----
read_s = batch × 样本大小 / 存储带宽
etl_s  = batch / 1000 × 每千条 ETL 耗时
t_data = max(read_s, etl_s)                 # 读和算本身可以重叠

# ---- 计算段（02 编译）----
dense_flop = 6 × 稠密参数量 × batch          # 前向+反向的标准估算
t_dense    = dense_flop / (峰值算力 × 0.45)  # 大 GEMM 实测约 45% 峰值
emb_bytes  = batch × 序列长 × 维度 × 4 × 3
t_emb      = emb_bytes / HBM带宽             # embedding 是纯访存，用带宽算不用算力算

# ---- 通信段（03 网络）----
t_ar  = 2(n-1)/n × 稠密参数×4 / 网络带宽      # 梯度 AllReduce（Ring）
t_a2a = batch×序列长×维度×4 × (n-1)/n × 2 / 网络带宽   # Embedding AllToAll
```

### 第 3 步：三种重叠程度

```python
none      : step = t_data + t_compute + t_comm
realistic : hidden = min(0.5 × t_comm, t_compute)      # 通信最多藏起计算那么长的一段
            step   = max(t_data, t_compute + t_comm - hidden)
perfect   : step = max(t_data, t_compute, t_comm)      # 理论下界
```

`realistic` 里那个 `min(..., t_compute)` 是关键：**藏起来的部分不可能超过计算本身的时长**。

### 第 4~6 步：三组敏感度分析

- **把某一段做快 2x**，端到端能快多少
- **卡数扫描**（weak scaling）：瓶颈怎么迁移
- **模型形态扫描**：验证一个纸面推导

## 三、涉及的概念

### Roofline 模型

```
可达性能 = min(峰值算力,  算术强度 × 峰值带宽)
                            └── 斜坡段：带宽说了算
脊点 = 峰值算力 / 峰值带宽
```

**在写任何优化之前就该做的判断**：这个算子在斜坡上还是在平台上？
在斜坡上，优化算力毫无意义。

### MFU（Model FLOPs Utilization）

```
MFU = 实际有效 FLOPs / 峰值 FLOPs
```

LLM 训练能到 40~50%，推荐训练普遍只有百分之几。**这不是工程没做好**，
是因为推荐是**搬运型负载** —— 用算力利用率去衡量一个搬运任务，本身就是错的指标。

### 一个漂亮的约分

```
计算量 ∝ 参数量 P × batch B
梯度通信量 ∝ 参数量 P

计算/通信 ∝ (P × B) / P = B        ← 参数量【约掉了】
```

> **纯数据并行下，计算/通信的平衡点只由单卡 batch 决定，和模型多大根本没关系。**

这条推导很反直觉，demo 里的 `[5]` 就是用来验证它的。

## 四、方案对比

### 六个算子的 Roofline 位置

| 算子 | 算术强度 | 可达峰值 | 类型 |
|---|---|---|---|
| **Embedding lookup** | **0** | 0% | memory-bound（纯搬运，一次乘法都没有） |
| 逐元素（门控/加权/激活） | 0.1 | 0% | memory-bound |
| LayerNorm | 1.0 | 0.3% | memory-bound |
| 小 GEMM（batch=8，在线推理） | 7.9 | 2.7% | memory-bound（权重搬进来只用一次） |
| GEMM 1024³ | 341 | 100% | **compute-bound** |
| GEMM 8192³ | 2731 | 100% | **compute-bound** |

**只有大 GEMM 是 compute-bound，而它在推荐模型里的占比远小于 LLM。**

### 三种优化投入的收益（默认场景）

| 优化 | 端到端收益 | 谁的活 |
|---|---|---|
| 存储/ETL 快 2x | **1.00x** | 01 存储 |
| 算子快 2x（融合/编译） | **1.00x** | 02 编译 |
| 网络快 2x | **2.00x** | 03 网络 |

**收益完全由当前占比决定，和这件事本身有多难、多前沿毫无关系。**

## 五、怎么读输出

### `[2] 一次 step 的时间账单`

```
环节                          耗时     占比                          对应目录
数据: 读样本 + ETL           8.2ms    7.2%  ██··········  01_data_storage
计算: 稠密 GEMM              4.1ms    3.6%  █···········  02_compile
计算: Embedding 访存         0.1ms    0.1%  ············  02_compile
通信: 梯度 AllReduce        95.8ms   84.4%  ████████████  03_network
通信: Embedding AllToAll     5.4ms    4.7%  █···········  03_network
```

默认场景（512 卡、稠密 300M、单卡 batch 1024）下**通信占 89%**。

```
重叠程度                 step 耗时     MFU     全局吞吐(样本/s)
完全不重叠                113.6ms     1.6%       4,616,659
数据全叠+通信尽量叠       101.2ms     1.8%       5,182,211
完美重叠(理论下界)        101.2ms     1.8%       5,182,211
```

**注意后两行一模一样** —— 这不是 bug。通信 101ms 远大于计算 4.2ms，
而"通信藏在计算背后"最多只能藏起计算那么长的一段。
**通信一旦成为绝对大头，重叠就基本没有空间了**，唯一的出路是**减少通信量本身**
（梯度压缩/量化、分层 AllReduce、更大的 batch 摊薄同步频率）。

### `[4] 卡数扫描`

```
   卡数     数据     计算     通信      step   并行效率   当前瓶颈
      1   8.2ms   4.2ms   0.0ms     8.2ms    100.0%     数据
      8   8.2ms   4.2ms  88.7ms    88.7ms      9.2%     通信
    512   8.2ms   4.2ms 101.2ms   101.2ms      8.1%     通信
   4096   8.2ms   4.2ms 101.3ms   101.3ms      8.1%     通信
```

单卡计算量**一点没变**，通信量却在涨（Ring 的 `2(n-1)/n` 很快趋于 2），于是通信占比单调上升。
**这就是"千卡之后效率变低"的算术来源**（展开细节见 `03/demo2`）。

> **实践含义：小规模时该优化计算，大规模时该优化通信。**
> 同一个团队在不同阶段，正确答案是不一样的。

### `[5] 模型形态`（验证那个约分）

```
场景                            单卡batch    数据    计算    通信   瓶颈
推荐: 300M 稠密 / batch 1k          1,024    7.2%    3.7%   89.1%   通信
中等: 1B 稠密 / batch 8k            8,192   12.2%   20.6%   67.2%   通信
类 LLM: 7B / batch 32k token       32,768    4.5%   53.7%   41.8%   计算
大 LLM: 70B / batch 256k token    262,144    0.8%   90.5%    8.7%   计算
```

**推导被验证了**：瓶颈从通信翻到计算，唯一的驱动因素是 **batch 变大**。
参数量从 300M 到 70B 涨了 200 多倍，却没有改变这个平衡。

这解释了为什么 LLM 那套 infra 经验搬到推荐上会水土不服。
不是"我们模型小所以不用操心通信" —— 恰恰相反，
**模型小反而更该操心，因为决定权在 batch 手里，而推荐的 batch 天生小。**

而推荐还不能靠无脑加大 batch 来救：推荐是**在线学习**的，
batch 越大对最新行为的响应越慢，直接损失线上效果。LLM 没有这个约束。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `BATCH_PER_GPU` | 1024 → 16384 | 瓶颈从通信翻到计算 | 验证那个约分：**batch 才是那个旋钮** |
| `N_GPU` | 512 → 1 | 通信归零，瓶颈变成数据 | 单机调优的经验完全不适用于集群 |
| `NET_GBS` | 25 → 200 | 通信占比大幅下降，`[3]` 的排序整个变化 | **敏感度表只在当前工作点有效**，换硬件就要重算 |
| `DENSE_PARAMS_M` | 300 → 30000 | 计算和通信**同比例**放大，占比几乎不变 | 再次验证参数量约掉了 |
| `STORAGE_GBS` | 2 → 0.2 | 数据段变成瓶颈 | 存储慢到一定程度，前面所有优化都白搭 |
| `GPU_TFLOPS` | 989 → 100 | 脊点降到 30 F/B，更多算子变成 compute-bound | 脊点是硬件属性，不是算子属性 |

**建议先做第一个**（batch 调到 16384）。看着瓶颈从"网络"翻到"计算"，
你就理解了为什么 LLM 团队和推荐团队关心的东西完全不一样。

## 七、这个模型的边界（很重要）

这是一个**一阶模型**，用来建立数量级直觉和**排序**，**不是用来预测具体毫秒数的**。它没有建模：

- 流水线并行 / 张量并行 / ZeRO 的通信模式（只做了纯数据并行）
- 慢节点（straggler）、网络抖动、故障重传
- 稀疏参数服务器的实际访问模式（这里用一个 AllToAll 近似）
- kernel 启动开销、显存不足导致的重计算
- 混合精度下梯度是 2 字节而不是 4 字节

> **真实系统的瓶颈定位必须靠 profile，不能靠这个模型。**
> 它的作用是让你在打开 profiler 之前，就知道该去看哪一段、以及看到的数字是否离谱。

## 八、这个项目的一句话总结

三个方向不是三块并列的知识，而是**一次 step 里的三段时间**：

```
01 存储  =  把数据搬到 GPU 门口
02 编译  =  让 GPU 门内的那段代码跑得像样
03 网络  =  让几百上千张卡的结果对齐
```

共同的母题只有一个：

> **在异构硬件上，把"搬运"的成本压到接近"计算"。**

搜广推让这个母题格外尖锐，因为它同时要 (a) 万亿级流量 (b) 毫秒级 P99 (c) 稀疏不定长数据
—— 去掉任何一条，通用方案就够用了。

**学习建议**：别按目录顺序学，按这张账单的占比学。
先跑这个 demo，看看你关心的场景里瓶颈在哪一段，再回去读对应目录。
