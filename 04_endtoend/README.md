# 04 · 端到端：一次训练 step 的时间预算

这个目录不对应表格里的任何一个团队。它是前面三个目录的**收束**：
把存储、编译、网络三段放进同一张账单里，回答两个问题——

1. **瓶颈在哪？** 也就是"我该先学/先做哪一段"。
2. **瓶颈会随什么迁移？** 换个卡数、换个 batch、换个模型形态，答案就变了。

```bash
python3 04_endtoend/demo1_step_budget.py
```

---

## 一、为什么必须有这一节

前面每个 demo 都在回答"某一段能快多少"。但一个 5% 占比的环节，
**就算你把它做到无穷快，端到端也只有 1.05x**。

这不是打击人，而是选择研究方向时最该先算的一笔账。真实世界里这条规律天天被违背，
因为团队总是倾向于优化自己熟悉的那一段——那正是他们能拿出漂亮 benchmark 的地方。

所以这个 demo 的第一价值不是任何一个具体数字，而是**建立"先算账再动手"的习惯**。

## 二、demo 里的五张表

### [1] Roofline：这台机器上，什么算子值得优化

脊点 = 峰值算力 / 峰值带宽 ≈ **300 FLOP/Byte**（H100 量级）。算术强度低于它的算子，
无论如何都吃不满算力——它在等内存。

| 算子 | 算术强度 | 结论 |
|---|---|---|
| Embedding lookup | **0** | 纯搬运，一次乘法都没有 |
| 逐元素（门控/加权/激活） | ~0.1 | memory-bound |
| LayerNorm | ~1 | memory-bound |
| 小 batch GEMM（在线推理） | ~8 | memory-bound（权重搬进来只用一次） |
| 大 GEMM (8192³) | ~2700 | **唯一真正吃算力的** |

**这解释了一个反复被问到的问题**：为什么推荐模型的 MFU 普遍只有百分之几，
而 LLM 能到 40~50%？不是工程没做好，**是模型形态决定的**——
一个以搬运为主的负载，本来就不该用算力利用率去衡量。

推论：推荐场景砸钱买更强的算力卡，收益远小于 LLM 场景；
真正该投的是**带宽**（HBM、网络、存储），也就是这个项目的三个方向。

### [2] 一次 step 的时间账单

把 step 拆成数据 / 计算 / 通信三段，每段都由硬件常数算出来，不是拍脑袋写的。
默认场景（512 卡、稠密 300M、单卡 batch 1024）下通信占了 ~89%。

这里还有一个容易被忽略的点：**重叠不是万能的**。"通信藏在计算背后"最多只能藏起
计算那么长的一段。当通信是绝对大头时，重叠基本没有空间，
唯一的出路是**减少通信量本身**（梯度压缩/量化、分层 AllReduce、更大的 batch 摊薄同步频率）。

### [3] 敏感度：把某一段做快 2x，端到端能快多少

收益完全由**当前占比**决定，和这件事本身有多难、多前沿毫无关系。

### [4] 卡数扫描：瓶颈会迁移

单卡计算量一点没变，通信量却随卡数上涨，于是通信占比单调上升。
这就是"千卡之后效率变低"的算术来源（展开细节见 `03/demo2`）。

**实践含义：小规模时该优化计算，大规模时该优化通信。同一个团队在不同阶段，
正确答案是不一样的。**

### [5] 模型形态：一个漂亮的约分

纸面推导：计算量 ∝ 参数量 × batch，梯度通信量 ∝ 参数量。两者一比，**参数量约掉了**。

> 纯数据并行下，计算/通信的平衡点**只由单卡 batch 决定，和模型多大无关**。

demo 里的表验证了这个推导：参数量从 300M 到 70B 涨了 200 多倍，
瓶颈的翻转却完全由 batch 驱动。

这解释了为什么 LLM 那套 infra 经验搬到推荐上会水土不服。不是"我们模型小所以不用操心通信"
——恰恰相反，**决定权在 batch 手里，而推荐的 batch 天生小**。
而推荐还不能靠无脑加大 batch 来救：推荐是在线学习的，batch 越大对最新行为的响应越慢，
直接损失线上效果。LLM 没有这个约束。

## 三、这个模型的边界（重要）

这是一个**一阶模型**，用来建立数量级直觉和排序，不是用来预测具体毫秒数的。它没有建模：

- 流水线并行 / 张量并行 / ZeRO 的通信模式（只做了纯数据并行）
- 慢节点（straggler）、网络抖动、故障重传
- 稀疏参数服务器的实际访问模式（这里用一个 AllToAll 近似）
- kernel 启动开销、显存不足导致的重计算
- 混合精度下梯度是 2 字节而不是 4 字节

**真实系统的瓶颈定位必须靠 profile，不能靠这个模型。** 它的作用是让你在打开 profiler
之前，就知道该去看哪一段、以及看到的数字是否离谱。

## 四、可以往下挖的点

| 方向 | 切口 |
|---|---|
| 让这个模型更准 | 用真实 profile 数据反标定各段系数，做成一个可预测的性能模型 |
| 自动瓶颈归因 | 从 timeline trace 自动切分三段并给出"优化谁收益最大"的排序 |
| 联合优化 | 批大小 / 并行策略 / 梯度精度是耦合的，应当联合搜索而不是分别调 |
| 成本视角 | 把时间换算成钱（卡时 + 存储 + 带宽），按"每元样本吞吐"排序优化项 |
