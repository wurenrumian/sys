## 怎么用

每个子目录都有自己的 `README.md`（讲解）和若干 `demoN_*.py`（演示）。演示全部：

- 只依赖 **Python 3.9 + numpy**（torch 是可选的，没有会自动降级）
- 单文件、秒级出结果、打印一张对比表
- 不是玩具复现，而是把**工业级问题的量级关系**用小规模数值还原出来（比如 P999 尾延迟怎么被大流冲垮）

## 反直觉结论速查

这些都是**实验跑出来推翻了我预期**的结果，比那些"符合预期"的部分更值得看：

| 在哪 | 直觉 | 实测 |
|---|---|---|
| `01/demo3` | PSI 能抓住数据事故 | PSI 漏掉了两类事故，AUC 掉了 2 个点它还报"正常"——因为它只看边缘分布，抓不到"分布没变但语义错位" |
| `02/demo1` | 手工优化 numpy 会更快 | 两种"看起来更优"的写法（零分配 `out=`、布尔掩码）分别慢 2.5x 和 7.7x |
| `02/demo2` | 手写分块能实现算子融合 | 比不融合还慢——"块要小到进 cache"和"块要大到摊薄解释器开销"直接冲突，Python 层根本表达不了融合 |
| `02/demo3` | 分页分配器消灭碎片 | 它只是把**外部**碎片换成了**内部**碎片；4MB 页在 80% 水位照样 OOM，页减到 256KB 才扛住 |
| `03/demo1` | 优先级队列能救尾延迟 | 低利用率下改善 **0%**——包不可抢占，优先级只能决定"下一个发谁"。真正有效的是分片 |
| `03/demo1` | 利用率高 = 尾延迟差 | 周期性流量下推到 93% 利用率，P999 纹丝不动。决定尾延迟的是**突发性**，不是平均利用率 |
| `03/demo3` | DCTCP 的阈值 K 是吞吐/延迟的取舍 | 该模型里 K 调小几乎免费（利用率始终 >98%）；K 的真实约束来自突发吸收和反馈时延，而这恰是流体模型抓不到的 |

每个结论在对应 demo 的输出里都有数据支撑和原因分析。

## 建议的阅读顺序

如果你的目标是准备这个联合实验室的方向（或面试），建议按 **网络 → 存储 → 编译** 的顺序，
因为这正是一次训练 step 的数据流向：网络把参数/梯度搬过来 → 存储把样本喂进来 → 编译决定这些
Python/算子代码跑得多快。

三个方向共同的底层母题只有一个：

> **在异构硬件（CPU/GPU/DPU/网卡）上，把"数据搬运"的成本压到接近"数据计算"的成本。**

搜广推场景让这个母题变得格外尖锐，因为它同时要 (a) 万亿级流量 (b) 毫秒级 P99 (c) 稀疏
不定长数据 —— 这三条任意去掉一条，通用的 LLM Infra 方案就够用了；三条同时成立，就必须重做。
