## 一、怎么用（推荐：网站）

```bash
cd ~/self/sys
python3 site/serve.py --open        # 打开 http://127.0.0.1:8777
```

这个站点做了三件命令行做不到的事：

1. **调参重跑**——每个 demo 的关键常数都做成了表单里的滑块（样本量、Zipf 指数、
   扇出度、DCTCP 阈值 K、卡数…）。改完点「运行」就在浏览器里**真的 fork 一个
   python 子进程**去跑，输出流式回传。参数只作为环境变量传进去，**不改一行代码**。
2. **逐条验证**——每个 demo 都登记了一组「验证点」，把结论拆成可以自动比对的断言
   （比如"优先级队列相比 FIFO 的改善 < 5%"）。跑完自动标出通过 / 不符 / 未匹配，
   还能导出一份 Markdown 验证报告。
3. **讲解和源码在一起**——README 的讲解、demo 源码、真实输出在同一页。

> **为什么强调"能调参"**：这些 demo 的价值在结论，不在某个具体数字。
> 一个结论如果只在默认参数下成立，那它多半是巧合。跑出"不符"是好事——
> 那说明这个结论有边界条件，而边界条件才是真正值得记住的东西。

其他用法：

```bash
python3 01_data_storage/demo1_row_vs_col.py          # 单个跑
N_ROWS=1000000 python3 01_data_storage/demo1_row_vs_col.py   # 命令行调参，同一套机制
bash run_all.sh                                       # 全部跑一遍
bash run_all.sh 03                                    # 只跑 03 目录
python3 site/export.py                                # 导出离线单文件 HTML 快照
```

## 二、反直觉结论速查

这些都是**实验跑出来推翻了预期**的结果，比那些"符合预期"的部分更值得看：

| 在哪 | 直觉 | 实测 |
|---|---|---|
| `01/demo3` | PSI 能抓住数据事故 | PSI 漏掉两类事故，AUC 掉了 2 个点它还报"正常"——它只看边缘分布，抓不到"分布没变但语义错位" |
| `01/demo4` | 动态 padding 比全局 padding 省很多 | 几乎白干（1.00x）。一批 512 个样本里只要有一个超长的，整批就被撑满——极值统计 |
| `01/demo5` | 平均 ETL 比 GPU 快就不会拖后腿 | 照样挨饿。快的时候省下的时间**存不下来**，除非有队列；抖动才是成本 |
| `01/demo5` | 加大 num_workers 总没坏处 | 过了拐点收益精确为 0；而且队列槽位数才是并行度的硬上限 |
| `02/demo1` | 手工优化 numpy 会更快 | 两种"看起来更优"的写法分别慢 2.5x 和 7.7x |
| `02/demo2` | 手写分块能实现算子融合 | 比不融合还慢——"块要小到进 cache"和"块要大到摊薄解释器开销"直接冲突 |
| `02/demo3` | 分页分配器消灭碎片 | 它只是把**外部**碎片换成了**内部**碎片；真正的价值是把不可控问题变成可调参数 |
| `02/demo5` | 缓存命中率 97% 已经很好 | P99 是 401ms。编译开销不会消失，只是全部集中到了尾延迟里 |
| `02/demo5` | 按流量分布切等频桶更聪明 | 更差 4 倍。padding 浪费是**相对量**，桶必须等比排布 |
| `03/demo1` | 优先级队列能救尾延迟 | 低利用率下改善 **0%**——包不可抢占。真正有效的是分片 |
| `03/demo1` | 利用率高 = 尾延迟差 | 周期性流量推到 93% 利用率，P999 纹丝不动。决定尾延迟的是**突发性** |
| `03/demo3` | DCTCP 的阈值 K 是吞吐/延迟的取舍 | 该模型里 K 调小几乎免费；K 的真实约束来自突发吸收和反馈时延，恰是流体模型抓不到的 |
| `03/demo4` | 缓冲区加大就能解决 incast | P50 好了，P99 仍是 200ms——把"每次都炸"变成"偶尔炸"，而 SLA 按偶尔那次签 |
| `03/demo4` | 单机偶尔慢一下没关系 | 单分片 p99=1%，扇出 100 就有 63% 的请求踩雷（tail at scale） |
| `04/demo1` | 推荐训练 MFU 低是工程没做好 | 是模型形态决定的：embedding lookup 的算术强度是 **0** |
| `04/demo1` | 模型越大通信压力越大 | 参数量在计算/通信之比里**约掉了**；决定权在单卡 batch 手里 |

每个结论在对应 demo 的输出里都有数据支撑和原因分析，在网站上还有对应的验证点。

## 三、建议的阅读顺序

**先跑 `04_endtoend/demo1_step_budget.py`**，它会算出一次训练 step 的时间账单。
然后按账单里占比最大的那一段，去读对应目录——因为**优化非瓶颈环节的收益精确等于 0**，
学习也一样。

如果是为了系统地准备这个方向，`99_learning/README.md` 里有一条四周路线、
每个方向的高频追问与参考答案、以及一份不求全但有用的资料清单。

三个方向共同的底层母题只有一个：

> **在异构硬件（CPU/GPU/DPU/网卡）上，把"数据搬运"的成本压到接近"数据计算"的成本。**

搜广推场景让这个母题变得格外尖锐，因为它同时要 (a) 万亿级流量 (b) 毫秒级 P99
(c) 稀疏不定长数据 —— 这三条任意去掉一条，通用的 LLM Infra 方案就够用了；
三条同时成立，就必须重做。

## 四、目录结构

```
sys/
├── 00_overview/README.md          知识地图 / 量级速查 / 术语表 / 5 条通用规律
├── 01_data_storage/               行列存、缓存分层、DCAI、Jagged、流水线重叠
├── 02_compile/                    解释器开销、算子融合、显存碎片、动态批、动态 shape
├── 03_network/                    队头阻塞、AllReduce、拥塞控制、incast 与尾延迟
├── 04_endtoend/                   Roofline + 一次 step 的时间预算
├── 99_learning/README.md          学习路径、面试问答、资料清单
├── common/params.py               统一的参数入口（环境变量 → demo 常量）
├── site/                          本地站点：serve.py / catalog.json / static / export.py
└── run_all.sh
```

`common/params.py` 是所有"可调旋钮"的统一入口。每个 demo 开头会打印本次生效的参数，
被改过的用 `*` 标出——看一份跑飞了的输出时，第一个要问的永远是"这是用什么参数跑的"。
