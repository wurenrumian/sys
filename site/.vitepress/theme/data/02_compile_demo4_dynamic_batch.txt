====================================================================================
动态批处理演示: 52,873 个请求 / 60 秒, 均值 800 QPS
流量形态: 正弦波动(±40%) + 第 30~34 秒 3 倍尖峰
GPU 成本模型: 单批耗时 = 2.0ms 固定开销 + 0.012ms x batch_size
====================================================================================

策略                      P50      P99      P999        最大      平均批     GPU利用率
------------------------------------------------------------------------------------
固定批 bs=16              9.2ms    34.2ms     44.5ms     61.8ms     16.0     12.1%
固定批 bs=64             33.5ms   123.8ms    148.7ms    182.5ms     63.9      3.8%
固定批 bs=256           130.0ms   469.8ms    536.6ms    564.0ms    255.4      1.7%
固定超时 5ms               5.1ms     7.1ms      7.2ms      7.3ms      5.5     33.0%
固定超时 20ms             12.9ms    22.3ms     22.5ms     22.7ms     18.8     10.5%
自适应                    2.9ms     4.0ms      4.1ms      4.2ms      2.1     83.3%

------------------------------------------------------------------------------------
[固定批的问题] 它把'什么时候发车'完全交给了流量:
  bs=16 : 批小 -> 发车频繁 -> 固定开销占比高 -> GPU 利用率 12.1%
  bs=256: 批大 -> 低谷期要等很久才凑满 -> P999 高达 536.6ms
  固定批的致命问题: 流量低谷时请求会被**饿死在队列里**等后来者凑批,
  而这恰恰是 GPU 最闲、本该最快响应的时候. 完全是反的.

[固定超时的改进] 给等待加了一个硬上界, 延迟可控了:
  5ms 超时 : P999 7.2ms, 平均批 5.5, GPU 利用率 33.0%
  20ms 超时: P999 22.5ms, 平均批 18.8, GPU 利用率 10.5%
  但超时值本身是个**静态**参数: 调小则高峰期批太小、吞吐不够;
  调大则低谷期白白多等. 一个值没法同时服务两种流量状态.

[自适应] 让等待时间随队列积压走:
  P50 2.9ms / P99 4.0ms / P999 4.1ms, 平均批 2.1, GPU 利用率 83.3%
  规则很简单: 积压少 -> 几乎不等就发车(反正 GPU 闲着, 何必让人干等);
             积压多 -> 愿意多等一点凑大批(此时凑批几乎不花时间, 白赚吞吐).
  它在低谷期像'小超时', 在高峰期像'大批量', 两种状态自动切换.

------------------------------------------------------------------------------------
[分段看] 尖峰期(7,383 条) vs 非尖峰期(45,490 条) 分别的表现:

  策略                     低谷P99     尖峰P99     低谷P999     尖峰P999
  --------------------------------------------------------------
  固定批 bs=16              35.0ms     14.3ms      45.2ms      16.9ms
  固定批 bs=64             126.2ms     46.9ms     149.5ms      74.7ms
  固定批 bs=256            476.8ms    370.5ms     538.7ms     418.0ms
  固定超时 5ms                7.1ms      7.2ms       7.1ms       7.2ms
  固定超时 20ms              22.3ms     22.5ms      22.4ms      22.6ms
  自适应                     4.0ms      4.1ms       4.1ms       4.2ms

  -> 注意固定批策略的**低谷 P99 反而比尖峰更差** —— 这是反直觉但正确的:
     尖峰期请求多, 一眨眼就凑满一批发车了; 低谷期请求稀疏, 先到的请求
     要干等后来者凑够批. 也就是说, 系统最闲的时候, 用户等得最久.
     固定超时策略修掉了这一点, 但延迟被超时值死死锁住(5ms 配置就是 ~7ms).
     自适应的价值: 低谷期不等(P99 4.0ms, 优于任何静态配置),
     高峰期又能自动放大批量 —— **两段都不吃亏**.

[对应到表格的课题]
  '构建基于推荐请求特征(如用户活跃度、请求峰值)的动态批处理阈值自适应模型'
  本 demo 的自适应规则只用了'队列积压'这一个信号, 已经明显优于静态策略.
  真实系统还能用上更多信号, 这正是课题的空间:
    - 请求特征: 用户序列长度(决定这条请求的实际计算量, 不是所有请求都等价)
    - 时间特征: 日内周期、活动日历(可以**预测**尖峰而不是被动响应)
    - SLA 反馈: 实时 P99 距离 SLA 还有多少余量, 据此决定要不要更激进地凑批
    - 显存约束: 大批需要更多 KV Cache, 要和 demo3 的显存分配协同决策
  更进一步: 这本质上是个在'吞吐-延迟'帕累托前沿上的实时控制问题,
  可以上强化学习/模型预测控制(MPC), 而不只是手写规则.
