========================================================================================
链路 100Gbps | RPC: 20,000QPS x 512B | 集合通信: 每 2.0ms 一个 4.0MB 块
========================================================================================

[带宽账]
  RPC  需求:   0.08 Gbps ( 0.1% 链路)
  集合通信  :  16.00 Gbps (16.0% 链路)
  合计      :  16.08 Gbps (16.1% 链路利用率)

  单个 4.0MB 大包的发送耗时 =    320.0 us
  单个 512B 小包的发送耗时 =    0.041 us
  -> 一个大包占住链路的时间, 相当于 7,812 个 RPC 包的发送时间.
     这就是队头阻塞的量级: RPC 排在大包后面, 就要等这么久.

调度策略                      RPC P50    RPC P99    RPC P999     RPC 最大        训练吞吐
----------------------------------------------------------------------------------------
FIFO 单队列                  0.0us    299.3us     318.0us    320.0us      16.0Gbps
优先级(RPC优先)                0.0us    299.3us     318.0us    320.0us      16.0Gbps
加权轮转 1:1                  0.0us    299.3us     318.0us    320.0us      16.0Gbps
加权轮转 4:1                  0.0us    299.3us     318.0us    320.0us      16.0Gbps
优先级+分片64KB                0.0us      4.9us       5.2us      5.3us      16.0Gbps
优先级+分片4KB                 0.0us      0.3us       0.4us      0.4us      16.0Gbps

----------------------------------------------------------------------------------------
[1] 队头阻塞: FIFO 下 RPC 的 P999 = 318.0us, 最大 320.0us
    而 RPC 包自身只需要 0.041us 就能发完, 链路利用率也只有 16%.
    尾延迟几乎精确等于一个大包的发送时间 320.0us —— 这不是巧合:
    RPC 的尾延迟完全由'倒霉撞上一个正在发的大包'决定, 与平均负载无关.

[2] 反直觉的结果: 优先级队列 P999 = 318.0us, 相比 FIFO 改善 0.0% —— 几乎**没有用**.
    为什么? 因为包一旦开始发送就**不可抢占**(store-and-forward).
    优先级只能决定'下一个发谁', 决定不了'打断正在发的那个'.
    在 16% 这种低利用率下, 队列里通常只有一个大包,
    根本没有'下一个'可选 —— 于是优先级完全失效, 尾延迟仍是那 320us.
    (等到高利用率、队列里堆积多个大包时, 优先级才开始起作用, 见 [4])

[3] 真正治本的是分片: 切成 4KB 后 P999 = 0.37us, 比优先级好 99.9%
    因为不可抢占的时间窗口从 320.0us 缩到了 0.328us,
    整整小了 977 倍. 尾延迟随之等比例下降.
    这条结论的一般形式: **尾延迟的下界 = 最大不可抢占单元的传输时间.**
    想降尾延迟, 就得缩小这个单元, 而不是调整排队顺序.
    代价: 分片增加包头开销和 CPU 中断次数(本 demo 未建模这部分成本),
    片太小会让 CPU/网卡成为新瓶颈, 所以片大小本身是个权衡.

----------------------------------------------------------------------------------------
[4] 利用率推高时会发生什么? 取决于流量的**突发性**, 而不只是平均利用率
    左半张表: 集合通信严格周期性到达(纯训练集群)
    右半张表: 集合通信泊松到达(弹性调度混部, 平均带宽完全相同)

       链路利用率|     周期性 FIFO        周期性 优先级|     突发 FIFO        突发 优先级       突发 分片4KB
  ----------------------------------------------------------------------------------
        16%|        318us          318us|       619us         318us          0.4us
        32%|        319us          319us|      1101us         319us          0.4us
        64%|        319us          319us|      2069us         320us          0.4us
        80%|        320us          320us|      3643us         320us          0.4us
        89%|        320us          320us|      6253us         320us          0.4us
        93%|        320us          320us|     10799us         320us          0.4us

  -> 这张表推翻了一个常见的直觉('利用率高 = 尾延迟差'):
     * 周期性流量下, 即使把利用率推到 93%, P999 依然稳定在一个大包的时间(320us).
       因为到达是规整的(D/D/1 排队), 队列根本不会堆积.
     * 突发流量下, 同样的平均利用率, P999 却随利用率显著恶化 ——
       泊松到达会让多个大包挤在一起, RPC 要等的就不止一个包了.

     所以真正决定尾延迟的是**突发性**, 不是平均利用率. 这恰好解释了
     表格里为什么单独把'弹性调度场景'列为更难的一类: 把在线集群的空闲资源
     分给训练, 引入的不只是更高的利用率, 更是**多个互不协调的任务**
     所带来的突发性 —— 后者才是 SLA 杀手.
     注意最后一列: 无论突发与否, 分片都把 P999 稳定压在 1us 以内.

[对应到表格的课题]
  本 demo 只做了**单点链路**的调度. 表格里的课题要难得多:
  1. '差异化负载的统一性能建模' —— 要能**预测**上面这张表, 而不是模拟出来;
     难在异构网络(NVLink/IB/RoCE 带宽差数十倍)和复杂拓扑层级.
  2. '跨层协同的标准化信令' —— 上面我是**假设**调度器知道哪个包是 RPC.
     真实系统里网络层根本不知道! 应用层的 QoS 优先级传不到转发层,
     这个信息断层才是最难的部分.
  3. '无侵入落地' —— 分片和优先级都要求改协议栈或换交换机配置,
     而课题要求'不修改业务代码、不更换现有硬件'.
