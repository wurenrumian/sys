[水位扫描] 显存用到几成时, 碎片开始真正伤人? (长尾负载, OOM 次数)
  每一列的 OOM 都**不是**因为显存真的不够 —— 存活数据始终在水位以下,
  一个理想分配器应当全程 0 OOM. 所以下面每一个非零数字都是碎片的代价.

  水位        First-Fit    Best-Fit       Buddy   Paged/4MB   Paged/1MB Paged/256KB
  -------------------------------------------------------------------------------
  60%               0           0          11           0           0           0
  70%               3           0         127           0           0           0
  80%              41          18         322          38           0           0
  85%              89          52         423         335           0           0
  90%             162          93         534         568           0           0
  95%             244         161         654         685          53           0

  -> 三件事同时发生, 都值得注意:
     1. 连续分配器(First/Best-Fit)在 70~80% 水位就开始因**外部碎片** OOM,
        意味着显存的最后 20~30% 你根本用不上.
     2. Buddy 最早垮, 因为向上取整到 2 的幂制造了约 30% 的**内部碎片**.
     3. Paged/4MB 在 80% 以上同样 OOM —— 但原因完全不同: 它没有外部碎片,
        垮掉是因为 4MB 的页对中位数仅 ~5MB 的请求太粗, 内部碎片高达 ~20%.
        把页减小到 1MB / 256KB, 内部碎片随之下降, 抗压水位显著提高.

     结论不是'分页万能', 而是: **分页把难以控制的外部碎片, 换成了**
     **可以用页大小这一个旋钮精确调节的内部碎片.** 这才是它的真正价值 ——
     从一个无法预测的问题, 变成一个可以定量权衡的问题.
     (代价: 页越小, 页表越大、间接寻址开销越高 —— 见下面的页大小权衡)

====================================================================================
[怎么读这张表]
  外部碎片率 = 1 - 最大连续空闲块 / 全部空闲显存
    它回答的是: '我还剩 1GB 显存, 但我能一次性申请到多大?'
    这个值越高, 就越容易出现'显存明明够, 却 OOM'的诡异现象.
  内部碎片 = 1 - 实际申请量 / 实际占用量  (向上取整浪费掉的部分)

[结论]
  1. First-Fit / Best-Fit 都在和外部碎片搏斗. Best-Fit 挑最小的洞,
     反而制造出大量用不上的小碎屑, 空闲块数量爆炸.
  2. Buddy 用'向上取整到 2 的幂'换来了快速合并, 但代价是显著的内部碎片 ——
     申请 33MB 实占 64MB, 这在长尾分布下浪费极大.
  3. Paged 把外部碎片**直接降为 0**: 因为申请不再要求物理连续,
     任何一页都能被任何请求使用. 内部碎片只剩最后一页的零头(平均半页).

[对推荐场景的意义]
  - 这正是 vLLM 的 PagedAttention 之所以是范式级改进的原因;
    它把操作系统里成熟了几十年的虚拟内存分页思想搬进了 KV Cache 管理.
  - 推荐场景比 LLM **更**需要它: 用户行为序列的长度分布是长尾的(见上表),
    大小差异越大, 连续分配器的碎片就越严重.
  - 页大小是个可调参数: 页越小内部碎片越少, 但页表越大、间接寻址开销越高.
    表格里'构建基于显存使用情况与推理任务特征的智能分配模型'指的就是
    根据实时负载特征动态选择这类参数.
  - 分页还顺带解锁了**前缀共享**: 多个请求的公共前缀可以指向同一批物理页,
    这直接对应电商推荐那条课题里的'用户多刷之间 KvCache 的共享'.
