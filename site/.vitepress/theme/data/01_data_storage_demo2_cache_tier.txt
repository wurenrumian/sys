==============================================================================
Embedding 表 1,000,000 key, 请求 400,000 条, Zipf(a=1.15) 长尾分布
==============================================================================

[0] 分布有多偏: 访问过的 key 共 92,161 个, 其中最热的 1% 承接了 67.0% 的请求
    -> 这就是缓存在推荐场景性价比极高的根本原因

[1] 缓存容量 vs 命中率 (缓存条目数 / 全表)
  容量占比             条目数       LRU       LFU
  0.1%           1,000     58.7%     65.3%
  0.5%           5,000     67.5%     71.6%
  1.0%          10,000     70.6%     73.2%
  5.0%          50,000     76.1%     76.3%
  10.0%        100,000     77.0%     77.0%
  -> 命中率对容量是强凹的: 前 1% 的容量买到了绝大部分收益, 之后急剧衰减

[2] 热点 churn (每 5 万请求换一批热点, 模拟新内容爆火/旧热点过气)
  策略              稳态流量     churn流量        掉幅
  LRU            70.6%       68.3%     -2.3%
  LFU            73.2%       66.9%     -6.3%
  -> 稳态下 LFU 更强(记得住长期热点); churn 下 LFU 的优势被吃掉甚至反转,
     因为陈旧的高频次计数会挡住新热点进入缓存(cache pollution).
     工业方案 W-TinyLFU: 小 LRU 窗口吸收突发 + 主体 TinyLFU 保稳态 + 计数老化.

[3] 端到端有效延迟 —— '提命中率' 和 '让某层变快' 哪个更值?
  层级                  延迟(us)     相对HBM
  GPU HBM                0.2        1x
  本机 DRAM                2.0       10x
  远程 DRAM/RDMA          10.0       50x
  本地 NVMe              100.0      500x
  对象存储               10000.0    50000x

  场景A 穿透率高:   穿透到对象存储 = 2.000%, 基线有效延迟 = 210.86 us
    投入                            延迟(us)        改善
    上层调优: HBM +1pt                210.84      0.0%
    硬件升级: NVMe 提速 10x           203.66      3.4%
    压穿透: 穿透率减半                   111.86     47.0%

  场景B 穿透率低:   穿透到对象存储 = 0.050%, 基线有效延迟 = 17.81 us
    投入                            延迟(us)        改善
    上层调优: HBM +1pt                 17.79      0.1%
    硬件升级: NVMe 提速 10x             8.85     50.3%
    压穿透: 穿透率减半                    15.33     13.9%

  -> 场景A 里穿透率虽只有 2%, 却贡献了绝大部分平均延迟, 此时上层调优和硬件升级
     基本是噪声, 唯一有效的动作是压穿透率; 等穿透率压到万分之几(场景B),
     压穿透的边际收益迅速衰减, 上层的命中率分布才开始成为主要矛盾.
     这就是 TikTok 那条课题写'优化多级 Buffer 穿透率'而不是'把某层做快'的原因 ——
     优化顺序是被这条延迟-穿透率曲线决定的, 不是拍脑袋定的.

[4] 分层的成本意义 (相对单位成本; 200TB Sparse 参数不可能全放 HBM)
  层级                    容量占比        相对成本
  GPU HBM               0.5%       0.500
  本机 DRAM               5.0%       0.500
  远程 DRAM/RDMA         15.0%       1.200
  本地 NVMe              30.0%       0.300
  对象存储                100.0%       0.050
  合计                               2.550   (全量放 HBM = 100.0)
  -> 存储成本降到全 HBM 方案的 2.55%;
     在低穿透率下(场景B), 代价是有效延迟 17.8us vs 全 HBM 的 0.2us.
     即: 成本降到 1/39, 换来延迟涨 89 倍.
     分层存储的全部设计工作, 就是在这条兑换曲线上找业务能接受的那个点.
