写法                            耗时(ms)       加速比      ns/元素   备注
------------------------------------------------------------------------------
纯 Python 循环                   77.5        1x       38.8   (实测 200,000 元素后线性外推)
列表推导 + sum                    80.0        1x       40.0   (同上外推)
numpy 向量化                      7.3       11x        3.6   
numpy out=(零分配)                7.9       10x        3.9   
numpy 布尔掩码                    16.9        5x        8.5   <- 陷阱: 看似省算术, 实则 gather/scatter

结果一致性检查: 各写法结果相对偏差 3.11e-03 (外推项有采样误差, 应 <1e-2)

------------------------------------------------------------------------------
[为什么慢] 纯 Python 每个元素要做的事:
  1. 取指/译码: 解释器逐条执行 BINARY_MULTIPLY 等字节码
  2. 装箱拆箱: a[i] 返回的是堆上的 PyFloatObject, 不是寄存器里的 float
  3. 动态分派: 每次乘法都要查类型, 决定调用哪个 __mul__
  4. 引用计数: 每个中间对象的生死都要维护 refcount(还可能触发 GC)
  真正的浮点乘法只占其中不到 1%.

  向量化的本质: 一次类型分派处理整个数组, 把上面 1-4 摊薄到接近 0.

------------------------------------------------------------------------------
[新瓶颈] 向量化之后, 瓶颈从'解释器'变成了'内存带宽':
  numpy 版本搬运约 56 MB, 耗时 7.3 ms
  -> 实测有效带宽 7.7 GB/s
  而这段代码的算术量只有约 6M FLOP, 算术强度 0.11 FLOP/Byte
  算术强度 < 1 意味着这是彻底的 memory-bound —— 加再多算力也没用,
  唯一的出路是**减少访存次数**, 也就是算子融合 (见 demo2).

------------------------------------------------------------------------------
[本 demo 最反直觉的一点] 手工优化是不可预测的:
  '零分配 out=' 和 '布尔掩码只算需要的部分' 这两种听起来都更优的写法,
  实测都比朴素的 numpy 向量化**更慢**(慢 2.5x 和 7.7x). 原因分别是:
    - out= 版: 在这个尺寸下分配根本不是瓶颈(numpy 有 allocator 缓存),
               而 copyto(where=) 的逐元素判定反而引入了额外开销;
    - 掩码版: 不连续的 gather/scatter 访存代价, 远超省下来的那点算术量.
  也就是说, 靠人肉猜'哪种写法更快'的成功率并不高 —— 必须实测.

[对编译方向的意义]
  这正是表格那句痛点的实质: '局部手动优化开发成本高、维护难、破坏 Python 研发体系'.
  手工优化不仅贵, 而且经常是负收益, 因为程序员的心智模型跟不上
  cache/预取/向量化/分配器的真实行为.
  编译方向的目标: 让算法同学写 v1 那样自然的代码, 由编译器基于**实际的 cost model**
  (而不是人的直觉)自动选择 codegen 策略, 稳定产出接近 v5 的性能.
