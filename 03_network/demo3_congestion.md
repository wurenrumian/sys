# demo3 · 拥塞控制：为什么一个算法服务不了两类流量

> 队列深度和尾延迟几乎是一回事。而 RPC 要浅队列、训练大流要深队列 —— 同一个队列没法既浅又深。

---

## 一、真实场景：这段代码对应线上的什么

表格原文："现有拥塞控制算法要么针对 RPC 低延迟优化（如 DCTCP），要么针对大模型高吞吐优化
（如 HPCC、AICC），**缺乏同时满足两类需求的通用算法**"。

拥塞控制回答一个问题：**发送方该以多快的速度发？**

- 发太慢 → 链路空闲，带宽浪费
- 发太快 → 数据堆在交换机队列里 → **排队延迟** → 尾延迟灾难；再快就丢包

而队列深度直接等于排队延迟：

```
排队延迟 = 队列深度 / 链路速率
```

所以拥塞控制的目标其实是两个**天然冲突**的东西：

```
(a) 链路利用率高  ——  要求随时有数据在途，不让链路空闲
(b) 队列深度低    ——  队列深度就是排队延迟，直接决定尾延迟
```

**填满队列是确保 (a) 的最简单办法，但它直接毁掉 (b)。**
"高利用率 + 低队列"是所有拥塞控制算法的圣杯。

## 二、这个 demo 具体干了什么（流程）

### 模型：按毫秒推进的流体近似

```python
每个 ms：
    offered = Σ(各流 cwnd) / RTT          # 本 ms 想发多少
    served  = min(offered + queue, 链路能力)
    queue   = max(0, queue + offered - 链路能力)     # 超出的堆进队列
    lost    = queue > QUEUE_CAP                      # 队列满了就丢
    marked  = queue > K                              # 超过 ECN 阈值就打标
    各流根据 (marked, lost) 调整自己的 cwnd
```

**这不是包级仿真**，但足以复现拥塞控制的核心动力学：在途数据超过 BDP 的部分会堆在队列里。

### 统计口径

丢掉前 1/4 的启动瞬态（避免慢启动污染稳态指标），然后统计：
链路利用率、平均队列、P99 队列、平均/P99 延迟、Jain 公平性指数。

### 关键参数

```
BDP = 链路速率 × RTT = 100 包        # 带宽时延积：在途数据的"理想量"
QUEUE_CAP = 500 包                   # 交换机缓冲，是 BDP 的 5 倍
DCTCP_K = 20 包                      # ECN 标记阈值
```

## 三、涉及的算法

### Reno（丢包驱动，AIMD）

```python
无事发生：cwnd += 1/cwnd        # 加性增：每 RTT 涨 1
丢包：    cwnd = cwnd / 2       # 乘性减
```

**致命弱点：它只能靠丢包感知拥塞，而丢包意味着队列已经满了。**
于是 Reno 的稳态就是"把队列填满 → 丢包 → 减半 → 再填满"的锯齿，**队列常年很深**。

这就是著名的 **bufferbloat**：运营商为了不丢包配了大缓冲区，
结果被丢包驱动的算法当成"可用容量"填满，延迟灾难。

### DCTCP（ECN 驱动）

```python
alpha = (1-g)·alpha + g·(本次是否被标记)     # 标记比例的指数加权移动平均
被标记：cwnd *= (1 - alpha/2)                 # 按标记比例【温和】降速
```

两个关键改进：

1. **在队列变深之前就拿到信号**（交换机队列超过 K 就给包打 ECN 标记），而不是等丢包；
2. **按标记比例温和降速**，而不是 Reno 的粗暴减半 —— 轻微拥塞就轻微降速。

于是队列能稳定在 K 附近的低水位。**代价**：需要交换机支持 ECN 标记，且 K 要针对场景调优。

### BBR 式（BDP 驱动）

```python
bw_est  = max(近期交付率)
min_rtt = min(近期 RTT)
cwnd    = gain × bw_est × min_rtt       # 把在途数据控制在 BDP 附近
```

**不响应单个丢包/标记**，而是主动估计瓶颈带宽和最小 RTT。
理想情况下能同时拿到高利用率和空队列 —— 但代价是**要准确估计 BDP**：
估高了自己制造队列，估低了浪费带宽。

## 四、方案对比

| 算法 | 拥塞信号 | 反应方式 | 队列水位 | 优点 | 代价 |
|---|---|---|---|---|---|
| **Reno** | 丢包 | 减半 | **满**（bufferbloat） | 无需网络支持 | 尾延迟灾难；对 RPC 致命 |
| **DCTCP** | ECN 标记比例 | 按比例温和降速 | **低（≈K）** | 高利用率 + 低延迟 | 需交换机 ECN；K 要调 |
| **BBR 式** | 交付率 + minRTT | 直接设 cwnd = BDP | 理论上空 | 不靠丢包，跨广域网强 | BDP 估计误差；和 Reno 共存时抢不过/抢太多 |

## 五、怎么读输出

### 主表

```
算法                  链路利用率   平均队列  P99队列   平均延迟   P99延迟   公平性
Reno (丢包驱动)          87.1%      56包    474包    1.56ms    5.74ms    1.000
DCTCP (ECN驱动)          98.6%       5包     21包    1.05ms    1.21ms    1.000
BBR式 (BDP驱动)          96.9%       3包      6包    1.03ms    1.06ms    1.000
```

**读法**：

- Reno 利用率 87% 看着不低，但**平均队列 56 包**，把 RTT 从 1ms 抬到 1.56ms，P99 抬到 5.74ms。
- DCTCP 利用率**更高**（98.6%）而队列**更浅**（5 包）—— 两个目标同时改善了。
  这说明 Reno 的深队列不是"换来的吞吐"，而是**纯粹的浪费**。
- **队列深度和延迟这两列几乎是同一条数据**（延迟 = RTT + 队列/速率），这是本 demo 的基本事实。

### `[DCTCP 的阈值 K 怎么选]`

```
   K(包)     利用率   平均队列   P99延迟    适合谁
       5     98.3%      2包     1.06ms   延迟可接受
      20     98.6%      5包     1.21ms   延迟可接受
     100     98.9%     25包     1.90ms   延迟可接受
     200     99.0%     50包     2.75ms   延迟偏高, RPC 吃亏
```

**先说这张表【没有】显示什么**：所有 K 的链路利用率都在 98% 以上。
也就是说在这个理想化模型里（单瓶颈、同构 RTT、恒定负载），
**把 K 调小几乎是免费的** —— 队列变浅、延迟变好、吞吐没损失。
如果只看这个模型，结论会是"K 越小越好"，那 DCTCP 就没有取舍可言了。

**但现实中 K 不能无限小**，原因是这个流体模型**没有建模**的两件事：

1. **突发吸收**：真实流量是突发的，浅队列没有缓冲余量，突发直接变成丢包，
   而丢包重传的代价远大于排队。**队列的存在本就是为了吸收突发。**
2. **反馈时延**：ECN 信号要一个 RTT 才能传回发送方。在这一个 RTT 里队列仍在增长，
   K 太小会导致来不及反应就已经溢出，引发剧烈震荡。

这两件事都需要包级仿真才能复现。

> **所以"一个算法服务不了两类流量"的真正含义，不是"K 调不好"，而是：**
> **RPC 要浅队列（低延迟），训练大流要深队列（吸收突发、保吞吐），**
> **同一个队列没法同时既浅又深** —— 这是**队列本身的物理约束**，不是参数调优能绕过去的。
>
> 出路只能是给两类流量分配**不同的队列**，而这又要求网络能**区分**它们
> —— 回到 `03/demo1` 和跨层信令的问题。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `QUEUE_CAP` | 500 → 2000 | **Reno 的队列和延迟跟着涨，利用率几乎不变** | **这就是 bufferbloat 的实验证据**：给丢包驱动的算法更大的缓冲，它只会填得更满，一点吞吐都不多赚 |
| `QUEUE_CAP` | 500 → 120 | Reno 的延迟大幅改善（被迫早丢包） | 缓冲区小反而延迟好 —— 反直觉但正确 |
| `N_FLOWS` | 4 → 32 | 各算法的队列都变深，Reno 尤其 | 并发流越多，聚合的攻击性越强，单流的温和无济于事 |
| `RTT_MS` | 1.0 → 10 | BDP 变大，DCTCP 的 K 相对变小，可能出现利用率下降 | **K 应该按 BDP 定，而不是拍一个绝对包数**。这是 DCTCP 部署时最常见的坑 |
| `DCTCP_K` | 20 → 2 | 本模型里几乎没有代价 | 提醒你这个模型的边界：它抓不到突发吸收和反馈时延 |

**建议做第一个实验**（`QUEUE_CAP` 翻 4 倍）。看着 Reno 的延迟涨而吞吐不涨，
是理解 bufferbloat 最快的方式。

## 七、对应到表格的课题

表格提的解法方向是"通用自适应传输与拥塞控制策略设计"，即算法要能
"自动识别负载类型，动态调整拥塞窗口、速率控制、队列调度策略"。拆开来是三个真问题：

1. **怎么识别流量类型？** 包长分布、到达周期性、连接时长都是线索，
   但要在线实时判断，且不能误判（误判的代价是 SLA 违约）。
2. **识别之后怎么隔离？** 光有分类没用，还要能给不同类流量分配不同的队列/阈值 ——
   这需要交换机侧的多队列支持（回到 `demo1`）。
3. **信号怎么跨层传递？** 应用层知道"这是延迟敏感的 RPC"，但传不到交换机；
   交换机知道"这条链路拥塞了"，但传不回去指导并行策略调整。这就是"跨层信令"课题。

**另见 `03/demo4`**：DCTCP 正是为 incast 设计的，但它需要一个 RTT 才生效，
而 incast 的突发在一个 RTT 内就完成了 —— 这是拥塞控制对 incast 天然乏力的原因。
