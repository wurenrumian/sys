# demo4 · Incast 崩塌与尾延迟放大：系统自己造出来的两个杀手

> 加大缓冲把"每次都炸"变成"偶尔炸"，而 SLA 恰恰按偶尔那次签。
> 单分片 p99=1%，扇出 100 就有 63% 的请求踩雷。

---

## 一、真实场景：这段代码对应线上的什么

一次推荐请求的真实链路是 **scatter-gather（扇出-聚合）**：

```
                   ┌→ 召回分片 1  ┐
                   ├→ 召回分片 2  │
用户请求 → 接入层 ──┼→ ...        ├→ 等【全部】返回 → 粗排 → 精排 → 返回
                   ├→ 分片 63     │
                   └→ 分片 64     ┘
        （还有 embedding 参数服务器、特征服务、多路模型…同样是扇出）
```

这个结构自带两个杀手，而且**都和链路带宽不够无关** —— 平均利用率可能只有百分之几：

| 杀手 | 机制 | 后果 |
|---|---|---|
| **Incast** | N 个响应几乎**同时**回到同一个网口 → 瞬时突发压垮交换机出端口缓冲 → 丢包 → TCP 超时重传 | P999 从微秒级跳到 200ms |
| **尾延迟放大** | 请求延迟 = max(N 个分片)，分片越多越容易撞上慢的 | 扇出 100 时中位数请求都变慢 |

---

## 二、这个 demo 具体干了什么（流程）

### 杀手一：Incast 模拟

```python
burst_kb = w × resp_kb                              # 一轮里同时涌向网口的数据量
avail    = buffer_kb × uniform(0.4, 1.0)            # 可用缓冲（背景流量占掉一部分）
drain_kb = 链路在一个 RTT 内能排掉的量
overflow = max(0, burst_kb - avail - drain_kb)
lost     = ceil(overflow / resp_kb)                 # 溢出多少就丢多少个响应

一轮耗时 = 传输时间 + RTT + (若这轮有丢包，再加一个 RTO)
```

**两个关键建模点**：

1. **可用缓冲是随机的**（0.4~1.0 倍），因为背景流量占了一部分。
   这正是为什么 incast 表现为"偶发的、难复现的" P999 毛刺 —— 同样的扇出有时丢有时不丢。
2. **RTO 是毫秒级，传输是微秒级**，差 2~3 个数量级。这个不对称是整个问题的核心。

`batch=W` 参数模拟**应用层限并发**：一次只向 W 个分片发请求，分多轮完成。

### 杀手二：尾延迟放大

```python
单分片延迟 ~ lognormal，中位数 1ms，p99 = SHARD_P99_X × 中位数
请求延迟 = max(N 个分片的延迟)
```

对数正态模拟真实的服务延迟长尾。这个长尾来自：GC、page cache miss、锁竞争、
被同机邻居抢 CPU、磁盘/网卡队列、以及最烦人的"这台机器就是有点慢"。

**对冲请求（hedged request）**：

```python
thr = 第 hedge_pct 百分位
慢分片的实际延迟 = min(原来的, thr + 重发那份的延迟)
额外负载 = 超过阈值的分片比例
```

## 三、涉及的机制

### 为什么 incast 是"崩塌"而不是"退化"

```
扇出 16：突发 512KB < 缓冲 → 零丢包 → 完成时间 0.22ms，吞吐 19 Gbps
扇出 32：突发 1MB   ≈ 缓冲 → 75% 的请求丢包 → 完成时间 200ms，吞吐 0.06 Gbps
```

跨过临界点后吞吐不是缓慢下降，而是**断崖式**掉下去。原因是：
**等 RTO 的时候链路是空着的。** 带宽没被用完，时间却全花光了。

这是所有 scatter-gather 系统（推荐召回、分布式存储、MapReduce shuffle）共同的坑，
而推荐系统的扇出度天然就高。

### 为什么加大缓冲救不了

缓冲加大 4 倍后，P50 从 200ms 变成 0.72ms，看起来救回来了。但 **P99 仍然是 200ms** ——
它只是把"每次都炸"变成"偶尔炸"（踩雷比例从 100% 降到 10%）。

而且缓冲变大本身会抬高排队延迟（bufferbloat，见 `demo3`）。
**花钱换硬件，买到的是一个更难复现的故障。**

> **一般原则：突发问题要在源头解决，在下游用缓冲去接是接不住的。**

### 尾延迟放大的数学

```
P(整个请求全部命中"快"路径) = (1 - p)^N

单分片 p99 = 1%（p = 0.01）：
    N = 1   →  99.0% 的请求没事
    N = 100 →  0.99^100 = 36.6% 没事，即 63.4% 的请求会撞上至少一个慢分片
    N = 300 →  只剩 4.9%
```

**推论：高扇出系统里，单分片的 p99 比平均值重要得多。**
一台机器偶尔慢一下，在扇出 1 的系统里没人察觉，在扇出 100 的系统里是大多数请求都会碰到。

### 对冲请求为什么有效

慢是**独立随机**的：同一个分片在两台副本上同时慢的概率，是各自慢的概率相乘。
所以"等一会儿还没回来就再发一份，取先回的"能把 `max` 的尾巴砍掉一大截，
而代价只是 `1 - hedge_pct` 比例的额外请求量。

**本质是用一点冗余算力去买确定性。**

## 四、方案对比

### Incast 的四种解法

| 方案 | P50 | P99 | 踩雷比例 | 有效吞吐 | 评价 |
|---|---|---|---|---|---|
| 不做任何控制 | 200ms | 200ms | 100% | 0.08 Gbps | — |
| **缓冲区加大 4x**（换硬件） | 0.72ms | **200ms** | 10.2% | 0.80 Gbps | 治标，且抬高排队延迟 |
| **响应压缩到 1/2** | 200ms | 200ms | 75% | 0.06 Gbps | 只是把临界扇出度乘 2 |
| **应用层限并发 W=16** | 0.87ms | **0.87ms** | **0%** | 19.3 Gbps | **治本，一行业务代码** |

工业界的完整方案还包括：让分片错峰返回、用 DCTCP/ECN 提前降速、
把 `RTO_min` 从 200ms 调到微秒级、RDMA 的无损网络 PFC —— 各有代价。

### 尾延迟的对策

| 方案 | 请求 P99 | 额外负载 | 前提 |
|---|---|---|---|
| 不对冲 | 35.9ms | 0% | — |
| **p95 后对冲** | **12.1ms** | 5% | 请求**幂等** + 系统有**余量** |
| p90 后对冲 | 11.1ms | 10% | 同上 |

**两个前提缺一不可**：

1. 请求必须**幂等**（重复执行不产生副作用）—— 读请求天然满足；
2. 系统要有**余量**。如果本来就跑在 90% 负载上，对冲会引发**雪崩**：
   多打的请求让系统更慢，更慢又触发更多对冲 —— 正反馈。
   所以工业实现都会给对冲加**全局速率上限**（比如"对冲量不超过总量的 5%"）。

## 五、怎么读输出

### `[0] 先算账`（读表之前先看这个）

```
一次请求的响应总量 = 64 × 32KB = 2048KB，而缓冲只有 1024KB —— 突发量是缓冲的 2 倍
传完这 2048KB 只要 0.67ms，而丢一个包要等 200ms 才重传 —— 差 298 倍
```

**整个 incast 问题就浓缩在最后这个对比里。**

### `[1] 扇出度扫描` —— 看崩塌

```
扇出度      P50        P99       P999    踩到丢包   有效吞吐Gbps
     8    0.13ms     0.13ms     0.13ms      0.0%        15.66
    16    0.22ms     0.22ms     0.22ms      0.0%        19.26
    32  200.39ms   200.39ms   200.39ms     75.1%         0.06   ← 崩了
    64  200.72ms   200.72ms   200.72ms    100.0%         0.08
```

吞吐从 19.26 掉到 0.06 —— **300 倍**，而扇出只从 16 变成 32。

### `[2] 四种解法` / `[3] 尾延迟放大` / `[4] 对冲`

见上面的方案对比表。`[3]` 里特别注意 **P50 那一列**：
扇出 100 时请求的**中位数**延迟（11.4ms）已经接近单分片的 p99（9.9ms）。
"一半的请求都很慢"成了常态。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `FANOUT` | 64 → 16 | 完全不丢包，吞吐正常 | 临界点是真实存在的，且很陡 |
| `BUFFER_KB` | 1024 → 8192 | 临界扇出度往后推，但**总能找到一个扇出度让它再崩** | 缓冲只能推迟问题，不能消除 |
| `RTO_MS` | 200 → 5 | 崩塌后的延迟从 200ms 变成 5ms，**吞吐大幅恢复** | 数据中心里把 RTO_min 调小是真实且有效的手段（Linux 默认 200ms 是为广域网设计的） |
| `RESP_KB` | 32 → 8 | 临界扇出度乘 4 | 突发量 = 扇出 × 响应大小，两个乘数地位等同 |
| `SHARD_P99_X` | 10 → 3 | 尾延迟放大大幅缓解 | **单分片的尾巴有多长，直接决定扇出系统的命** |
| `FANOUT` | 64 → 300（看 `[3]`） | 撞上慢分片概率 95% | 扇出度是尾延迟的放大器 |

**建议做 `RTO_MS` 那个实验**：把 200 调成 5，看吞吐怎么回来。
它会让你理解为什么"数据中心 TCP"要专门改内核参数 —— 默认值是为互联网设计的，不是为机架内。

## 七、和其他 demo 的关系 / 对应到表格的课题

- **`demo1` 说"大包堵住小包"，本 demo 说"小包自己堵住自己"** ——
  两者都指向同一个结论：**尾延迟由突发和不可抢占单元决定，与平均利用率无关**。
- **`demo3` 的 DCTCP 正是为 incast 设计的**：在缓冲被打满之前就让发送方降速。
  但它需要一个 RTT 才生效，而 incast 的突发**在一个 RTT 内就完成了** ——
  这是拥塞控制对 incast 天然乏力的原因，也是为什么必须在应用层限并发。
- **`01/demo2` 必看**：那里说"缓存命中率 99% 很好"，这里的扇出放大告诉你
  `0.99^500 ≈ 0.65%` —— 几乎每个请求都会碰到至少一个未命中的冷 key。
  **单看命中率会严重低估长尾的伤害。**

**对应表格里"跨层协同的标准化信令体系"**：应用层**知道**自己要扇出 100 个分片，
网络层却要等丢包才发现。如果这个信息能提前传下去（哪怕只是一个"我要发一次 2MB 突发"的提示），
交换机就能提前预留缓冲或调度错峰 ——
**这正是 incast 这个几十年的老问题至今没有干净解法的症结所在。**
