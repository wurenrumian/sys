# demo1 · 队头阻塞：两类流量的冲突与调度策略

> 优先级队列在低利用率下改善 **0%** —— 因为包不可抢占，优先级只能决定"下一个发谁"。

---

## 一、真实场景：这段代码对应线上的什么

一根网线上，同时跑**搬家卡车**和**救护车**：

| | 集合通信（AllReduce/AllToAll） | 微服务 RPC |
|---|---|---|
| 单次大小 | 几 MB ~ 几十 MB | 几百字节 |
| 在乎什么 | 什么时候搬完（**吞吐**） | 有没有被堵住（**尾延迟**） |
| 形态 | 周期性、大包、可预测 | 泊松到达、小包、突发 |

这两者的目标函数**直接冲突**：让卡车跑满带宽，救护车就排在它后面；给救护车让路，卡车吞吐就掉。

而在**弹性调度**场景下（把在线集群的空闲卡分给训练），它们必须共存在同一张网上。
对应表格原文："在推理集群中，用户请求 RPC 流量的 P999 延迟要求通常低于 100ms，
而 KV Cache 分布式同步、多卡推理的张量传输流量占比超过 60%，
两类流量的性能冲突直接影响服务 SLA 达标率"。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造两类流量

```python
RPC :  泊松到达，20000 QPS × 512B          →  0.08 Gbps
Bulk:  每 2ms 一个 4MB 块（严格周期）       →  16 Gbps
                                    合计    →  16.08 Gbps / 100 Gbps = 16% 利用率
```

**注意这个 16%**：整条链路只用了 16%，后面所有的尾延迟灾难都发生在这个**极低**的利用率下。

### 第 2 步：单链路调度模拟

关键建模点：

```python
# 一个包一旦开始发送就【不可抢占】(store-and-forward)
start = max(now, arrive)
dur   = tx_time_ms(nbytes)
now   = start + dur          # 这段时间里，链路被这个包独占
```

**这一条就是队头阻塞的全部机制。** 一个 4MB 包在 100Gbps 上要占 320µs，
期间到达的所有 RPC 都只能排队 —— 哪怕它们只需要 0.04µs 就能发完。

### 第 3 步：四种调度策略

| 策略 | 选包规则 |
|---|---|
| `fifo` | 两队列里谁先到发谁 |
| `priority` | RPC 队列非空就发 RPC，否则发 bulk |
| `wrr` | 加权轮转，按权重比例轮流服务两个队列 |
| `priority + chunk_kb` | RPC 优先，**并且把大包切成小片再入队** |

### 第 4 步：利用率 × 突发性的二维扫描

把 bulk 周期从 2.0ms 缩到 0.345ms（利用率 16% → 93%），
同时对比两种到达模式：

- **周期性**（`bulk_bursty=False`）：纯训练集群，每个 step 同步一次，节奏由计算决定，非常规整
- **泊松**（`bulk_bursty=True`）：弹性调度/多任务混部，多个训练任务互不协调地共用链路

**两者的平均带宽完全一样，差别只在突发性。**

## 三、涉及的机制

### 队头阻塞（Head-of-Line Blocking）

```
时刻 0     : 4MB 大包开始发送，占用链路 320µs
时刻 0.1µs : 一个 RPC 到达 → 只能等
时刻 320µs : 大包发完，RPC 才开始发（自己只要 0.04µs）
             这个 RPC 的延迟 = 320µs，其中 99.99% 是等待
```

### 为什么优先级救不了（本 demo 的核心反直觉点）

优先级队列决定的是**"下一个发谁"**，它决定不了**"打断正在发的那个"**。

在 16% 利用率下，队列里通常**只有一个大包**在发，后面根本没有排队的包 ——
于是"选下一个"这个动作**无事可做**，优先级完全失效。

```
FIFO      P999 = 318.0µs
优先级     P999 = 318.0µs      改善 0.0%
```

**只有当利用率高到队列里堆积了多个包时，优先级才开始起作用**（见扫描表的高利用率行）。

### 为什么分片有效

分片把**不可抢占的时间窗口**从"一个 4MB 包的发送时间"缩小到"一个 4KB 片的发送时间"：

```
320 µs  →  0.33 µs        （小了 1000 倍）
```

于是尾延迟等比例下降。这引出一条可以直接背下来的一般规律：

> **尾延迟的下界 = 最大不可抢占单元的传输时间。**
> 想降尾延迟，就得缩小这个单元，而不是调整排队顺序。

**分片的代价**（本 demo 没建模）：增加包头开销（每片一个头）和 CPU/网卡中断次数。
片太小会让 CPU 或网卡成为新瓶颈，所以片大小本身是个权衡。

### 突发性 vs 平均利用率

排队论里，**周期性到达（D/D/1）** 和 **泊松到达（M/D/1）** 的排队行为完全不同：

- D/D/1：只要服务率 > 到达率，队列**根本不堆积**，排队延迟恒定
- M/D/1：排队延迟 ∝ `ρ/(1-ρ)`，ρ→1 时发散

所以同样的平均利用率，突发流量的尾延迟可以差几个数量级。

## 四、方案对比

| 策略 | RPC 尾延迟 | 训练吞吐 | 实现代价 | 什么时候用 |
|---|---|---|---|---|
| **FIFO 单队列** | 灾难（= 一个大包时间） | 满 | 零 | 只有一类流量时 |
| **优先级** | **低利用率下无改善** | 大流可能饿死 | 需要交换机多队列 + 能识别流量 | 高利用率下才有意义 |
| **加权轮转 WRR** | 折中 | 折中 | 同上 | 需要保证大流最低带宽时 |
| **分片（chunking）** | **压到 1µs 以内** | 略降（包头开销） | 要改协议栈/网卡配置 | **治本的方案** |
| 分片 + 优先级 | 最好 | 略降 | 两者的代价都要付 | 生产环境的完全体 |

## 五、怎么读输出

### 带宽账（读表之前先看这个）

```
  RPC  需求:   0.08 Gbps ( 0.1% 链路)
  集合通信  :  16.00 Gbps (16.0% 链路)
  合计      :  16.08 Gbps (16.1% 链路利用率)

  单个 4.0MB 大包的发送耗时 =    320.0 us
  单个 512B 小包的发送耗时 =      0.041 us
  -> 一个大包占住链路的时间，相当于 7,813 个 RPC 包的发送时间
```

**这三行是全篇的地基**：利用率只有 16%，但一个大包的独占时间是小包的 7813 倍。

### 主表

```
调度策略               RPC P50   RPC P99  RPC P999  RPC 最大   训练吞吐
FIFO 单队列             160.0us   316.7us   318.0us   320.0us   16.0Gbps
优先级(RPC优先)         160.0us   316.7us   318.0us   320.0us   16.0Gbps   ← 一模一样
加权轮转 1:1            160.0us   316.7us   318.0us   320.0us   16.0Gbps
优先级+分片64KB           2.6us     5.1us     5.2us     5.2us   16.0Gbps
优先级+分片4KB            0.19us    0.33us    0.37us    0.41us  16.0Gbps   ← 小了 860 倍
```

- **P999 ≈ 318µs ≈ 一个大包的发送时间（320µs）**，这不是巧合：
  RPC 的尾延迟完全由"倒霉撞上一个正在发的大包"决定，**与平均负载无关**。
- 优先级和 FIFO 数字完全一样 —— 改善 0.0%。
- 分片后训练吞吐**一点没掉**（本模型未建包头开销），而尾延迟小了三个数量级。

### 利用率 × 突发性扫描（本 demo 第二个反直觉点）

```
  链路利用率|  周期性 FIFO  周期性 优先级|  突发 FIFO  突发 优先级  突发 分片4KB
       16%  |      318us        318us  |     320us       320us         0.4us
       48%  |      318us        318us  |     574us       420us         0.4us
       93%  |      318us        318us  |    3273us      1108us         0.5us
```

**推翻了"利用率高 = 尾延迟差"这个常识**：

- **周期性流量**：把利用率推到 93%，P999 依然稳定在 318µs。因为到达是规整的（D/D/1），队列不堆积。
- **突发流量**：同样的平均利用率，P999 恶化了 10 倍。泊松到达会让多个大包挤在一起。
- **注意最后一列**：无论突发与否，分片都把 P999 稳定压在 1µs 以内。

> **真正决定尾延迟的是「突发性」，不是平均利用率。**
>
> 这恰好解释了表格里为什么单独把"弹性调度场景"列为更难的一类：
> 把在线集群的空闲资源分给训练，引入的不只是更高的利用率，
> 更是**多个互不协调的任务**所带来的突发性 —— 后者才是 SLA 杀手。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `BULK_MB` | 4 → 0.5 | P999 从 318µs 掉到约 40µs | 尾延迟**线性正比于最大不可抢占单元**。这是全篇最该验证的一条 |
| `CHUNK_KB` | 4 → 64 | 分片后的 P999 涨 16 倍 | 同上，从另一个方向验证 |
| `RPC_QPS` | 20000 → 200000 | P999 基本不变 | 尾延迟由**大包**决定，和 RPC 自己的负载几乎无关 |
| `LINK_GBPS` | 100 → 400 | 所有延迟等比例下降 | 更快的链路能缓解，但改变不了"尾延迟 ∝ 大包时间"这个结构 |
| `BULK_PERIOD_MS` | 2.0 → 0.4 | 利用率推到 80%，周期性下 P999 仍不变 | 单独验证"周期性流量不怕高利用率" |

**建议先做第一个**（`BULK_MB` 拖到 0.5）。它把"尾延迟的下界 = 最大不可抢占单元"
这条规律直接摆出来，比任何解释都直观。

## 七、对应到表格的课题（本 demo 的边界）

本 demo 只做了**单点链路**的调度。真实课题要难得多：

1. **"差异化负载的统一性能建模"** —— 要能**预测**上面那张表，而不是模拟出来。
   难在异构网络（NVLink/IB/RoCE 带宽差数十倍）和复杂拓扑层级。
2. **"跨层协同的标准化信令"** —— 上面我是**假设**调度器知道哪个包是 RPC。
   真实系统里网络层根本不知道！应用层的 QoS 优先级传不到转发层，
   **这个信息断层才是最难的部分。**
3. **"无侵入落地"** —— 分片和优先级都要求改协议栈或换交换机配置，
   而课题要求"不修改业务代码、不更换现有硬件"。

另见 `03/demo4`：那里讲的是**小包自己堵住自己**（incast），
和这里的"大包堵小包"指向同一个结论。
