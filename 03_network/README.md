# 03 · 基础库团队 - 网络方向

> 表格原文（节选）：数据中心网络面临两类核心负载的差异化需求挑战：**AI 训练推理负载**以周期性、
> 大包、高吞吐的集合通信流量为主；**微服务 RPC 请求**以小包、高频、低延迟流量为主……
> 在推理集群中，RPC 流量的 P999 要求通常低于 100ms，而 KV Cache 分布式同步、多卡推理的张量传输
> 流量占比超过 60%；在训练集群中，AllReduce/AlltoAll 占总流量 80% 以上，而控制面的调度信令、
> 元数据同步虽然仅占 20% 但延迟敏感，极易受集合通信干扰。
>
> 探索方向：差异化负载的统一性能建模、通用自适应传输与拥塞控制、跨层协同的标准化信令体系、
> 全场景兼容与无侵入落地、动态环境下的自适应决策。

## 一、这个课题的一句话版本

> **一根网线上，同时跑"搬家卡车"和"救护车"。**

- 集合通信（AllReduce/AlltoAll）= 搬家卡车：单次几十 MB，只关心什么时候搬完（吞吐）。
- 微服务 RPC = 救护车：单次几百 B，只关心有没有被堵住（尾延迟）。

这两者的目标函数是**直接冲突**的：让卡车跑满带宽，救护车就会排在它后面；给救护车让路，
卡车的吞吐就掉。而在弹性调度（把在线集群的空闲卡分给训练）场景下，它们还必须共存在同一张网上。

难点在于**尾延迟对排队极度敏感**。这是排队论的基本结论：当链路利用率 ρ 接近 1 时，
排队延迟按 `1/(1-ρ)` 发散。利用率从 80% 到 95%，平均延迟涨 4 倍，而 P999 涨得更狠。
demo1 会把这条曲线直接跑出来。

## 二、demo1：两类流量的冲突与调度策略

```bash
python3 demo1_traffic_conflict.py
```

对比四种调度方式，在"RPC 小包 + 训练大流"混跑下的表现：

| 策略 | 做法 | 预期 |
|---|---|---|
| FIFO 单队列 | 先到先服务 | RPC 被大包堵死，尾延迟灾难 |
| 优先级队列 | RPC 绝对优先 | RPC 好了，但训练可能饿死 |
| 加权轮转 (WRR) | 按权重分配带宽 | 折中 |
| 优先级 + 大包分片 | RPC 优先 + 把大包切小 | 兼顾两者 |

**要点**

- **队头阻塞（HoL blocking）**是核心机制：一个 4MB 的 AllReduce 包在 100Gbps 链路上要占用
  ~320µs，期间到达的所有 RPC 都得排队。RPC 本身只需要几微秒。
- 所以**分片（chunking）**是最朴素也最有效的手段：把大包切成小片，就把"不可抢占的占用时间"
  从 320µs 降到了几微秒，给高优先级流量创造了插队点。
- demo 会打印 RPC 的 P50/P99/P999 和训练流的吞吐，让你看到这个取舍的具体数字。

## 三、demo2：AllReduce 通信量 —— 为什么拓扑算法这么重要

```bash
python3 demo2_allreduce.py
```

**要点**

- 表格提到千卡规模下"卡间通信开销会随着卡数变多而效率变低"。这不是玄学，是可以算的。
- 三种算法的通信模型（N 卡，数据量 D）：

  | 算法 | 通信轮数 | 单卡传输量 | 特点 |
  |---|---|---|---|
  | Naive（中心汇聚） | 2 | (N-1)·D | 中心节点带宽成为瓶颈，完全不可扩展 |
  | Ring AllReduce | 2(N-1) | 2·(N-1)/N·D | **单卡传输量与 N 无关**，但延迟随 N 线性增长 |
  | Tree / Halving-Doubling | 2·log₂N | ~2·D | 延迟只随 log N 增长，适合小数据/大规模 |

- 关键洞察：**Ring 是带宽最优的，Tree 是延迟最优的**。数据量大时被带宽支配 → 用 Ring；
  数据量小时被启动延迟支配 → 用 Tree。NCCL 实际上会根据数据量和拓扑自动选择。
- demo 会在 8/64/512/1024 卡、不同数据量下算出各算法的耗时，并标出交叉点。
  你会清楚看到"千卡规模下通信效率变低"具体是怎么发生的。

## 四、demo3：拥塞控制 —— 为什么一个算法服务不了两类流量

```bash
python3 demo3_congestion.py
```

**要点**

- 表格原文："现有拥塞控制算法要么针对 RPC 低延迟优化（如 DCTCP），要么针对大模型高吞吐优化
  （如 HPCC、AICC），缺乏同时满足两类需求的通用算法"。
- demo 实现三种拥塞控制的简化版，在同一个瓶颈链路上跑：
  - **Reno（丢包驱动）**：必须把队列填满、丢包了才知道拥塞 → 队列常年很深 → 尾延迟差。
  - **DCTCP（ECN 驱动）**：交换机队列超过阈值就打标记，发送方按标记比例温和降速
    → 队列维持在低水位 → 尾延迟好，但对大流略保守。
  - **BBR 式（带宽时延积驱动）**：主动探测瓶颈带宽和最小 RTT，把在途数据量控制在 BDP 附近。
- demo 打印每种算法的：链路利用率、平均队列深度、P99 排队延迟、公平性。
  你会看到**队列深度和尾延迟几乎是一回事**，而"高利用率 + 低队列"是所有拥塞控制的圣杯。

## 五、把三个 demo 串起来的一张图

```
应用层     RPC 请求(小包/低延迟)          AllReduce(大包/高吞吐)
              │                                  │
              │  <-- 缺一个标准化的跨层信令 -->    │   (表格里的"跨层协同"课题)
              ▼                                  ▼
传输层     拥塞控制算法 (demo3: 一个算法服务不了两类需求)
              │
              ▼
网络层     队列调度 / 优先级 / 分片 (demo1: 队头阻塞与取舍)
              │
              ▼
物理层     拓扑与集合通信算法 (demo2: Ring vs Tree, 千卡下的效率衰减)
```

表格里那句"打通应用语义、传输协议、网络转发三层壁垒"，说的就是：
**上层知道自己是什么流量但没法告诉网络，网络看到了拥塞但没法反馈给上层去调整并行策略。**
这个信息断层是当前所有局部优化的天花板。

## 六、可以往下挖的研究点

| 表格里的方向 | 真正的难点 | 切口 |
|---|---|---|
| 统一性能建模 | 两类流量的 QoS 度量都不同构 | 用排队论 + 实测校准，建 (拓扑, 混部比例) → (延迟, 吞吐) 的预测模型 |
| 通用自适应拥塞控制 | 要先能**识别**流量类型 | 在线分类（包长/周期性/连接时长）+ 分类驱动的参数切换；或直接上 RL |
| 跨层信令标准 | 要跨 RPC 框架/NCCL/内核/交换机 | 复用现有可扩展字段（IPv6 扩展头/INT），避免改硬件 |
| 无侵入落地 | 不能改业务代码、不能换硬件 | eBPF + 用户态协议栈；在 NCCL/RPC 框架的下层做透明拦截 |
| 动态自适应 | 静态策略在故障/负载突变时失效 | 实时遥测 + 控制论方法（MPC）；注意控制环路本身的稳定性 |
