前面的目录是知识本身，这一页是学习顺序、自检方式，以及往外走的入口。

## 一、先说方法：这类材料该怎么学

这些 demo 的目标不是让你"知道有列存这回事"。知道概念的人很多，
区别在于**能不能算出量级、能不能说出边界条件**。所以：

**1. 先看结论，再看过程，最后自己推翻它。**
每个 demo 顶上都有一句"反直觉结论"。先只看这句话，问自己：我信吗？为什么？
然后再跑 demo 看数据。**你不同意的地方，才是你真正学到东西的地方。**

**2. 每读完一段，逼自己写一个数量级估算。**
比如："1000 亿条/日、单条 1KB → 100 PB/日 → 列存压缩 6x + 投影 7.5% → 一次实验扫 1.25 PB。"
能把这类账当场算出来，就已经超过大多数人了。

**3. 改参数，找结论失效的边界。**
网站上每个 demo 都能调参重跑。一个结论如果只在默认参数下成立，那它多半是巧合。
真正的理解是知道**它什么时候不成立**：
- 列存的收益依赖"投影比例低"，一次实验要全字段时它归零；
- 分片能压尾延迟，但片太小时 CPU 中断和包头开销会反噬；
- 对冲请求很有效，但系统跑在 90% 负载时它会引发雪崩。

**4. 每个方向问自己"钱花在哪"。**
系统优化最终是成本问题。存储分层是拿延迟换成本，分桶是拿算力换稳定性，
对冲是拿冗余算力换确定性。**说得出交换的是什么，才算真懂。**

## 二、四周学习路线

### 第 0 步（30 分钟）：先看清全局

```bash
python3 04_endtoend/demo1_step_budget.py     # 一次 step 的账单
```
读 `00_overview/README.md` 的量级速查表。把延迟阶梯和脊点记住。

> 目标：能回答"一次训练 step 的时间大概花在哪三段，各占多少"。

### 第 1 周：网络（03）

一次 step 的时间大头通常在这里，而且它的规律（排队论、尾延迟）最通用。

- day 1–2：`demo1` 队头阻塞与分片。重点体会"尾延迟 = 最大不可抢占单元的传输时间"。
- day 3–4：`demo2` AllReduce 的 alpha-beta 模型。**手推一遍** Ring 和 Tree 的公式。
- day 5：`demo3` 拥塞控制。理解"高利用率 + 低队列"为什么是圣杯。
- day 6–7：`demo4` incast 与 tail at scale。这一节的结论最容易迁移到任何分布式系统。

> 自检：不看材料，说清楚"为什么优先级队列救不了尾延迟"，以及"分片的代价是什么"。

### 第 2 周：存储（01）

- day 1：`demo1` 行存/列存。能算出压缩比 × 投影比的复合收益。
- day 2–3：`demo2` 缓存与分层。重点是"穿透率决定平均延迟"这条曲线，
  以及为什么"提命中率"通常比"让某层更快"划算。
- day 4：`demo3` DCAI。理解 PSI 的盲区，以及为什么必须分层组合多种监控。
- day 5–6：`demo4` 不定长序列。搞清楚 padding / 分桶 / Jagged 三者的取舍。
- day 7：`demo5` 流水线重叠。这是最实用的一节，几乎所有训练任务都能用上。

> 自检：说清楚"为什么动态 padding 几乎没用，而排序分桶有用"。

### 第 3 周：编译（02）

- day 1：`demo1` 解释器开销。理解装箱、分派、引用计数各自的代价。
- day 2–3：`demo2` 算子融合。**这一节最重要**：算术强度 → memory/compute-bound 判断
  → 融合为什么是头号优化。
- day 4：`demo3` 显存碎片。理解外部碎片与内部碎片的区别，以及分页的真实价值。
- day 5：`demo4` 动态批处理。
- day 6–7：`demo5` 动态 shape。理解它和 `01/demo4` 的 Jagged 之间的**张力**。

> 自检：说清楚"为什么在 Python 层写不出有效的算子融合"。

### 第 4 周：串起来 + 往外走

- 重跑 `04_endtoend/demo1`，用不同参数模拟你关心的场景。
- 挑一个方向，读下面资料清单里的 2~3 篇原始材料。
- 把"三个方向 → 一次 step 的三段"这张图，讲给一个不懂的人听。**讲得通才算学会。**

## 三、高频追问与参考答案

这些是这份材料对应的方向上，最容易被追问的问题。答案给的是**思路骨架**，
不要背，要能用 demo 里的数据把它撑起来。

### 存储方向

**Q：列存到底省在哪？只是压缩率高吗？**
A：两处，而且是**相乘**的关系。① 投影：只读需要的列，I/O 按投影比例线性下降；
② 压缩：同一列的数据同质、熵低，压缩比更高。默认 demo 里是 7.5% × (1/6.85)。
代价是写入要攒批（column chunk），批大则数据不新鲜、批小则压缩差且小文件爆炸——
**这正是流式 Lakehouse（Iceberg/Hudi/Paimon）的核心矛盾**。

**Q：缓存该做多大？**
A：不该先问"多大"，该先看命中率-容量曲线。Zipf 分布下它是强凹的：前 1% 容量买到绝大部分收益。
而分层系统里真正决定平均延迟的是**穿透率**——因为最底层比顶层慢 4~5 个数量级，
2% 的穿透率就能贡献绝大部分平均延迟。所以优化顺序是被这条曲线决定的，不是拍脑袋定的。

**Q：LRU 还是 LFU？**
A：稳态热点用 LFU（记得住长期热点），热点 churn 时 LFU 反而更差
（陈旧的高频计数挡住新热点进入，cache pollution）。工业方案是 W-TinyLFU：
小 LRU 窗口吸收突发 + 主体 TinyLFU 保稳态 + 计数老化。推荐场景 churn 很剧烈（新内容不断爆火），
所以这个选择很关键。

**Q：怎么监控数据质量？PSI 够吗？**
A：不够，而且它的盲区恰好是推荐系统最高频的事故。PSI 是**单特征边缘分布**指标，
对"分布没变但语义错位"（离在线不一致、特征版本错位）完全盲视——demo 里 AUC 掉了 2 个点，
PSI 判定"正常"。必须分层组合：统计类（空值率）抓任务挂掉、分布类（PSI/KS）抓口径变更、
**逐样本对拍**抓训推不一致、特征-label 关联漂移抓语义错位、影子流量 AUC 兜底。

**Q：不定长序列怎么处理？**
A：三条路。① padding（简单但浪费，注意**动态 padding 在长尾下几乎无效**，
因为一批里有一个长样本就撑满了，必须配合按长度排序分桶）；
② 截断（拿效果换成本，砍掉的是重度用户的长期兴趣，要和算法一起决策）；
③ Jagged（零浪费，但每个算子都要重写，且破坏静态 shape、和编译器对冲）。
工业上通常是"排序分桶 + 局部 Jagged"的组合。

### 编译方向

**Q：这个方向不就是把 Python 换成 C++ 吗？**
A：不是，题目明确要保住 Python 研发体系。真正的问题是**在不改变表达的前提下换掉执行方式**。
而且推荐场景比 `torch.compile` 的常规假设多两个约束：高频迭代（要增量编译/热更新，
不能每次全量编译几分钟）、不定长稀疏数据（静态 shape 假设直接失效）。

**Q：算子融合能带来多少收益？**
A：先做 roofline 判断。逐元素算子的算术强度远小于 1 FLOP/Byte，是彻底 memory-bound，
所以收益上界由**访存次数**决定：`d=relu(a*b+c)*s` 从 8 趟降到 4 趟，理论 2x。
实测 `torch.compile` 有时会超过 2x，因为它顺带消掉了算子分发和临时张量分配的框架开销——
**访存模型只是下界**。

**Q：为什么不能在 Python 里手写融合？**
A：直接冲突的两个要求：块要**小**才能进 cache（融合才有意义），
块要**大**才能摊薄每块 5 次 numpy 调用的解释器开销。demo 的块大小扫描把这个冲突跑出来了——
手写分块比不融合还慢。融合必须发生在**编译产物内部**。

**Q：显存明明够为什么 OOM？**
A：外部碎片——空闲显存不连续，最大连续块装不下一次申请。推荐场景尤其严重，
因为不定长请求让每次分配大小都不同。分页（PagedAttention 思路）把外部碎片降为 0，
代价是内部碎片，但**内部碎片是可以用页大小这一个旋钮精确调节的**。
这才是分页的真正价值：把一个无法预测的问题，变成一个可以定量权衡的问题。

**Q：动态 shape 怎么办？**
A：三选一或组合：不编译（稳但慢）/ 每 shape 特化（平均快但编译风暴打爆 P99）/ 分桶。
分桶的桶数是 U 形曲线，最优点在中间。**桶边界要等比排布而不是等频**——
因为 padding 浪费是相对量，按流量直方图切等频桶反而更差（demo5 有实测）。
再进一步是分层编译：先用动态版本顶上，后台异步编译特化版本，编译好了再切。

### 网络方向

**Q：优先级队列为什么救不了 RPC 的尾延迟？**
A：因为包一旦开始发送就**不可抢占**（store-and-forward）。优先级只能决定"下一个发谁"，
决定不了"打断正在发的那个"。低利用率下队列里通常只有一个大包，根本没有"下一个"可选，
所以改善接近 0%。**尾延迟的下界 = 最大不可抢占单元的传输时间**，
想降它就得缩小这个单元——也就是分片。

**Q：利用率高是不是尾延迟就一定差？**
A：不一定。demo 里周期性流量推到 93% 利用率，P999 纹丝不动（D/D/1，队列不堆积）；
而同样平均利用率的泊松流量，P999 显著恶化。**决定尾延迟的是突发性，不是平均利用率。**
这恰好解释了为什么"弹性调度把在线集群空闲卡分给训练"更难——它引入的不只是更高利用率，
更是多个互不协调任务带来的突发性。

**Q：Ring 和 Tree 怎么选？**
A：Ring 带宽最优（单卡传输量趋近 2D，与卡数无关）但延迟项随 N 线性增长；
Tree 延迟最优（2log₂N 轮）但每步传完整 D，带宽项随 log N 增长。
所以大数据量用 Ring、小数据量用 Tree，NCCL 会自动选。
另外递归折半（HD）在理想模型里两项都最优，工业上仍多用 Ring，
是因为 HD 要求卡数为 2 的幂、且通信对端跨拓扑层级，而 Ring 只和相邻节点通信、对物理拓扑更友好。

**Q：千卡后通信效率为什么变低？**
A：Ring 的延迟项 ∝ 2(N-1)×单跳延迟，1024 卡就是 2046 轮。demo 里 4096 卡时
带宽项占比降到 80% 以下——有 20% 时间纯耗在轮次累积上。解法是分层 AllReduce：
机内先 reduce-scatter，机间只搬 D/8，最后机内 all-gather。

**Q：incast 是什么？加大缓冲能解决吗？**
A：N 个分片的响应几乎同时回到同一个网口，瞬时突发压垮出端口缓冲，丢包，触发 RTO（~200ms）。
关键量级对比：正常传输是微秒级，丢包恢复是毫秒级，差 2~3 个数量级。
加大缓冲**不能解决**——demo 里缓冲加大 4x 后 P50 从 200ms 变成 0.72ms，但 P99 仍然是 200ms，
只是把"每次都炸"变成"偶尔炸"，而且抬高了排队延迟（bufferbloat）。
有效的是**在源头限制并发扇出**。一般原则：突发问题要在源头解决，在下游用缓冲接是接不住的。

**Q：扇出对尾延迟的影响？**
A：请求延迟 = max(N 个分片)。单分片 p99=1% 时，扇出 100 就有 63% 的请求踩到至少一个慢分片。
**所以高扇出系统里，单分片的 p99 比平均值重要得多。**
最便宜的对策是对冲请求：等到 p95 还没回来就再发一份给副本，多打 5% 负载换来尾延迟大幅下降。
前提是请求幂等，且系统有余量（否则会正反馈雪崩，所以要给对冲加全局速率上限）。

### 跨方向的"大题"

**Q：如果让你从这三个方向里挑一个做，你挑哪个？**
A：先算账，再回答。用 `04/demo1` 的框架：给定场景（卡数、batch、模型形态），
三段各占多少？占比最大的那段收益最高。并且要说明**瓶颈会迁移**：
小规模优化计算、大规模优化通信；batch 大计算主导、batch 小搬运主导。
不给场景就说"我要做 X"，说明没有系统 sense。

**Q：这三个方向共同的难点是什么？**
A：**信息断层**。应用层知道自己是什么负载（这是延迟敏感的 RPC / 这是可以慢的大流 /
这条序列有多长），但这个信息传不到下层；下层看到了拥塞、碎片、抖动，
也没法反馈给上层去调整策略。表格里"跨层协同的标准化信令体系"就是在说这件事，
它是当前所有局部优化的天花板。

## 五、最后一条建议

这份材料里所有的数字都可以过时，但有三样东西不会：

1. **量级直觉**（延迟阶梯、带宽阶梯、脊点）；
2. **先测量后优化的纪律**（木桶效应是可量化的）；
3. **对平均值的警惕**（方差和尾部才是系统的真实成本）。

把这三样带走，其余的都可以现学。
