# demo2 · 算子融合：向量化之后的下一道墙

> 手写分块融合比不融合还慢 —— 因为"块要小到进 cache"和"块要大到摊薄解释器开销"直接冲突。

---

## 一、真实场景：这段代码对应线上的什么

推荐模型里有**大量**这种形态的算子：

```python
# 特征归一化
x = (x - mean) / std
# 多路 embedding 融合
e = e_user * w1 + e_item * w2 + e_ctx * w3
# 门控
h = sigmoid(g) * h1 + (1 - sigmoid(g)) * h2
# 各种业务加权
score = relu(a * b + c) * boost
```

它们的共同点：**算术量极小，访存量极大**。每个元素只做一两次乘加，
却要从内存读进来、写回去好几趟。

在 PyTorch/numpy 这类**逐算子执行**的框架里，`relu(a*b+c)*s` 会变成 4 个独立的 kernel，
每个 kernel 都是"把整个数组从内存读出来 → 算一下 → 写回内存"。
中间结果全都在内存里绕了一圈。

**融合**就是把这 4 个 kernel 合成 1 个：数据只过一遍内存，中间值留在寄存器里。
算术量完全没变，访存量减半以上。

对应表格里："融合传统编译器（LLVM、GCC）与深度学习编译器（TVM 等）的优势，
覆盖「纯业务逻辑 Python 代码」与「深度学习相关 Python 代码」的全场景优化"。

## 二、这个 demo 具体干了什么（流程）

### 任务：`d = relu(a*b + c) * s`

### 三种实现

```python
unfused(a,b,c,s):                       # 逐算子，每步产生全尺寸临时数组
    t1 = a * b        # 读 a,b  写 t1
    t2 = t1 + c       # 读 t1,c 写 t2
    t3 = maximum(t2,0)# 读 t2   写 t3
    return t3 * s     # 读 t3   写 out
                      # 共 8 趟全数组访存

fused_numpy(a,b,c,s):                   # numpy 能做到的最好
    out = empty_like(a)
    multiply(a,b,out=out); add(out,c,out=out)
    maximum(out,0,out=out); multiply(out,s,out=out)
                      # 少了临时数组，但**仍然是 4 趟独立遍历**
                      # numpy 的每个 ufunc 都是独立 kernel —— 这是它的架构上限

fused_blocked(a,b,c,s,block):           # 手工分块"融合"
    for i in range(0, n, block):
        在一个小块上把 4 步全做完      # 理论上中间结果留在 cache 里
```

### 实验 1：规模扫描

在 100K / 1M / 8M / 32M 四个规模上跑三种实现，看工作集超出 cache 后会发生什么。
`assert np.allclose(...)` 保证三者结果一致。

### 实验 2：块大小扫描（本 demo 的核心）

固定 N=8M，把 block 从 1024 扫到 N，同时标出"这个块能不能进 cache"。
**这张表是用来解释实验 1 那个反常结果的。**

### 实验 3：访存量分析

用纯算术算出每种实现的 kernel 数、内存遍历趟数、访存字节、算术强度。

### 实验 4：交给真正的编译器

## 三、涉及的机制

### 访存趟数的账

| 实现 | kernel 数 | 全数组遍历趟数 | 明细 |
|---|---|---|---|
| 未融合 | 4 | **8** | 读a读b写t1 \| 读t1读c写t2 \| 读t2写t3 \| 读t3写out |
| numpy `out=` | 4 | **7** | 省掉一次临时数组分配，但趟数没少 |
| 真正融合 | 1 | **4** | 读a读b读c写out（理论下限） |

**理论加速上限 = 8/4 = 2x。** 注意这是**下界**：真实的 `torch.compile` 有时超过 2x，
因为它还顺带消掉了算子分发、临时张量分配等框架开销。

### 算术强度与 roofline

```
算术强度 = FLOP / 访存字节
未融合：  3N FLOP / 32N Byte = 0.09 F/B
融合后：  3N FLOP / 16N Byte = 0.19 F/B
```

而机器的脊点在 **300 F/B** 量级。两者都远小于 1，**彻底 memory-bound**。

> 这意味着：**换更强的算力芯片一点用都没有，只有减少访存才有用。**
> 这就是为什么深度学习编译器的头号优化永远是算子融合。

### 为什么手写分块融合会失败（本 demo 最重要的一点）

分块融合要求块**小到能进 cache**（否则中间结果还是要落内存，融合就白做了）。
但在 Python 里，每处理一个块要发 **5 次 numpy 调用**，每次调用有 1~2µs 的解释器开销。

于是出现了**直接冲突的两个要求**：

```
块要小  →  才能进 L1/L2，融合才有意义
块要大  →  才能摊薄每块 5 次调用的解释器开销
```

块大小扫描那张表把这个冲突量化了：块小的时候被调用开销压垮，块大的时候进不了 cache。
**两头都不讨好，所以整条曲线上没有一个点能赢过不融合。**

> **结论：在 Python 层根本无法表达有效的算子融合。**
> 融合必须发生在**编译产物内部** —— 生成的机器码里是一个真正的融合循环，
> 每个元素只付一次循环开销，而不是每块付 5 次解释器调用。

## 四、方案对比

| 方案 | 访存趟数 | 实测 | 为什么 |
|---|---|---|---|
| 逐算子（未融合） | 8 | 基线 | 每个算子一次完整内存往返 |
| numpy `out=` | 7 | 略好或持平 | 只省了分配，趟数几乎没变 |
| 手写 Python 分块 | 理论 4 | **比基线还慢** | 解释器调用开销吃掉全部收益 |
| `torch.compile` | 4 | **~2.3x** | 生成真正的融合 kernel，每元素只付一次循环开销 |
| 手写 C++/CUDA kernel | 4 | ≈ 编译器 | 效果一样，但成本高、不可维护、破坏 Python 体系 |

**这张表就是编译方向存在的全部理由**：融合的收益是真的（2x），
但拿到它的唯一可行路径是**自动编译**，不是手写。

## 五、怎么读输出

### 规模扫描

```
      规模     工作集      未融合   numpy out=    分块融合    融合加速
     8.0M     128MB     10.09ms     9.51ms     12.87ms      0.78x
```

**融合加速 < 1**，也就是分块融合比不融合还慢。访存量明明少了一半，为什么反而更慢？
下面这张表给答案。

### 块大小扫描（解释上面那个反常）

```
     块大小    块工作集      块数      耗时   vs未融合   能否进cache
      1,024      16KB     7,813   19.65ms     0.51x   L1/L2 ✓
      8,192     128KB       977   13.20ms     0.76x   L1/L2 ✓
     65,536    1024KB       123   12.55ms     0.80x   L3 ~
  1,048,576   16384KB         8   12.66ms     0.79x   L3 ~
  8,000,000  125000KB         1   12.83ms     0.78x   不进 ✗
```

- 块 = 1024 时能完美进 L1，但要发 7813×5 ≈ 4 万次 numpy 调用 → 被调用开销压垮（0.51x）
- 块 = 8M 时只有 1 次调用，但工作集 125MB 进不了任何 cache → 融合失效（0.78x）
- **中间任何一个点都赢不了不融合**

### 访存量分析

```
  实现          kernel数   内存遍历   访存字节    算术强度
  未融合             4        8       256MB     0.09 F/B
  numpy out=         4        7       224MB     0.11 F/B
  分块融合           1        4       128MB     0.19 F/B
```

理论上融合能把访存从 8 趟降到 4 趟（2x），前提是**能真正生成融合 kernel**。

### torch.compile

```
  torch eager    :     1.66 ms  (逐算子)
  torch.compile  :     0.73 ms  (2.28x)
```

**2.28x 超过了纯访存分析给出的 2x 上限。** 说明 eager 基线里除了访存，
还有算子分发、临时张量分配等开销，也一并被编译消掉了 ——
这正是"访存模型只是下界，真实收益还包含框架开销"的体现。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `N_MAIN` | 8M → 1M | 工作集降到 16MB，可能进 L3，分块融合的劣势缩小 | 融合的收益**取决于工作集和 cache 的相对大小**，不是绝对的 |
| `N_MAIN` | 8M → 32M | 更彻底的 memory-bound，几种写法差距被访存拉平 | 数据越大，越只剩带宽说了算 |
| `USE_TORCH` | 关掉 | 跳过 torch.compile（省 10 秒） | 只想看前面几节时用 |
| `REPEAT` | 5 → 15 | 数字更稳 | 这个 demo 的差异只有 20~30%，噪声容易盖过信号 |

## 七、对推荐场景的特殊意义

1. **融合的目标算子很多**：特征归一化、多路 embedding 相加、门控、各种业务加权，
   全是算术量小访存量大的逐元素算子 —— 全是融合的目标。
2. **不定长数据让融合更难**：静态 shape 的融合策略在变长序列上会失效
   （见 `01/demo4` 和 `02/demo5`）。这是推荐比 LLM 更难的地方。
3. **融合边界本身是个优化问题**：融太少省不下访存，融太多则寄存器不够用导致 spill
   （中间值被踢回内存，融合白做）。自动搜索这个边界（auto-scheduling）是 TVM/Ansor 的核心贡献。
