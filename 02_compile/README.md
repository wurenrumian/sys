# 02 · 基础库团队 - 编译方向

> 表格原文（节选）：
> (1) 搜广推系统在离线批处理、在线特征计算、模型训练胶水层、推理链路业务编排、大模型 serving
> 轻量化调用、业务数据结构与张量的异构转换、多模型结果融合等**全链路环节都有 Python 代码参与**……
> 现有优化手段要么是局部手写 C++（成本高、破坏 Python 研发体系），要么是单一编译工具的碎片化优化。
> (2) 百亿/千亿参数推荐大模型的 Serving 面临资源瓶颈，CPU&GPU 异构架构下资源协同与调度问题显著，
> 显存碎片、动态批处理、细粒度资源隔离都是难点。
>
> 探索方向：差异化编译策略（离线重吞吐/在线重延迟）、LLVM+TVM 融合、增量编译与热更新、
> 轻量化编译产物部署、显存碎片清理与复用、动态批处理阈值自适应、细粒度资源隔离。

## 一、这个课题的真正含义

它**不是**"把 Python 换成 C++"。表格里明确说了要保住 Python 研发体系。真正的问题是：

> 推荐系统的算法同学用 Python 表达业务逻辑，这个表达是对的、必须保留；
> 但 CPython 的执行方式（逐条字节码解释 + 每个对象都是堆上的 PyObject）
> 让这份表达的执行效率损失了 1~2 个数量级。**编译方向要在不改变表达的前提下换掉执行方式。**

这和 LLM 那边的 `torch.compile` 是同一个母题，但推荐场景多了两个约束：
**(a) 高频迭代**（所以要增量编译/热更新，不能每次全量编译几分钟）、
**(b) 不定长稀疏数据**（所以静态 shape 的编译假设直接失效）。

## 二、demo1：Python 解释器开销到底有多大

```bash
python3 demo1_python_overhead.py
```

测同一个推荐场景的特征交叉计算，五种写法逐级递进：纯 Python 循环 → 列表推导 →
numpy 向量化 → 消除临时数组 → torch（可选）。会打印每一级的加速比和"每元素纳秒数"。

**要点**

- 纯 Python 每次 `a[i] * b[i]` 都要：解释字节码、装箱/拆箱 PyObject、做动态类型分派、
  可能触发引用计数。真正的乘法只占其中极小一部分 —— 这就是**解释开销**。
- 向量化的本质是**把循环下沉到编译过的代码里**，一次分派处理一整个数组。
  编译方向要做的事，是让你**不用手写向量化**也能得到这个效果。
- 你会看到向量化之后瓶颈从"解释器"变成了"内存带宽" —— 这就引出了 demo2。

## 三、demo2：算子融合 —— 向量化之后的下一道墙

```bash
python3 demo2_operator_fusion.py
```

**要点**

- `d = (a + b) * c` 用 numpy 写，会生成 2 个 kernel、3 次全数组读、2 次全数组写，
  中间还有一个和输入等大的临时数组。当数据超过 L2/L3 cache，**这些访存就是全部成本**。
- 融合成一个 kernel 后：1 次遍历、0 个临时数组。算术量完全没变，但访存量减半以上。
- demo 会算出每种写法的**算术强度**（FLOP / 访存字节）并对照实测带宽，
  让你看到"这段代码是 memory-bound 还是 compute-bound" —— 这是所有编译优化的第一个判断。
- 这正是 TVM/XLA/`torch.compile` 的核心价值，也是表格里"融合传统编译器（LLVM/GCC）
  与深度学习编译器（TVM）优势"这句话的落点。

## 四、demo3：显存碎片 —— 为什么显存"够"却 OOM

```bash
python3 demo3_gpu_mem_frag.py
```

**要点**

- 表格原文："设计显存碎片实时清理与内存复用策略，减少推荐大模型推理过程中的显存碎片"。
- 推荐场景的请求是**不定长**的（用户序列长短不一），所以每次分配的 block 大小都不同，
  这是产生外部碎片的最佳温床 —— LLM 场景里定长 batch 反而没这么严重。
- demo 对比四种分配器：**First-Fit / Best-Fit / Buddy / 分页（PagedAttention 思路）**，
  在同一段不定长分配序列上比较：碎片率、OOM 次数、有效利用率。
- 结论会很明确：前三种都在跟"外部碎片"搏斗，而**分页把外部碎片直接消灭**
  （代价是引入少量内部碎片和一层间接寻址）—— 这就是 vLLM 的 PagedAttention
  为什么是范式级改进，以及为什么推荐场景更需要它。

## 五、demo4：动态批处理 —— 吞吐与 P99 的取舍

```bash
python3 demo4_dynamic_batch.py
```

**要点**

- 表格原文："构建基于推荐请求特征（如用户活跃度、请求峰值）的动态批处理阈值自适应模型，
  实时调整批处理尺寸"。
- 攒批（batching）是提升 GPU 利用率的第一手段，但攒批要等，**等就是延迟**。
  固定批大小在流量低谷时会把请求饿死在队列里，在高峰时又会让批太大撑爆 P99。
- demo 用排队模型模拟三种策略：**固定批 / 固定超时 / 自适应（按队列积压动态调整）**，
  在正弦波动 + 突发尖峰的流量下，对比吞吐、P50、P99、P999 和 GPU 利用率。
- 你会看到自适应策略在**两端都不吃亏**，这就是那条课题的价值所在。

## 六、demo5：动态 shape —— 编译收益为什么拿不到手

```bash
python3 demo5_dynamic_shape.py
```

前四个 demo 讲的都是"编译能带来多少收益"。这一个讲**收益为什么拿不到**。

**要点**

- 编译加速的前提是能为具体 shape 生成特化代码（循环边界是常数、能展开、能选最优 tile）。
  但在线推理请求的序列长度千变万化，每来一个新长度就是一个新 shape，
  就要重新编译一次，一次几百毫秒。
- demo 对比：不编译（解释执行）/ 每 shape 特化 / 只编译一份动态 shape 版本 / 分桶 padding。
- **第一个反直觉**：每 shape 特化的**平均**延迟很漂亮，但 P99 是 401ms——
  比不编译还差 20 倍。缓存命中率 97% 听起来很高，可 **SLA 是按 P99 签的，不是按命中率**。
  编译开销不会消失，它只是全部集中到了尾延迟里。
- **第二个反直觉**：分桶用 41% 的确定性算力浪费，换掉了 400ms 的不确定抖动。
  "用一点确定的浪费换掉一大堆不确定的抖动"——这是系统设计里反复出现的模式。
- **第三个反直觉**：按流量分布切**等频**桶听起来明显更聪明，实测却差 4 倍。
  因为 padding 浪费是**相对量**（把 10 补到 20、把 500 补到 1000 都是白烧一倍），
  桶必须**等比**排布。2 的幂分桶就是等比的特例，所以老经验表现接近最优。
  一般结论：分桶要按**算力分布**优化，而不是按**请求数分布**。
- 最后两节对应表格里的"增量编译与热更新"：推荐模型天天上线，每次上线编译缓存整体失效。
  demo 扫描了上线频率对延迟的影响，并演示了**异步编译**（先用动态版本顶着，
  后台编译特化版本，好了再切）如何同时拿到两者的好处。

**和 `01/demo4` 的张力**：Jagged 消灭 padding 却消灭了静态 shape；分桶保住了静态 shape
却引入 padding。这两个解法互相拉扯，正是推荐场景不能照搬 LLM（定长 batch + 静态图）的原因。

## 七、可以往下挖的研究点

| 表格里的方向 | 真正的难点 | 切口 |
|---|---|---|
| 差异化编译策略 | 离线要吞吐/在线要延迟，同一份代码两套目标 | 同一 IR 出两套 codegen；PGO（用线上 profile 反馈指导编译） |
| 增量编译 + 热更新 | 推荐策略天天改，全量编译等不起 | 函数级编译缓存 + 稳定 ABI 边界；类似 JIT 的分层编译（先解释后优化） |
| 不定长数据的编译 | 静态 shape 假设失效，padding 浪费巨大 | Jagged Tensor 的 padding-free codegen（和 TikTok 那条课题是同一个） |
| 轻量化产物部署 | 解耦 Python 运行时依赖 | AOT 编译成 .so + 稳定 C ABI；参考 PyTorch AOTInductor |
| 显存碎片 | 不定长分配 | 分页 + 前缀共享（多刷之间的 KV Cache 复用，见电商推荐那条） |
| 异构调度 | CPU 侧能力被浪费 | CPU 做稀疏 lookup/序列预处理，GPU 专注稠密算力；关键是流水线重叠 |
