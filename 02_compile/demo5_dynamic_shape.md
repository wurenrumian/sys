# demo5 · 动态 shape：编译收益为什么拿不到手

> 编译缓存命中率 97% 听起来很好，但 P99 是 401ms —— **SLA 是按 P99 签的，不是按命中率**。

---

## 一、真实场景：这段代码对应线上的什么

前四个 demo 讲的都是"编译能带来多少收益"。这一个讲**收益为什么拿不到**。

编译加速的前提是能为**具体的 shape** 生成特化代码：

```c
// 静态 shape：循环边界是常数
for (int i = 0; i < 128; i++)   // 可以展开、可以向量化、可以选最优 tile 大小

// 动态 shape：边界是变量
for (int i = 0; i < n; i++)     // 展开不了、tile 大小只能保守、要处理尾部余数
```

但在线推理请求的序列长度**千变万化**：

```
请求 1：seq_len = 23    →  新 shape，编译 400ms
请求 2：seq_len = 156   →  新 shape，编译 400ms
请求 3：seq_len = 23    →  缓存命中，0.09ms
请求 4：seq_len = 891   →  新 shape，编译 400ms
...
```

而且推荐模型**天天上线**（一天几次），每次上线编译缓存整体失效。
编译器的假设是"编译一次跑很久"，推荐系统的现实是"跑一会儿就换一版"。**两者直接冲突。**

对应表格里："增量编译与热更新机制，避免全量编译带来的高时间成本" /
"差异化编译策略（离线重吞吐、在线重延迟）" / "轻量化编译产物部署"。

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造请求长度分布

```python
lens = clip(lognormal(3.2, SIGMA), 1, MAX_LEN)     # 默认出现 511 种不同长度
```

关键数字：**20000 个请求里出现了 511 种不同的长度**。每一种都是一个新 shape。

### 第 2 步：成本模型

```python
COMPILE_MS   = 400      # 编译一个新 shape 的耗时（同步阻塞那个倒霉请求）
MS_INTERP    = 0.020    # 未编译时，每个元素的耗时
MS_COMPILED  = 0.004    # 特化编译后，每个元素的耗时     （5x 加速）
DYN_PENALTY  = 1.5      # 动态 shape 编译版相对特化版的减速
```

### 第 3 步：四种策略，逐请求模拟

```python
'interp'  : 不编译，直接解释执行            lat = 0.020 × L
'exact'   : 每个出现过的 shape 特化编译     首次付 400ms，之后 0.004 × L
'dynamic' : 只编译一份支持任意长度的版本    只付一次 400ms，之后 0.006 × L
'bucket'  : 向上取整到桶边界再编译          首次付 400ms/桶，之后 0.004 × 桶长（含 padding 浪费）
```

**关键建模点**：编译是**同步阻塞**的 —— 触发编译的那个请求要等编译完才能返回。
这就是编译开销跑到尾延迟里去的机制。

### 第 4 步：三种分桶方案对比

| 方案 | 边界怎么定 |
|---|---|
| `buckets_pow2` | 1, 2, 4, 8, ..., MAX_LEN（2 的幂） |
| `buckets_geometric(k)` | 等比数列，公比 `MAX_LEN^(1/k)`，桶数可调 |
| `buckets_quantile(lens, k)` | 按**实际流量分布**的分位数切，每桶请求数大致相等 |

### 第 5 步：热更新扫描

`RELOAD_EVERY` 步清空编译缓存，模拟模型上线。

### 第 6 步：异步编译

```python
async_lat = np.minimum(r_dyn['lat'], r_bucket['lat'])
```

模拟"编译好之前走动态版本，编译好之后走特化版本"，取两者较快的。

## 三、涉及的机制

### 形状特化（shape specialization）

编译器为具体 shape 生成代码，能做的优化：循环展开、向量化（知道能整除）、
选最优 tile 大小、常量折叠索引计算、静态分配寄存器。这些在动态边界下都要打折。

### 编译缓存与命中率的陷阱

```
命中率 = 1 - 编译次数 / 请求数 = 1 - 511/20000 = 97.45%
```

这个数字看着很漂亮。但那 511 次未命中，**每次要付 400ms 的同步阻塞**。
平均下来只有 10.4ms（被 97% 的快请求摊薄了），但 P99 是 **401ms**。

> **编译开销不会消失，它只是从平均值里搬到了尾延迟里。**
> 只看平均值的监控完全看不到这个问题。

### 为什么分桶的桶边界必须"等比"而不是"等频"

padding 浪费是**相对量**：

```
把长度 10 补到 20    →  浪费 1 倍算力
把长度 500 补到 1000 →  浪费 1 倍算力
```

要让**最坏相对浪费**在所有桶上一致，桶边界就必须**等比排布**（每桶上界 = 下界 × 常数 r）。

而按流量直方图切等频桶，会把桶全堆在请求密集的短序列区，长尾区只剩一两个巨宽的桶 ——
于是一个长度 400 的请求被补到 1024。**而恰恰是长序列贡献了绝大部分算力。**

> **一般结论：分桶要按「算力分布」优化，而不是按「请求数分布」。**
> 这提醒我们："自适应"不等于"照着直方图切"，**目标函数得先写对**。

## 四、方案对比

| 策略 | 编译次数 | 平均延迟 | 尾延迟 | 算力浪费 | 什么时候用 |
|---|---|---|---|---|---|
| **不编译** | 0 | 差（5x 慢） | **稳定** | 0 | 流量极低、或 shape 完全无规律 |
| **每 shape 特化** | 511 | 看着好 | **灾难（401ms）** | 0 | 离线批处理（没有延迟要求，编译一次跑很多轮） |
| **动态 shape 编译** | 1 | 较好 | **稳定** | 0 | 作为兜底/首选的保守方案 |
| **分桶 padding** | 8~16 | **最好** | 好 | 20~50%（可调） | **在线服务的默认选择** |
| **异步编译（分层）** | 同分桶 | 最好 | **最好** | 同分桶 | 生产环境的完全体，代价是要维护两套产物 |

## 五、怎么读输出

### 主表

```
策略                    平均      P50      P99     P999   编译次数  算力浪费
不编译(解释执行)       0.98ms   0.48ms    7.8ms   19.4ms       0      0.0%
每 shape 特化编译     10.42ms   0.10ms  401.2ms  403.0ms     511      0.0%
动态 shape 编译一次    0.32ms   0.14ms    2.4ms    5.8ms       1      0.0%
2的幂分桶(11 个桶)     0.50ms   0.13ms    2.0ms    4.1ms      11     41.4%
```

- 每 shape 特化的 **P50 是 0.10ms**（最快），**P99 是 401ms**（最慢）。
  同一个策略在两个分位上分列第一和倒数第一 —— 这就是尾延迟问题的典型长相。
- 分桶用 41.4% 的**确定性算力浪费**，换掉了 400ms 的**不确定抖动**。
  「用一点确定的浪费换掉一大堆不确定的抖动」—— 这是系统设计里反复出现的模式
  （另见 `02/demo3` 的分页、`03/demo1` 的分片）。

### 桶数扫描（U 形曲线）

```
  几何分桶 k=2  (实2桶)    1.77ms    编译2次     浪费 780.9%
  几何分桶 k=8  (实8桶)    0.47ms    编译8次     浪费  55.6%    ← 最优点
  几何分桶 k=32 (实29桶)   0.80ms    编译29次    浪费  10.2%    ← P999 开始变 400ms
  几何分桶 k=64 (实52桶)   1.25ms    编译52次    浪费   4.6%
```

两端各有一个失效原因：**桶太少 → padding 浪费主导；桶太多 → 编译次数主导。**

### 等比 vs 等频

```
  几何分桶 k=16 (16桶)   浪费  23.0%
  分位数分桶 k=16 (16桶) 浪费 103.2%     ← 同样 16 个桶，差 4 倍
```

"按流量分布切"这个听起来更聪明的做法，实测差 4 倍。原因见上面的机制部分。
（顺带说明：2 的幂分桶就是等比的特例，所以老经验表现接近最优。）

### 热更新扫描

```
  上线频率            平均      P99     P999   编译次数   编译总耗时
  不更新(理想)      0.50ms    2.0ms    4.1ms        11       4.4s
  每 2000 请求一次  2.48ms    2.0ms  401.0ms       110      44.0s
  每 100 请求一次  39.98ms  402.0ms  404.1ms     1,985     794.0s
```

上线越频繁，编译成本被摊薄的机会越少，最后编译时间反而成了主要成本。
**这就是"增量编译与热更新"这条课题的由来。**

### 异步编译

```
  同步编译 + 分桶      0.50ms   2.00ms   4.06ms
  动态 shape 兜底      0.32ms   2.40ms   5.76ms
  异步编译(两者取快)   0.28ms   1.68ms   3.44ms      ← 两边的好处都拿到了
```

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `RELOAD_EVERY` | 0 → 500 | 分桶策略的 P99 也开始出现 400ms | 热更新会把**任何**编译策略的优势吃掉。这是推荐场景特有的约束 |
| `COMPILE_MS` | 400 → 20 | 每 shape 特化突然变成最优 | 结论完全取决于**编译成本与执行成本的比值**。编译快了就该多特化 |
| `SIGMA` | 1.2 → 0.4 | 不同 shape 数大幅减少，每 shape 特化变得可行 | 长尾是问题的根源。shape 分布集中时这个问题不存在 |
| `N_REQ` | 20000 → 200000 | 每 shape 特化的平均延迟大幅改善（编译被摊薄），**P99 依然 401ms** | 摊薄能救平均值，**永远救不了尾延迟** |

**建议做最后一个实验**：请求数翻十倍，看着平均延迟变好而 P99 纹丝不动。
这是理解"尾延迟为什么是独立问题"最直观的一课。

## 七、可行的工程方向

1. **编译产物持久化 + 跨实例共享**：一台机器编译，全集群复用。
   对"热更新导致缓存失效"最直接的解药。
2. **函数级缓存 + 稳定 ABI**：只有改动的子图重新编译，而不是整个模型。
   这就是"增量编译"的技术含义。
3. **分层编译（像 JIT 那样）**：先用解释/动态版本顶上，后台异步编译特化版本，
   编好了再切过去 —— 于是编译**再也不会阻塞任何一个请求**。demo 最后一节模拟的就是这个。
4. **按线上 shape 分布自适应选桶**：而不是拍脑袋定 2 的幂。
   但要按算力分布优化，别照着请求数直方图切。

## 八、和 `01/demo4` 的张力（重要）

- `01/demo4` 说：Jagged 消灭 padding，是不定长数据的正解。
- 本 demo 说：分桶 padding 保住静态 shape，是编译的正解。

**这两个解法互相冲突**：Jagged 消灭了 padding，却也消灭了静态 shape，编译器更难特化；
分桶保住了静态 shape，却引入了 padding 浪费。

> 这个张力是推荐系统 infra 最核心的难题之一，也是为什么不能把 LLM 那套
> （定长 batch + 静态图）直接搬过来。谁能同时拿到两边的好处，谁就解决了一个真问题。
