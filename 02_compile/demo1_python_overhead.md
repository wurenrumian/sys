# demo1 · Python 解释器开销到底有多大

> 向量化能拿回 50 倍。但两种"看起来更优"的手工优化，实测分别慢了 2.5x 和 7.7x。

---

## 一、真实场景：这段代码对应线上的什么

表格原文点名了推荐系统里 Python 参与的**全链路环节**：

```
离线批处理  →  在线实时特征计算  →  模型训练的胶水层  →  推理链路的业务编排
→  大模型 serving 的轻量化调用  →  业务数据结构与张量的异构转换  →  多模型结果融合
```

也就是说，Python 不是只在"写模型"的时候出现，它在**每一段的接缝处**都出现。
而接缝处的代码往往是这种形态：

```python
for i in range(len(user_emb)):
    v = user_emb[i] * item_emb[i]
    if v > threshold:          # 一条业务规则
        v = v * weight[i]
    score += v
```

一个算法同学写出这样的代码，逻辑是**对的**、可读性是**好的**、迭代速度是**快的**。
问题只有一个：它比等价的机器码慢 1~2 个数量级。

**编译方向的目标不是让人别这么写，而是让这么写也能跑得快。**
表格里说得很清楚：现有手段要么局部手写 C++（成本高、破坏 Python 研发体系），
要么是单一编译工具的碎片化优化。

## 二、这个 demo 具体干了什么（流程）

### 任务定义

对 N 个元素做：`score = Σ (a[i]*b[i] 若 ≤0.5，否则 a[i]*b[i]*c[i])`。
就是上面那段推荐特征交叉，**刻意保留了一个业务分支**（真实业务代码里到处是 if）。

### 五种写法，逐级递进

| 写法 | 做法 | 想验证什么 |
|---|---|---|
| `v1_pure_python` | 纯 for 循环，操作 Python list | 解释开销的基线 |
| `v2_listcomp` | 列表推导 + `sum` + `zip` | 少了一些字节码，但每元素仍是 PyObject |
| `v3_numpy_naive` | `np.where(v>0.5, v*c, v).sum()` | 循环下沉到 C，但有多个临时数组 |
| `v4_numpy_out` | 全程 `out=` 写进预分配缓冲，**零新分配** | "减少分配"到底值不值 |
| `v4b_numpy_mask` | 布尔掩码 `v[mask] *= c[mask]`，**只算需要的部分** | "减少算术量"到底值不值 |
| `v5_torch` | torch 张量（可选） | 另一套 kernel + 多线程 |

### 测量方法

```python
def bench(fn, *args, repeat):
    best = min(多次运行的耗时)      # 取最小值，不是平均值
```

**为什么取最小值**：最小值排除了调度抖动、其他进程干扰、cache 冷启动，
最接近"这段代码本身要花多久"。平均值会被偶发的系统噪声污染。

纯 Python 太慢，所以只跑 `SUB`（默认 20 万）个元素再**线性外推**到 N。
外推是合理的，因为纯 Python 循环没有任何规模效应（每元素成本恒定）。

### 一致性校验

```python
spread = (max(vals) - min(vals)) / mean(vals)     # 应 < 1e-2
```

确认六种写法算的是同一个东西 —— 否则性能对比毫无意义。

### 最后两节分析

- **解释开销拆解**：说明纯 Python 每元素到底在干什么
- **带宽分析**：算出向量化之后的实测带宽和算术强度，引出 demo2

## 三、涉及的机制

### 纯 Python 每个元素要做的四件事

```python
v = a[i] * b[i]
```

1. **取指/译码**：解释器逐条执行字节码（`BINARY_SUBSCR`、`BINARY_MULTIPLY`…），
   每条都要一次 switch 分派 + 栈操作
2. **装箱/拆箱**：`a[i]` 返回的是堆上的 `PyFloatObject`（一个带引用计数和类型指针的对象），
   不是寄存器里的 float。要取出来算完再包回去
3. **动态分派**：每次乘法都要查类型，决定调哪个 `__mul__`
4. **引用计数**：每个中间对象的生死都要维护 refcount，还可能触发 GC

**真正的浮点乘法只占其中不到 1%。**

### 向量化的本质

不是"numpy 的乘法更快"，而是**把循环下沉到编译过的代码里**：
一次类型分派处理整个数组，把上面 1~4 摊薄到接近 0。

**编译方向要做的事，就是让你不用手写向量化也能得到这个效果。**

### 新瓶颈：内存带宽

向量化之后，解释开销没了，暴露出来的是访存：

```
算术强度 = FLOP / 访存字节
```

demo 算出来约 **0.11 FLOP/Byte**。而 H100 这类硬件的"脊点"（峰值算力/峰值带宽）在
**300 FLOP/Byte** 量级。差了三个数量级 —— 这是**彻底的 memory-bound**。

结论：**加再多算力也没用，唯一的出路是减少访存次数。** 这就引出了 demo2 的算子融合。

## 四、方案对比

| 写法 | 相对加速 | 为什么是这个结果 |
|---|---|---|
| 纯 Python 循环 | 1x | 解释开销吃掉一切 |
| 列表推导 | ~2x | 少了几条字节码，但 PyObject 的账一分没省 |
| **numpy 向量化** | **~53x** | 循环下沉到 C；瓶颈从解释器变成访存 |
| numpy `out=`（零分配） | ~21x（**比朴素慢 2.5x**） | 见下 |
| numpy 布尔掩码 | ~7x（**比朴素慢 7.7x**） | 见下 |
| torch | ~50x | 同量级；多线程收益被 memory-bound 抵消 |

### 为什么两种"优化"反而更慢

**`out=` 版**：在这个尺寸下**分配根本不是瓶颈** —— numpy 有 allocator 缓存，
反复分配同样大小的数组几乎零成本。而为了避免临时数组用的
`np.copyto(dst, src, where=mask)` 引入了逐元素的条件判定，比 `np.where` 生成新数组还慢。

**布尔掩码版**：`v[mask] *= c[mask]` 看起来"只算需要的部分"，实际触发了
**gather/scatter**（按索引跳着读写）。不连续访存意味着：cache line 利用率暴跌、
硬件预取器失效、无法向量化。**省下的那点算术量，远远抵不上访存代价。**

> **这是本 demo 最值钱的一条**：靠人肉猜"哪种写法更快"的成功率并不高。
> 因为程序员的心智模型（"少分配就快"、"少算就快"）跟不上
> cache / 预取 / 向量化 / 分配器的真实行为。**必须实测。**

## 五、怎么读输出

```
写法                        耗时(ms)     加速比    ns/元素   备注
纯 Python 循环                  78.5        1x       39.3   (实测 200,000 元素后线性外推)
列表推导 + sum                  43.5        2x       21.8   (同上外推)
numpy 向量化                     1.5       53x        0.7
numpy out=(零分配)               3.7       21x        1.9
numpy 布尔掩码                  11.2        7x        5.6   <- 陷阱
torch 向量化                     1.6       50x        0.8
```

**`ns/元素` 这一列最有信息量**：纯 Python 每个元素 39 纳秒 ≈ 现代 CPU 的 100 多个时钟周期，
而一次浮点乘法只要 1 个周期左右。**99% 的时间在解释，不在算。**

带宽分析那一节：

```
numpy 版本搬运约 56 MB, 耗时 1.5 ms
-> 实测有效带宽 37.7 GB/s
算术强度 0.11 FLOP/Byte  →  彻底 memory-bound
```

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `N` | 2M → 100K | 数据进得了 L2/L3，numpy 的每元素成本明显下降；`out=` 版的劣势可能缩小 | 性能结论**依赖工作集大小**。小数据的 benchmark 会骗人 |
| `N` | 2M → 8M | 超出 L3，带宽成为绝对瓶颈，几种 numpy 写法趋同 | memory-bound 时，写法差异被访存淹没 |
| `REPEAT` | 3 → 10 | 结果更稳定 | 提醒：只跑一次的 benchmark 不可信 |
| `SUB` | 200K → 20K | 外推误差变大，一致性检查的偏差上升 | 外推是有代价的，别外推太远 |

**建议做第一个实验**：把 `N` 调到 100K 再调到 8M，看几种写法的排名会不会变。
**排名会变** —— 这正是"必须实测"的最好证明。

## 七、对编译方向的意义

这个 demo 论证了表格里那句痛点的实质：

> "局部手动优化开发成本高、维护难、破坏 Python 研发体系"

手工优化不仅**贵**，而且**经常是负收益**。

所以编译方向的目标应该是：让算法同学写 v1 那样自然的代码，
由编译器基于**实际的 cost model**（而不是人的直觉）自动选择 codegen 策略，
稳定产出接近 v5 的性能。

这也解释了为什么 PGO（profile-guided optimization）和 auto-tuning（TVM/Ansor）
在这个领域这么重要：**因为最优策略靠推理猜不出来，只能靠测。**
