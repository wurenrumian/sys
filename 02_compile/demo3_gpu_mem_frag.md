# demo3 · 显存碎片：为什么显存"还剩很多"却 OOM

> 分页不是消灭了碎片，它把**无法预测**的外部碎片，换成了**用一个旋钮就能调**的内部碎片。

---

## 一、真实场景：这段代码对应线上的什么

推荐大模型推理时，每个请求要为它的用户序列分配一块 KV Cache / 中间张量。
而推荐场景的请求是**不定长**的：

```
请求 A：用户序列长 8    →  申请 1.5 MB
请求 B：用户序列长 2000 →  申请 380 MB
请求 C：用户序列长 45   →  申请 8 MB
...
```

请求不断到达和结束，显存上就被切得千疮百孔。于是出现那个经典的诡异现象：

> **`nvidia-smi` 显示还剩 1.2GB，但申请 400MB 失败了。**

因为剩下的 1.2GB 分散在几百个不连续的小洞里，最大的一个洞只有 200MB。

**LLM 场景反而没这么严重**（定长 batch、请求形态规整），
所以这是推荐场景特有的、更尖锐的问题。对应表格里：
"设计显存碎片实时清理与内存复用策略，减少推荐大模型推理过程中的显存碎片，提升显存利用率；
构建基于显存使用情况与推理任务特征的智能分配模型，实现显存的动态按需分配"。

---

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造不定长的分配/释放序列

```python
size = clip(rng.pareto(1.2) * 6 + 1, 1, 400)     # 单位 MB，长尾
```

Pareto 分布模拟"多数请求很短、少数极长"。默认下中位数约 5MB、p99 约 100MB、最大 400MB。

**最关键的设计**（否则整个实验没有意义）：

```python
WATERMARK = 0.65      # 存活数据总量始终不超过显存的 65%
```

存活量被限制在水位以下，意味着**一个理想的分配器应该永远不 OOM**。
于是后面看到的**任何一次 OOM，都只可能是碎片造成的**，不是真的不够用。

> 如果让负载打满显存，OOM 次数就只反映"谁装得下更多"，完全无法区分碎片问题。
> 这个水位设计是整个 demo 能成立的前提。

### 第 2 步：实现四种分配器

在同一段分配/释放序列上跑 First-Fit / Best-Fit / Buddy / Paged，
每 200 步采样一次统计量。

### 第 3 步：水位扫描

把水位从 60% 扫到 95%，看每种分配器在什么水位开始垮，以及页大小的影响。

---

## 三、涉及的算法

### First-Fit（连续分配 + 首次适配）

维护一个按地址有序的空闲区间列表，**从头扫，找到第一个够大的洞就用**。
释放时和相邻空闲区间合并。

- 优点：分配快（平均只扫一半）
- 缺点：低地址区被切得很碎

### Best-Fit（连续分配 + 最佳适配）

**扫描全部空闲洞，选最小的够用的那个。**

- 直觉：选最贴合的洞，浪费最少
- 实际：**制造出大量用不上的小碎屑**（每次都留下一个刚好不够用的零头），空闲块数量爆炸
- 而且每次分配是 O(空闲块数)，还更慢

### Buddy（伙伴系统）

把申请大小**向上取整到 2 的幂**。大块可以逐级劈半，释放时和"伙伴"（地址异或 2^k）合并。

- 优点：合并是 O(log n)，块级几乎无外部碎片
- 缺点：**内部碎片严重** —— 申请 33MB 实际占用 64MB，浪费 48%

### Paged（分页，vLLM PagedAttention 的思路）

把显存切成**固定大小的页**，一次申请 = 一组**不必连续**的页 + 一张页表。

```
请求要 10MB，页大小 4MB  →  分配 3 页（12MB），这 3 页在物理上可以完全不相邻
```

- **外部碎片直接降为 0**：任何一页都能被任何请求使用，不再要求物理连续
- 代价：**内部碎片**（最后一页的零头，平均半页）+ 一层间接寻址

## 四、方案对比

| 分配器 | 外部碎片 | 内部碎片 | 分配复杂度 | 关键代价 |
|---|---|---|---|---|
| **First-Fit** | 高 | 0 | O(空闲块数) | 显存最后 20~30% 用不上 |
| **Best-Fit** | 高（碎屑更多） | 0 | O(空闲块数) | 空闲块数爆炸，且更慢 |
| **Buddy** | 低 | **~30%** | O(log n) | 向上取整到 2 的幂，长尾分布下浪费极大 |
| **Paged** | **0** | 可调（页越小越少） | O(页数) | 页表开销 + 间接寻址；页太大则内部碎片高 |

### 两种碎片的定义（读输出前必须搞清楚）

```
外部碎片率 = 1 - 最大连续空闲块 / 全部空闲显存
    回答的是："我还剩 1GB，但我能一次性申请到多大？"
    这个值越高，越容易出现"显存明明够却 OOM"

内部碎片   = 1 - 实际申请量 / 实际占用量
    向上取整浪费掉的部分
```

## 五、怎么读输出

### 主表（长尾负载）

```
  分配器              OOM次数    峰值占用   外部碎片率   内部碎片   空闲块数
  First-Fit(连续)          0     2657MB       11.7%      0.0%        58
  Best-Fit(连续)           0     2657MB       15.9%      0.0%       184   ← 碎屑更多
  Buddy(2的幂)           321     3406MB        3.6%     28.6%        22   ← 内部碎片
  Paged(4MB/页)            0     2795MB        0.0%      5.0%       325   ← 外部碎片为 0
```

- Best-Fit 的空闲块数是 First-Fit 的 3 倍 —— **"挑最贴合的洞"反而制造更多碎屑**
- Buddy 的内部碎片 28.6%，直接导致 321 次 OOM
- Paged 的外部碎片精确为 0

### 水位扫描（本 demo 的核心，也是结论所在）

```
  水位    First-Fit  Best-Fit    Buddy  Paged/4MB  Paged/1MB  Paged/256KB
  60%             0         0       16          0          0            0
  70%             1         0      123          0          0            0
  80%            37        23      311         38          0            0
  90%           159        90      553        568          0            0
  95%           208       134      652        685         53            0
```

**每一个非零数字都是碎片的代价**（存活数据始终在水位以下，理想分配器应全程 0）。

三件事同时发生：

1. **连续分配器在 70~80% 水位就开始 OOM** → 显存的最后 20~30% 你根本用不上
2. **Buddy 最早垮** → 向上取整制造了 ~30% 内部碎片
3. **Paged/4MB 在 80% 以上同样 OOM，但原因完全不同** → 它没有外部碎片，
   垮掉是因为 4MB 的页对中位数仅 5MB 的请求**太粗**，内部碎片高达 20%。
   **把页减到 1MB / 256KB，抗压水位显著提高。**

> **结论不是"分页万能"，而是：**
> **分页把难以控制的外部碎片，换成了可以用"页大小"这一个旋钮精确调节的内部碎片。**
>
> 这才是它的真正价值 —— 从一个**无法预测**的问题，变成一个**可以定量权衡**的问题。
> 而"可定量权衡"是工程上最值钱的性质：你可以为它建模、可以自动调参、可以给出 SLA。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `PAGE_MB` | 4 → 0.25 | 主表里 Paged 的内部碎片从 5% 掉到很小 | 页大小就是那个旋钮，收益立竿见影 |
| `PAGE_MB` | 4 → 32 | 内部碎片飙升，Paged 变成最差的之一 | 分页不是免费的，页太粗比连续分配还糟 |
| `PARETO_A` | 1.2 → 3.0 | 尾巴变短，请求大小趋于一致，**所有分配器都变好** | **碎片问题的根源是大小差异，不是分配算法本身**。这也是 LLM 定长 batch 没这么严重的原因 |
| `PARETO_A` | 1.2 → 0.8 | 尾巴更长，连续分配器更早垮 | 推荐场景比 LLM 更需要分页的直接证据 |
| `WATERMARK` | 0.65 → 0.9 | 所有分配器 OOM 都增加 | 水位越高，碎片的伤害越大（可用空间越小，越难找到合适的洞） |

**建议做 `PARETO_A` 那两个实验**：它能让你把"碎片"这个现象归因到**负载特征**而不是**算法好坏**，
这是理解这类问题的关键一步。

## 七、对推荐场景的意义 / 往下挖

- **这就是 vLLM 的 PagedAttention 之所以是范式级改进的原因**：它把操作系统里
  成熟了几十年的虚拟内存分页思想，搬进了 KV Cache 管理。
- **推荐比 LLM 更需要它**：用户行为序列长度是长尾的，大小差异越大，连续分配器的碎片越严重。
- **页大小应该是自适应的**：表格里"构建基于显存使用情况与推理任务特征的智能分配模型"，
  说的就是根据实时负载特征动态选择这类参数。这个 demo 给了它一个可量化的目标函数。
- **分页还顺带解锁了前缀共享**：多个请求的公共前缀可以指向**同一批物理页**，
  直接对应电商推荐那条课题里的"用户多刷之间 KV Cache 的共享"。
  这是分页的第二个红利，往往比省碎片更值钱。
