# demo4 · 动态批处理：吞吐与 P99 的取舍

> 固定批策略的**低谷 P99 反而比尖峰更差** —— 系统最闲的时候，用户等得最久。

---

## 一、真实场景：这段代码对应线上的什么

推荐推理服务的现实是：**GPU 喜欢大批，用户讨厌等待。**

GPU kernel 的耗时大致是 `固定启动开销 + 每条请求的边际计算`：

```
batch=1   →  2.0 + 0.012×1   = 2.01 ms   →  每条摊到 2.01 ms
batch=256 →  2.0 + 0.012×256 = 5.07 ms   →  每条摊到 0.02 ms   （100 倍差距）
```

正是那个**固定开销**让"攒批"有意义。但攒批要等，**等就是延迟**。

而推荐流量还有两个特点让这件事更难：

- **日内周期**：白天晚上差好几倍
- **突发尖峰**：大促、开屏推送、热点事件，几秒内翻几倍

对应表格里："构建基于推荐请求特征（如用户活跃度、请求峰值）的动态批处理阈值自适应模型，
实时调整批处理尺寸"。

---

## 二、这个 demo 具体干了什么（流程）

### 第 1 步：造流量

```python
qps(t) = BASE_QPS × (1 + 0.4·sin(2πt/20s))     # 正弦日内波动 ±40%
         × SPIKE_X  若 t 落在尖峰段              # 中段一个 3 倍尖峰
到达间隔 ~ Exponential(1/qps)                    # 泊松过程
```

泊松到达是排队论的标准假设，也接近真实的独立用户请求。

### 第 2 步：GPU 成本模型

```python
batch_time_ms(bs) = GPU_FIXED_MS + GPU_PER_REQ_MS × bs      # 默认 2.0 + 0.012·bs
```

这是真实 GPU kernel 的典型形态（固定的 launch/同步开销 + 线性的计算）。

### 第 3 步：离散事件模拟

单个 GPU worker，按事件推进时间。核心循环每轮做三件事：

1. 把当前时刻之前到达的请求全部入队
2. **根据策略决定"发车"还是"继续等"**
3. 发车：算出这一批的耗时，给批内每个请求记录端到端延迟（= 完成时刻 − 到达时刻）

### 第 4 步：三种策略

| 策略 | 规则 |
|---|---|
| `fixed_bs` | **攒够 N 条才发车**，不够就一直等 |
| `fixed_timeout` | 攒够 max_bs **或** 最老的请求等满 T 毫秒，哪个先到就发 |
| `adaptive` | 等待时间随队列积压动态变：`T = 0.5 + 4.0 × (积压/max_bs)`；积压 ≥ max_bs 直接满批 |

### 第 5 步：分段统计

把延迟按"尖峰段 / 非尖峰段"拆开，分别算 P99/P999 —— **这一步是本 demo 的点睛之笔**。

## 三、涉及的机制

### 攒批的收益与代价

```
收益：固定开销被 batch_size 摊薄  →  吞吐 ↑、GPU 利用率 ↑
代价：先到的请求要等后来者        →  排队延迟 ↑
```

### 为什么固定批在低谷会崩（本 demo 的反直觉点）

`fixed_bs=256` 在流量低谷时，凑满 256 条要等很久，先到的请求就**饿死在队列里**。
而这恰恰是 GPU 最闲、本该最快响应的时候。

**完全是反的**：系统越闲，用户等得越久。

### 自适应的规则为什么有效

```
积压少  →  说明流量低  →  几乎不等就发车（反正 GPU 闲着，何必让人干等）
积压多  →  说明流量高  →  愿意多等一点凑大批（此时凑批几乎不花时间，白赚吞吐）
```

它在低谷期表现得像"小超时"，在高峰期表现得像"大批量"，**两种状态自动切换**。
本质上这是一个用队列长度做反馈的控制器。

### 一个离散事件模拟的经典坑

```python
EPS = 1e-9
if oldest_wait < timeout_ms - EPS and i < n:
```

`oldest_wait = now - arrivals[q[0]]` 是浮点算出来的，可能略小于 `timeout_ms`，
而 `arrivals[q[0]] + timeout_ms` 又恰好等于 `now` → 时间无法推进 → **死循环**。
这个 `EPS` 不是随手加的，是被这个 bug 逼出来的。

## 四、方案对比

| 策略 | 优点 | 代价 | 什么时候用 |
|---|---|---|---|
| **固定批 bs 小** | 延迟低 | 固定开销占比高，GPU 利用率差 | 流量极低且 SLA 极严 |
| **固定批 bs 大** | 吞吐高 | **低谷期请求被饿死**，P999 灾难 | 离线批处理（没有延迟要求） |
| **固定超时** | 延迟有**硬上界**，可预测 | 超时值是静态的：调小则高峰吞吐不够，调大则低谷白等 | 流量平稳的服务 |
| **自适应** | 低谷不等、高峰凑批，两端都不吃亏 | 多一个反馈环路，要调阈值函数；有稳定性风险 | **流量有周期和尖峰的推荐场景** |

## 五、怎么读输出

### 主表

```
策略                    P50      P99     P999      最大   平均批   GPU利用率
固定批 bs=16          10.7ms   19.6ms   22.3ms   23.1ms    16.0     34.7%
固定批 bs=256        130.0ms  469.8ms  536.6ms  564.0ms   255.4      1.7%
固定超时 5ms           4.6ms    7.2ms    7.4ms    8.6ms     5.2     23.5%
固定超时 20ms         12.4ms   22.2ms   22.5ms   23.5ms    18.4     11.6%
自适应                 2.9ms    4.0ms    4.1ms    4.2ms     2.1     83.3%
```

自适应在**所有延迟分位**上都最好，同时 GPU 利用率最高。

> 注意 `GPU利用率` 这一列的含义是"GPU 忙碌时间占比"。固定大批的利用率极低（1.7%），
> 因为它大部分时间在**空等请求凑批**，而不是在算。

### 分段表（本 demo 最反直觉的一节）

```
策略                低谷P99    尖峰P99   低谷P999   尖峰P999
固定批 bs=256      476.8ms   370.5ms   538.7ms    418.0ms   ← 低谷比尖峰还差！
固定超时 5ms         7.2ms     7.2ms     7.4ms      7.2ms
自适应               4.0ms     4.1ms     4.1ms      4.2ms
```

**固定批策略的低谷 P99（476.8ms）比尖峰 P99（370.5ms）更差。** 这是反直觉但完全正确的：

- 尖峰期请求多，一眨眼就凑满一批发车了
- 低谷期请求稀疏，先到的请求要干等后来者凑够批

固定超时修掉了这一点，但延迟被超时值**死死锁住**（5ms 配置就永远是 ~7ms）。
自适应在低谷期 P99 只有 4.0ms —— **优于任何静态配置**，同时高峰期还能自动放大批量。

## 六、动手：改参数能验证什么

| 参数 | 调成 | 会发生什么 | 说明了什么 |
|---|---|---|---|
| `BASE_QPS` | 800 → 100 | 固定批 bs=256 彻底崩溃（要等更久才凑满）；自适应几乎不受影响 | **自适应的价值随流量波动幅度增长** |
| `BASE_QPS` | 800 → 5000 | 各策略趋同（高流量下人人都能凑满批） | 高负载时策略不重要，产能才重要 |
| `SPIKE_X` | 3 → 8 | 尖峰段所有策略的 P999 都恶化 | 突发的伤害无法靠调度完全消除，只能靠产能余量 |
| `GPU_FIXED_MS` | 2.0 → 0.2 | 攒批的收益大幅下降，小批策略变得可行 | **攒批的全部动机来自固定开销**。固定开销小了就不必攒批 |
| `GPU_PER_REQ_MS` | 0.012 → 0.1 | 大批变得很贵，最优批变小 | 边际成本高时，攒批的性价比下降 |

**建议做 `GPU_FIXED_MS` 那个实验**：把它调到 0.2，你会看到整个"批处理"话题的前提消失了。
这能让你把批处理理解成"摊薄固定开销"的手段，而不是一个孤立的技巧。

## 七、往下挖

本 demo 的自适应规则只用了**队列积压**这一个信号，已经明显优于静态策略。
真实系统还能用上更多信号，这正是表格那条课题的空间：

| 信号 | 能带来什么 |
|---|---|
| **请求特征**（用户序列长度） | 不是所有请求等价 —— 长序列请求的实际计算量大得多，应该按"计算量"而不是"条数"凑批 |
| **时间特征**（日内周期、活动日历） | 可以**预测**尖峰而不是被动响应 |
| **SLA 反馈**（实时 P99 距离 SLA 的余量） | 有余量时更激进地凑批，逼近 SLA 时立刻发车 |
| **显存约束** | 大批需要更多 KV Cache，要和 `02/demo3` 的显存分配**协同决策** |

更进一步：这本质上是个在"吞吐-延迟"帕累托前沿上的**实时控制问题**，
可以上强化学习 / 模型预测控制（MPC），而不只是手写规则。
但要注意控制环路本身的稳定性 —— 反馈太激进会震荡。
